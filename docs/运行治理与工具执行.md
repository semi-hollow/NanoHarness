# 运行治理与工具执行

> 模型只能提出 ToolCall；Runtime 决定本 Turn 是否可见、这次调用是否获准、是否已经
> 执行过，以及什么事实可以进入下一 Turn。

# 1. 主链

```text
Model ToolCall
    ↓
ToolExecutionPipeline._execute_call()
    ├── allowed-tool / guardrail checks
    ├── ask_human durable barrier
    └── remember_memory provenance check
    ↓
OperationTracker.build_operation_intent()
    ↓
OperationTracker.resolve_existing_operation()
    ├── unknown outcome / stale → fail closed
    └── executed + same fingerprint → reuse Observation
    ↓
ToolAuthorizationGate.authorize()
    ├── Hook DENY
    ├── ASK → ApprovalRepository
    └── ALLOW
    │
    ├── rejection / replay feedback
    │      ↓
    │   ToolFeedback.append_tool_observation()
    │      ↓
    │   tool Message (a StopRequest may follow)
    │
    └── authorized execution
    ↓
side-effect only:
Operation Ledger = approved → executing
    ↓
ToolExecutionPipeline._run_tool()
    ↓
ToolGateway.execute()
    ↓
raw Observation
    ↓
HookManager.after_tool()
    ↓
final / redacted Observation
    ↓
OperationTracker.record_execution_result()
    ↓
Ledger / WorkingMemory / Evidence / Trace / Checkpoint
    ↓
budget gate
├── stop     → no next-Turn tool Message
└── continue → AgentRunSession.messages(role=tool)
```

核心不变量：

```text
Model proposes
Runtime controls side effects
```

# 2. 三个不同问题

| 边界 | 回答的问题 | Canonical Owner |
|---|---|---|
| Routing | 当前 Turn 模型能看到哪些 Tool？ | `ToolRouter.route()` |
| Authorization | 这一次具体调用允许执行吗？ | `ToolAuthorizationGate.authorize()` |
| Dispatch | 已获准调用交给哪个 Tool implementation？ | `ToolGateway.execute()` / `ToolRegistry` |

Schema 合法不等于调用获准；调用获准也不代表 Tool 名称和参数一定可执行。分开三个
边界可避免 `ToolRegistry` 同时承担 Session、Approval、Ledger 与环境策略。

# 3. Routing 与执行复核

`TurnPreparation.prepare_turn()` 调用 `ToolRouter.route()`，从同一个
`ToolRoute` 得到：

```text
schemas
→ 发给模型

allowed_names
→ ToolExecutionPipeline 执行时再次复核
```

模型请求一个未在本 Turn 暴露的 Tool 时，Pipeline 在任何 HITL、Ledger 或 Gateway
动作之前拒绝。模型可见能力和 Runtime 放行集合因此不会漂移。

# 4. Operation Intent 与副作用分类

`OperationTracker.build_operation_intent()` 把 ToolCall 转换成稳定的
`OperationIntent`：

```text
tool identity
+ normalized target
+ action
+ side-effect semantics
+ operation key / fingerprint
```

只有存在外部或 workspace 副作用的 intent 才进入 Operation Ledger。普通读取仍受
routing、guardrail、Hook 和 Tool contract 约束，但不制造无意义的 durable operation
record。

特殊协议：

- `ask_human` 进入 `HumanInputRepository` 的 durable 等待/回答闭环；
- `remember_memory` 必须携带能在当前 Session user Message 中验证的
  `source_quote`，无法建立 provenance 时 fail closed；
- Worker coordination 由 Multi-Agent route/version authorization 管理，不冒充普通读取。

# 5. 授权（Authorization）

```text
ToolAuthorizationGate.authorize()
    ↓
hooks.before_tool()
    ├── ExecutionEnvironmentHook
    ├── PermissionHook
    └── configured lifecycle hooks
    ↓
DENY / ASK / ALLOW
```

- `DENY`：不执行 Tool；
- `ASK`：先持久化 ApprovalRequest 与 WAITING_APPROVAL checkpoint；
- `ALLOW`：返回授权结果，但副作用还没有发生。

已有 Approval 只有在 operation fingerprint 未漂移时才可复用；目标变化属于 stale
authorization，必须重新决策，避免 TOCTOU。

# 6. Operation Ledger 与 crash 边界

```text
planned
→ pending / approved
→ executing
→ executed / failed
```

`executing` 的含义不是“继续等待当前进程”，而是：

> Runtime 已越过副作用边界，但没有 durable 最终结果。

外部状态可能已经改变，因此自动重放会重复副作用。恢复时必须 fail closed，由显式
检查确认结果后再继续。

已存在 `executed` 且 fingerprint 一致时，Runtime 重建先前 Observation，不再次调用
Tool。Ledger 因此同时提供 idempotency 与 unknown-outcome boundary。

# 7. 唯一执行出口

`ToolExecutionPipeline._run_tool()` 的顺序固定：

```text
last terminal control check
→ side effect: record approved/executing
→ ToolGateway.execute()
→ HookManager.after_tool()
→ OperationTracker.record_execution_result()
→ WorkingMemory / Evidence / Trace / Checkpoint
→ budget and failure classification
→ append tool Message when Run continues
```

副作用必须在 Gateway 前写 `executing`，因为进程可能在外部状态变化后立即崩溃；
`executed/failed` 只能在 Gateway 返回并经过 after_tool 后提交。

# 8. Observation 与脱敏

```text
raw Observation
→ HookManager.after_tool()
→ SecretRedactionHook
→ final Observation
```

正常链路中的 Ledger result、WorkingMemory、Evidence、Trace、Checkpoint、
`session.observations` 和下一 Turn tool Message 都消费 after_tool 处理后的结果。

该边界保护 Runtime 内部传播，不是全系统 DLP；Tool 在 Runtime 外部自行写出的日志或
远端数据不可能被事后 Hook 回收。

# 9. Hook 异常边界

Hook 是生命周期扩展点，不是 Authorization 本身。

| Hook 类型 | 例子 | 异常策略 |
|---|---|---|
| 决策 Hook | `before_model`、`before_tool`、`on_stop` | fail closed，转换为 DENY/阻断事实 |
| 变换/通知 Hook | `after_model`、`after_tool`、`on_checkpoint` | 记录并隔离，保持主 Runtime 状态可解释 |

具体执行权仍由 Application service 与 durable repositories 收口。

# 10. Failure 与下一 Turn

Final Observation 进入 `StepController.classify_observation()`：

- 验证命令正常执行但测试或编译目标未通过时，作为可恢复反馈，不等同基础设施异常；
- permission、arguments、patch mismatch 和 command failure 使用不同 recovery hint；
- 连续失败、重复 ToolCall、wall-clock、step 和 cost 分别受有界控制。

Pipeline 先记录本轮保留的 assistant ToolCall。拒绝、回放、unknown-outcome 等治理
分支只要产生 protocol Observation，就会立即写入 tool Message，即使随后返回
`StopRequest`；正常 Gateway 结果先进入 typed Observation、Trace 与 Checkpoint，预算
允许继续时才写入 tool Message。没有 `StopRequest` 时 `AgentLoop` 才进入下一 Turn。

# 11. 信任边界（Trust Boundary）

```text
Untrusted proposal
├── Model ToolCall
└── Tool arguments
        ↓
Deterministic Runtime controls
├── route / schema / guardrail
├── authorization / approval fingerprint
├── side-effect ledger
└── execution environment
        ↓
External effect
        ↓
Typed and redacted Observation
        ↓
Durable facts and next model input
```

## 源码入口（Source Anchors）

- `agent_forge/tools/tool_router.py::ToolRouter.route()`：本 Turn Tool surface。
- `agent_forge/runtime/application/tool_execution.py::ToolExecutionPipeline._execute_call()`：单次 ToolCall 主链。
- `agent_forge/runtime/application/tool_authorization.py::ToolAuthorizationGate.authorize()`：Hook 与 Approval 收口。
- `agent_forge/runtime/application/operation_tracker.py::OperationTracker`：副作用身份、replay 与 Ledger。
- `agent_forge/runtime/adapters/hook_manager.py::HookManager`：生命周期 Hook 聚合。
- `agent_forge/tools/registry.py::ToolRegistry.execute()`：Tool contract 与 dispatch。
- `agent_forge/runtime/application/tool_feedback.py::ToolFeedback`：Observation 到 Session/Trace 的统一反馈。
- `agent_forge/runtime/application/step_control.py::StepController`：失败分类与有界停止。
