# 运行治理与工具执行

> 模型只能提出 ToolCall；Runtime 决定本 Model Step 可见哪些工具、具体调用是否获准、
> 副作用是否已经发生，以及怎样让每个调用形成唯一可恢复的 Observation。

# 1. 主链

```text
AgentResponse(content + ToolCalls)
    ↓
ToolExecutionPipeline.execute_calls()
    ↓
durable ConversationItem(role=assistant, complete batch)
    ↓
TaskCheckpoint.pending_execution
├── assistant_item_id
└── next_tool_call_index
    ↓
ToolExecutionPipeline._continue_pending_batch()
    ↓ each call in original order
ToolExecutionPipeline._execute_call()
    ├── current control / route / guardrail checks
    ├── ask_human durable barrier
    └── remember_memory provenance validation
    ↓
OperationTracker.build_operation_intent()
    ↓
OperationTracker.resolve_existing_operation()
    ├── executed + same fingerprint → reuse prior result
    ├── executing / unknown outcome → fail closed
    └── no prior effect → continue
    ↓
ToolAuthorizationGate.authorize()
    ├── DENY
    ├── ASK → durable Approval
    └── ALLOW
    ↓
side-effect only: Operation Ledger = approved → executing
    ↓
ToolExecutionPipeline._run_tool()
    ↓
ToolGateway.execute()
    ↓
HookManager.after_tool()
    ↓
OperationTracker.record_execution_result()
    ↓
ToolFeedback.append_tool_observation()
    ↓
durable ConversationItem(role=tool)
    ↓
advance pending cursor
```

核心不变量：

```text
Model proposes
Runtime controls side effects
ConversationThread records protocol truth
Checkpoint points to unfinished execution
```

# 2. 为什么先持久化完整 assistant batch

一个模型响应可以同时包含文本、reasoning 和多个 ToolCall。Runtime 不能先执行第一个调用，
再把剩余提案留在易失内存中：如果进程在外部副作用后崩溃，恢复端将不知道模型完整提出了
什么，也无法判断下一项调用。

因此 `ToolExecutionPipeline.execute_calls()` 固定执行：

```text
provider response
→ preserve complete assistant content/tool_calls
→ durable append to conversation.jsonl
→ persist PendingExecutionPointer
→ execute calls sequentially
```

预算裁剪、`ask_human` 排他屏障或后续终止只改变某个调用的执行 disposition，不删除模型
原始 batch。没有执行的调用也会得到 deterministic skipped/deferred Observation，从而闭合
assistant/tool 协议。

# 3. Resume 与 crash 边界

`ToolExecutionPipeline.resume_pending_calls()` 不调用模型，而是从 v4 checkpoint 找到原
assistant item，再按 `next_tool_call_index` 继续：

```text
TaskCheckpoint.pending_execution
    ↓
ConversationThreadRepository.get_item(assistant_item_id)
    ↓
restore original ToolCalls + routing metadata
    ↓
current Tool registry may only narrow executable set
    ↓
continue from durable cursor
```

恢复时仍重新经过当前 control、guardrail、authorization 与 operation replay checks；但
Runtime 不允许扩大原 Model Step 隐藏的工具，也不依赖模型重新生成相同 ToolCall。

三个关键崩溃窗口：

| 崩溃位置 | 恢复行为 |
|---|---|
| assistant item 已写、pointer 未写 | 扫描同 Turn 唯一未闭合 batch，重建 cursor；多个候选则 fail closed |
| Tool Observation 已写、cursor 未推进 | 发现稳定 tool item identity，只修复 cursor，不重复执行 |
| Ledger 已是 `executing`、最终结果未写 | 外部结果可能已发生，标记 unknown outcome，不自动重放 |

Tool item identity 绑定 `assistant_item_id + batch index + provider tool_call_id`。Provider 在
不同 Model Step 重用 call ID 不会造成跨 batch 冲突。

# 4. 三个不同治理问题

| 边界 | 回答的问题 | Canonical Owner |
|---|---|---|
| Routing | 当前 Model Step 模型能看到哪些 Tool？ | `ToolRouter.route()` |
| Authorization | 这一次具体调用允许执行吗？ | `ToolAuthorizationGate.authorize()` |
| Dispatch | 已获准调用交给哪个实现？ | `ToolGateway.execute()` / `ToolRegistry` |

`ModelStepPreparation.prepare_model_step()` 调用 `ToolRouter.route()`，从同一个 `ToolRoute`
取得 `schemas` 和 `allowed_names`：前者发给模型，后者在执行时再次复核。Schema 合法不等于
调用获准；调用获准也不代表目标和参数一定满足执行环境策略。

# 5. Operation Intent 与副作用身份

`OperationTracker.build_operation_intent()` 把 ToolCall 规范化为稳定身份：

```text
tool identity
+ normalized target
+ action
+ side-effect semantics
+ operation key / fingerprint
```

只有外部或 workspace 副作用进入 Operation Ledger。读取仍受 routing、guardrail、Hook 与
Tool contract 约束，但不制造没有价值的 durable operation record。

Ledger 状态：

```text
planned
→ pending / approved
→ executing
→ executed / failed
```

`executed` 且 fingerprint 一致时复用结果；同 identity 不同 fingerprint 属于 stale；
`executing` 没有 durable 结果表示副作用结果未知。该边界提供 idempotency，而不是宣称
本地文件协议可以回滚任意外部系统。

`run_command` 是允许执行测试/编译的低层 fallback，命令本身可能产生任意 workspace
副作用，因此也进入 Ledger；它的 key 绑定 durable assistant ToolCall invocation。
同一调用 crash resume 会回放结果，而新 Model Step 中相同命令仍可重新执行。

# 6. 授权与 Approval

```text
ToolAuthorizationGate.authorize()
    ↓
hooks.before_tool()
    ├── ExecutionEnvironmentHook
    ├── PermissionHook
    └── configured lifecycle hooks
    ↓
DENY / ASK / ALLOW
```

- `DENY`：不调用 Tool，并形成拒绝 Observation；
- `ASK`：持久化 ApprovalRequest，Turn 保持 active，当前 Run 进入 `waiting_approval`；
- `ALLOW`：仅表示授权通过，副作用尚未发生。

Approval 与 operation fingerprint 绑定。拒绝后，当前调用得到一条 Observation，batch
其余调用得到 skipped Observation，下一 Model Step 根据拒绝事实重新规划。

# 7. 唯一执行出口

`ToolExecutionPipeline._run_tool()` 的顺序固定：

```text
last terminal control check
→ side effect: record approved/executing
→ ToolGateway.execute()
→ HookManager.after_tool()
→ OperationTracker.record_execution_result()
→ WorkingMemory / Evidence / Trace / Checkpoint
→ durable Thread tool item
→ budget and failure classification
```

副作用必须在 Gateway 前写 `executing`，因为进程可能在外部状态改变后立即崩溃；
`executed/failed` 只能在 Gateway 返回并经过 after_tool 后提交。

# 8. Observation 与协议完整性

```text
raw Observation
→ HookManager.after_tool()
→ SecretRedactionHook
→ final Observation
→ ConversationThreadRepository.append(role=tool)
→ AgentRunSession bounded mirror
→ next PreparedModelStep projection
```

Ledger result、WorkingMemory、Evidence、Trace、Checkpoint 与后续模型输入都消费 after_tool
处理后的结果。该边界保护 Runtime 内部传播，不是全系统 DLP；Tool 在 Runtime 外自行写出的
远端日志不能被事后 Hook 回收。

每个 ToolCall 必须结束于且只结束于一条合法 Observation：

- 正常执行、参数错误、DENY、Approval 拒绝和 replay 都产生明确结果；
- 超出执行预算或被人工屏障推迟的调用产生 non-execution Observation；
- `waiting_approval`、`waiting_human`、`paused` 尚未产生结果时 cursor 停在原调用；
- cancel/failure 等 terminal stop 为 batch 余项写 `not executed` Observation 后收口。

# 9. `ask_human` 的 authority 与 Provider 投影

`ask_human` 建立同 batch 排他屏障。Runtime 先持久化问题并停止；Resume 取得真实人工回答后：

```text
authoritative raw journal order
human/operator ConversationItem(human_authority=true)
→ tool Observation that closes ask_human
```

这个顺序保证授权 provenance 先于 Runtime 派生结果。Provider 协议要求 tool result 紧跟
assistant ToolCall，因此模型输入由 `load_transaction_safe_conversation_page()` 只读投影为：

```text
assistant ToolCalls
→ all Tool Observations
→ authoritative human answer
```

投影不改写 raw journal。Provider `role=user` 不赋予 human authority；内部审计只认
`origin in {human, operator}` 且 `human_authority=true` 的 ConversationItem。

# 10. `remember_memory` 的窄授权边界

`remember_memory` 是模型可见的显式持久化操作，但不能从旧历史或 runtime coordination
伪造用户授权：

```text
current authoritative human message
→ exact source_quote match
→ current Model Step Management Candidates
→ CREATE / UPDATE / NOOP validation
→ LongTermMemoryService
```

`UPDATE/NOOP.target_memory_id` 必须属于当前候选；`CREATE` 生成新 identity。`scope=user`
只用于明确跨项目偏好；默认是 project。多个 memory 调用按 batch 原顺序独立处理，不额外
调用第二个模型。完整 Memory 角色见 [上下文工程](上下文工程.md)。

# 11. Hook 与失败边界

| Hook 类型 | 例子 | 异常策略 |
|---|---|---|
| 决策 Hook | `before_model`、`before_tool`、`on_stop` | fail closed，转换为 DENY 或阻断事实 |
| 变换/通知 Hook | `after_model`、`after_tool`、`on_checkpoint` | 记录并隔离，保持主状态可解释 |

Final Observation 进入 `StepController.classify_observation()`。验证命令执行成功但测试失败
属于可恢复任务反馈，不自动升级为基础设施异常；permission、arguments、patch mismatch、
command failure、重复调用和预算超限分别形成可区分的 recovery evidence。

# 12. 信任边界（Trust Boundary）

```text
Untrusted proposal
├── Model ToolCall
└── Tool arguments
        ↓
Deterministic Runtime controls
├── route / schema / guardrail
├── authorization / approval fingerprint
├── side-effect ledger
└── execution environment
        ↓
External effect
        ↓
Typed and redacted Observation
        ↓
Thread protocol truth + Run evidence + next model input
```
