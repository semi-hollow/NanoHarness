# 运行治理与工具执行

> 核心问题：模型返回 ToolCall 后，Runtime 如何把它转换为安全、可恢复、可审计的真实执行。

---

# 1. 主链

```text
LLM ToolCall
    │
    ▼
ToolExecutionPipeline._execute_call()
    │
    ▼
route recheck / repeat boundary
    │
    ▼
OperationTracker.build_operation_intent()
    │
    ▼
OperationTracker.resolve_existing_operation() [side-effect only]
    │
    ▼
ToolAuthorizationGate.authorize()
    │
    ▼
Authorization Result
    ├── DENY
    ├── ASK → ApprovalRepository
    └── ALLOW
    │
    ▼
Ledger: executing                     [side-effect only]
    │
    ▼
ToolExecutionPipeline._run_tool()
    │
    ▼
ToolGateway.execute() → ToolRegistry.execute()
    │
    ▼
raw Observation
    │
    ▼
HookManager.after_tool()
    │
    ▼
final/redacted Observation
    │
    ├── OperationTracker.record_execution_result() [side-effect only]
    ├── AgentRunSession.working_memory / evidence
    ├── Trace / AgentRunSession.observations
    └── TaskCheckpoint
    │
    └── if Run continues → AgentRunSession.messages(role=tool)
```

核心：

```text
Model proposes
Runtime authorizes
Gateway dispatches
Tool executes
Observation becomes fact
```

---

# 2. Hook 是什么

NanoHarness 使用的是：

```text
Explicit Lifecycle Hook Pattern
```

不是 AOP，也不是 decorator 隐式拦截。

Runtime 在固定生命周期点显式调用：

```text
before_model
after_model
before_tool
after_tool
on_checkpoint
on_stop
```

统一接口：

```text
RuntimeHook
```

统一聚合器：

```text
HookManager
```

HookManager 负责：

```text
注册顺序
调用顺序
决策合并
异常隔离 / fail-closed
```

异常策略不是统一 fail-closed：

```text
decision hooks: before_model / before_tool / on_stop
→ exception → DENY

transform / notification hooks: after_model / after_tool / on_checkpoint
→ exception → 记录失败并隔离，主链继续
```

Hook 不拥有：

```text
Approval state
Checkpoint state
Operation Ledger
Tool execution control flow
```

核心 Runtime 仍然拥有控制流。

---

# 3. 六个 Hook 生命周期点

| Lifecycle | 作用 | 当前默认内置业务控制 |
|---|---|---|
| `before_model` | 模型调用前决策扩展点 | 无专用内置控制，默认 DEFER |
| `after_model` | 模型返回后结果变换扩展点 | 无专用内置变换 |
| `before_tool` | 工具执行前 policy / environment 判断 | `ExecutionEnvironmentHook` + `PermissionHook` |
| `after_tool` | 工具结果进入 Runtime 前变换 | `SecretRedactionHook` |
| `on_checkpoint` | Checkpoint 已落盘后的观察/通知 | 当前内置 Hook 不占有状态，仅提供扩展点 |
| `on_stop` | Run 停止前条件判断 | 当前默认 Hook 不表达额外意见 |

当前真正承担内置治理的重点是：

```text
before_tool
after_tool
```

其余生命周期点主要提供统一扩展边界。

---

# 4. before_tool：环境边界与权限策略

```text
ToolAuthorizationGate.authorize(...)
↓
hooks.before_tool(HookContext)
↓
HookManager
├── ExecutionEnvironmentHook
├── PermissionHook
└── custom hooks
↓
DENY > ASK > ALLOW > DEFER
```

HookManager 合并规则：

```text
DENY
>
ASK
>
ALLOW
>
DEFER
```

所有 Hook 都返回 `DEFER` 时，`HookManager._merge()` 产生有效结果 `ALLOW`。

如果决策型 Hook 自己异常：

```text
fail closed
→ DENY
```

---

# 5. 执行环境 Hook（ExecutionEnvironmentHook）

执行前检查：

```text
command boundary
path boundary
```

例如：

```text
越界 path
→ DENY

不允许的 command
→ DENY
```

它回答：

> 这个调用是否越过当前 ExecutionEnvironment 的物理/命令边界？

---

# 6. 权限 Hook（PermissionHook）

底层：

```text
PermissionPolicy.decide(action, command)
```

基础规则：

```text
read / list / search  → ALLOW
validate              → ALLOW
memory_write          → ALLOW（另有 provenance gate）
write                 → ASK
run_command           → CommandPolicy → ALLOW / DENY
network/delete/
external_directory    → DENY
unknown action        → DENY
```

PermissionHook 再叠加：

```text
approval_mode
```

例如：

```text
LOCKED / DRY_RUN + side effect
→ DENY

ON_RISK + run_command
→ ASK
```

所以：

```text
PermissionPolicy
= 基础动作 policy

PermissionHook
= policy + approval mode

ToolAuthorizationGate
= hook decision + human approval + stale fingerprint 收口
```

---

# 7. Authorization 不等于 Hook

完整 Authorization：

```text
ToolAuthorizationGate
├── hooks.before_tool
├── DENY handling
├── ASK → ApprovalRepository
├── WAITING_APPROVAL checkpoint
├── approved / rejected handling
└── approval fingerprint drift / stale protection
```

Hook 只是在 Authorization 生命周期边界上的 policy extension mechanism。

---

# 8. 工具结果脱敏（after_tool / Secret Redaction）

真实顺序：

```text
ToolGateway.execute()
↓
raw Observation
↓
hooks.after_tool(...)
↓
SecretRedactionHook
↓
final/redacted Observation
```

随后才进入：

```text
Operation Ledger execution result
WorkingMemory
Evidence
Validation Evidence
Trace
session.observations
Checkpoint.last_observation
if Run continues → session.messages(role=tool)
```

因此在正常、未发生 Hook 异常的 Runtime 主链中：

> 正常 Runtime 主链中，这些下游 projection 使用的是 **after_tool 处理后的 Observation**。

也就是说 Tool Observation 内容如果包含被环境识别出的敏感信息，Trace / Checkpoint / Session / WorkingMemory 等后续 Runtime 证据看到的是脱敏后的值。

边界：

```text
SecretRedactionHook
≠ 全系统 DLP
```

如果某个 Tool implementation 自己在 Runtime 外部写日志、文件或远端系统，after_tool Hook 不能回头清理那些外部副作用。

它主要保护的是：

```text
ToolGateway 返回之后
→ Runtime 内部继续传播的 Observation
```

---

# 9. 工具执行入口（ToolGateway / ToolRegistry）

`ToolGateway` 是 Runtime 使用的执行 Port。

当前主要实现：

```text
ToolRegistry
```

职责：

```text
① get / lookup 已注册 Tool
② schema 汇总
③ required 参数校验
④ 基础参数类型校验
⑤ dispatch 到对应 Tool.execute()
⑥ 捕获 Tool exception
⑦ 统一归一化成 Observation
```

---

# 10. dispatch 是什么

这里的 dispatch 很简单：

```text
tool name
↓
registry lookup
↓
找到具体 Tool implementation
↓
调用它
```

例如：

```text
name = "read_file"
↓
ToolRegistry.get("read_file")
↓
ReadFileTool
↓
ReadFileTool.execute(arguments)
```

所以：

```text
dispatch
= 按调用身份选择正确实现并把请求送过去
```

不是网络协议专有词。

---

# 11. Authorization 和 ToolGateway 为什么分开

## 授权（Authorization）

回答：

```text
这一次操作允许执行吗？
```

需要：

```text
action
side effect
approval mode
human approval
target fingerprint
ExecutionEnvironment
Run state
```

属于：

```text
Policy / Control Plane
```

## 工具入口（ToolGateway）

回答：

```text
如果已经允许，这个 Tool 能不能被正确调用？
```

需要：

```text
Tool 是否存在
required args
argument types
具体 Tool implementation
exception normalization
```

属于：

```text
Capability / Execution Plane
```

---

# 12. 为什么不能合并

例 1：

```text
replace_text(path="foo.py", old="a", new="b")
```

参数完全合法，但：

```text
write action
→ ASK
→ 尚未批准
```

所以：

```text
contract valid
≠ authorized
```

例 2：

```text
replace_text(path=123, ...)
```

即使人工已经批准：

```text
argument contract invalid
→ Gateway 拒绝
```

所以：

```text
authorized
≠ executable
```

如果把两者塞进 ToolRegistry，它就必须同时依赖：

```text
ApprovalRepository
OperationLedger
AgentRunSession
Checkpoint
ApprovalMode
ExecutionEnvironment
Tool Schema
Tool implementation
```

Registry 会从通用执行边界膨胀成整个 Runtime Control Plane。

因此分离是：

```text
Separation of Concerns
+
Defense in Depth
```

---

# 13. 操作状态表（Operation Ledger）

只对需要副作用治理的 OperationIntent 建立 durable record。

关键状态：

```text
planned
↓
approved / pending
↓
executing
↓
executed / failed
```

Crash 在：

```text
executing
```

表示：

> 已越过副作用边界，但最终结果未知。

因此：

```text
no blind replay
fail closed
```

---

# 14. 工具反馈（Tool Feedback）

final Observation 后还会进入：

```text
session.messages(role=tool)
WorkingMemory
Trace
recovery classification
validation evidence
```

ToolFeedback 负责统一这些反馈格式和 FailureSignal 记录，避免不同治理分支各自拼不同的 tool message。
