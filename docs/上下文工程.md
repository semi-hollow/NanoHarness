# 上下文工程

> 核心问题：一个 Turn 的有限 LLM Context Budget，如何在不同信息源之间分配和治理。

---

# 1. 业务分层

```text
                         LLM Context Budget
                                │
          ┌─────────────────────┼─────────────────────┐
          │                     │                     │
     Runtime State          Knowledge            Capability
          │                     │                     │
     Conversation           Repo Context          Skills
     Working State          External Evidence     Tool Schemas
     Task State             Long-term Memory      Permissions
```

不同 Source 不使用同一种治理方式：

| Source | 治理方式 |
|---|---|
| Conversation | protocol-aware compaction |
| Working State | bounded structured state |
| Repo Context | selective retrieval |
| Long-term Memory | relevance recall |
| Skill | progressive disclosure |
| Tool Schema | routing / selection |
| Permission | 确定性权威投影（deterministic authoritative projection） |

---

# 2. 当前 Turn 的输入构造

```text
AgentRunSession.messages
↓
conversation_history = list(session.messages)
↓ + optional runtime_control_message
PromptWindowRequest.conversation_history
↓
PromptWindowManager.prepare()
↓
PromptWindowResult.llm_messages
↓
PreparedTurn.llm_messages / PreparedTurn.tool_schemas
↓
ModelPort.chat(...)
```

业务含义：Conversation History 经 Prompt Window Governance 后，形成当前模型输入。

---

# 3. 当前 Turn 系统上下文（Current Turn System Context）

当前 Turn 系统上下文（`TurnSystemContextBuildReport`）由仓库组装器重新构建：

```text
RepositoryTurnSystemContextAssembler.build()
↓
TurnSystemContextBuildReport
↓ render()
turn_system_message
```

它被 render 成：

```python
turn_system_message = Message(
    role="system",
    content=turn_system_context.render(),
)
```

主要 section：

```text
system_prompt
permission_summary
attention_sink
available_tools
active_skill_cards
project_instructions
long_term_memory
selected_file_previews
retrieved_docs
working_memory_summary
working_memory_items
repo_map
selected_files
context_state
```

它不包含 Conversation History。

过去 Turn 的 system context 不 append 到 `session.messages`；下一 Turn 根据最新 Runtime / Repo / WorkingMemory / Skill / Permission 重建。

# 4. 对话历史（Conversation History）

Conversation History 独立来自：

```python
conversation_history = list(session.messages)
runtime_control_message = self._turn_budget_control_message(...)
if runtime_control_message is not None:
    conversation_history.append(runtime_control_message)
```

`runtime_control_message` 只属于当前 `PromptWindowRequest.conversation_history`，不写回持久会话状态 `AgentRunSession.messages`。

典型内容：

```text
user
assistant(tool_calls)
tool(result)
assistant(tool_calls)
tool(result)
user(steer)
...
```

所以：

```text
Conversation History
≠ WorkingMemory
≠ Current Turn System Context
```

Observation 可以被同时投影到：

```text
session.observations
WorkingMemory
Message(role=tool)
Evidence
Trace
```

但这些消费者不等于彼此。

---

# 5. 为什么要把 System Message 和 History 平铺

当前代码：

```python
full_llm_messages = [
    request.turn_system_message,
    *request.conversation_history,
]
```

`*request.conversation_history` 是 Python list unpacking。

例如：

```text
turn_system_message = S
conversation_history = [M1, M2, M3]
```

结果：

```text
[S, M1, M2, M3]
```

原因不是“把不同信息当成同一种信息”，而是 Provider chat protocol 最终接收的就是一个**有序 Message 序列**。

逻辑结构仍然由以下信息保留：

```text
role
message order
section labels
ToolCall / tool_call_id linkage
```

---

# 6. 一个 System Message + 很多 History，会不会被 History 淹没

有风险，但不能按 Message 数量理解。

错误模型：

```text
1 个 system Message
vs
20 个 history Message
→ system 只有 1/21 注意力
```

LLM 不是这样工作。

真正相关的是：

```text
token 数量
system/user/tool role
position
内容相关性
长上下文退化
```

Current Turn System Context 即使只有一个 Message，也可能包含数千字符；system role 还承担高优先级指令语义。

但长 History 确实会带来：

```text
signal dilution
lost-in-the-middle
旧决策与当前状态冲突
重复 Observation 噪声
```

因此这是 Context Engineering 的真实问题。

---

# 7. 当前实现如何降低注意力稀释

```text
① Current Turn System Context 每 Turn 重建
   当前 Repo / WorkingMemory / Skill / Permission 都是最新值

② system role 保持运行规则和当前事实的协议层级

③ attention_sink
   把当前最需要关注的事实显式放进 system context

④ Current Turn System Context 自己有字符预算

⑤ PromptWindowManager 对完整 request 做 token 预算

⑥ 旧 Conversation 超限后压成 ConversationHistoryDigest

⑦ recent raw tail 保留最近协议细节
```

所以当前策略不是：

```text
无限 raw history + 一个固定 prompt
```

---

# 8. 当前仍然存在的边界

当前 compaction 主要在：

```text
soft token limit exceeded
```

时触发。

因此：

```text
History 没超 token 阈值
但语义已经很吵
```

这种情况不会因为“语义污染”自动压缩。

这是当前版本明确可演进的点。

更成熟方案可以是：

```text
incremental rolling compaction
phase-local context
salience / relevance-aware history retention
bounded typed task state
artifact references
semantic progress / stale-history pruning
```

但不需要把这些全部塞进当前稳定版本。

---

# 9. 对话历史摘要（ConversationHistoryDigest）

当前：

```text
old session.messages segments
+ aligned observations
↓
ConversationHistoryDigest
```

然后：

```text
ConversationHistoryDigest
├── render()  → role=system Message → llm_messages
├── object    → PreparedTurn
└── to_dict() → TaskCheckpoint
```

正常下一 Turn 不从 Checkpoint digest 增量计算；仍然从当前 `session.messages` 重新构建 Conversation Window。

---

# 10. Tool Schemas 为什么单独存在

`tool_schemas` 不属于 `session.messages`，但同样消耗 Provider input tokens。

所以 Prompt Budget 实际治理：

```text
TurnSystemContextBuildReport.render()
+
PromptWindowRequest.conversation_history
+
PromptWindowRequest.tool_schemas
```

Tool Schema 的主要优化方式是：

```text
ToolRegistry
↓
ToolRouter
↓
只暴露当前 Turn 需要的 Tool contracts
```
