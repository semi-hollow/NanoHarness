# 上下文工程

> 本文回答当前一个 Model Turn 的 System Context 如何构成、跨 Run Memory 如何进入
> Context/Tool contract，以及它们如何与 Conversation History、Tool Schemas 汇合。
> 历史压缩算法见 [上下文压缩与长任务设计](上下文压缩与长任务设计.md)。

# 1. 系统角色

`TurnSystemContextBuildReport` 是当前 Turn 稳定事实的有界读模型。它解决三个问题：

1. 从仓库、指令、WorkingMemory、长期召回和 Skill 中选择什么；
2. 如何在 `max_chars` 内按稳定区段分配预算；
3. 如何把选择、截断和治理事实同时提供给模型与 Trace。

它不包含 Conversation History，也不决定 Tool 是否授权执行。

# 2. 当前 Turn 的输入构造

```text
AgentRunSession
    ↓
TurnPreparation.prepare_turn()
    ├── ToolRouter.route()
    │      └── visible tool_schemas + allowed_tool_names
    ├── _management_candidates_for_turn()
    │      └── latest human message → bounded mutation targets
    ├── _attach_memory_management_candidates()
    │      └── only augments remember_memory schema
    │
    ├── RepositoryTurnSystemContextAssembler.build()
    │      └── TurnSystemContextBuildReport
    │              ↓ render()
    │         turn_system_message
    │
    └── conversation_history = list(session.messages)
             ↓
       PromptWindowRequest.conversation_history
             ↓
       PromptWindowManager.prepare()
             ↓
       PromptWindowResult.llm_messages
             ↓
       PreparedTurn.llm_messages
             ↓
       ModelPort.chat(...)
```

最终模型边界有两个独立入参：

```python
ModelPort.chat(
    PreparedTurn.llm_messages,
    PreparedTurn.tool_schemas,
)
```

Tool Schemas 不是 System Message 的替代品；它们是同一次调用的结构化能力契约。

# 3. System Context 所有权

```text
TurnPreparation
    │ owns request timing and final PreparedTurn
    ▼
TurnSystemContextAssemblerPort
    │ isolates repository/filesystem IO
    ▼
RepositoryTurnSystemContextAssembler
    ├── build_repo_map()
    └── build_turn_system_context()
            ▼
TurnSystemContextBuildReport
            ▼
turn_system_message = Message(role="system", ...)
```

`TurnPreparation` 不自己扫描仓库；Adapter 不读取 Session history，也不调用模型。

# 4. System Context 的四类信息

| 类别 | 当前真实内容 | 作用 |
|---|---|---|
| System / Policy | system prompt、permission summary、attention sink | 固定 Runtime 角色与治理边界 |
| Project Knowledge | project instructions、repo map、selected previews、retrieved docs | 提供当前仓库事实 |
| Capabilities | active Skill cards、available tool names | 告知当前可用能力 |
| Working State | WorkingMemory summary/items、long-term recall snapshot、context state | 提供当前 Run 的任务状态 |

`task` 参与候选选择，但不会作为一个重复区段再次 render 到 System Context；初始任务已经
存在于 `AgentRunSession.messages`。

# 5. 选择与预算

`build_context_strategy()` 先产生候选：

```text
task + repo files + WorkingMemory
    ↓
selected files / previews
retrieved docs
working-memory views
long-term-memory views
topic relation / attention sink
```

`build_turn_system_context()` 再按稳定 section order 与权重分配字符预算。被截断的
section、实际字符数和 dropped reason 进入 `TurnSystemContextBuildReport`，因此
“模型看到了什么”可以由 Trace 解释，而不是靠猜测。

# 6. Long-Term Memory 的两种查询生命周期

长期记忆向模型提供两个用途不同的有界视图，但它们的冻结周期不同：

```text
LongTermMemoryService
├── recall(namespace, query=session.task, max_chars)
│      ↓ exact-key PROJECT override
│      ↓ lexical relevance DESC
│      ↓ PROJECT scope tie-breaker
│      ↓ updated_at DESC + budget
│      ↓
│   Recall Snapshot
│      ↓
│   WorkingMemory.seed_long_term()
│      ↓
│   TurnSystemContextBuildReport.long_term_memory
│
└── management_candidates(namespace, query=latest_human_message, max_chars)
       ↓ lexical relevance + scope tie-break + recency + budget
       ↓
    AgentRunSession.memory_management_candidates
       ↓
    remember_memory Tool schema only
```

`Recall Snapshot` 是当前任务的 reasoning evidence；0 lexical relevance 的 global
preference 不会被硬过滤，并在 `RunPreparation` 中生成后冻结整个 Run。

`Management Candidates` 在每个 `TurnPreparation.prepare_turn()` 中根据最新
human-authority `role=user` Message 重新查询，只让模型看到稳定
`memory_id / scope / key / compact content`。它在当前 Turn 的模型请求和后续 target
validation 之间冻结，不进入 WorkingMemory，也不能冒充当前任务事实。使用
`role=user` 传输的 `RUNTIME COORDINATION EVIDENCE` 明确带有
`human_authority=false`，既不能作为 candidates query，也不能授权 Memory 写入。

因此当前 Run 中新写入的记录不会改变冻结的 reasoning snapshot；下一 Turn 的管理查询
可以看到它，下一次 Run 的 task-aware recall 才能把它作为 reasoning evidence 注入。

# 7. 显式 Memory 写入

没有第二个 Memory Agent 或隐藏模型调用。执行 consolidation 的就是当前 AgentLoop 的
同一次模型响应：

```text
current AgentLoop LLM
sees remember_memory schema + current-Turn Management Candidates
    ↓
one or more remember_memory ToolCalls
├── action = CREATE | UPDATE | NOOP
├── target_memory_id
├── key / normalized content / scope
└── source_quote
    ↓
ToolExecutionPipeline
├── exact quote exists in current-session human-authority role=user Message?
├── action / content / scope valid?
└── UPDATE/NOOP target belongs to current-Turn candidates and same scope?
    ↓
LongTermMemoryService.apply_consolidation()
    ↓
JsonLongTermMemoryRepository
```

Authority 边界是：

```text
Model proposes action / target / normalized content
Runtime owns memory_id / revision / timestamps / provenance / persistence
```

同一模型响应中的多条 `remember_memory` 按原顺序独立校验、执行和回填 Observation，
不消耗普通 read/edit/test ToolCall budget；`ask_human` 出现时仍是当前 Turn 的独占屏障，
所有 Memory 调用等待模型取得回答后重新规划。

`memory_id` 是权威 record identity。`key` 仍作为人可读 topic 和 exact-key
PROJECT-over-USER override label，但 UPDATE/NOOP 不能靠 key 定位；它们必须显式绑定
candidates 中的 `target_memory_id`。`source_quotes` 持久化产生记录版本的精确 user evidence。
`forget` 仍是 management API，不暴露新的 Model Tool。

# 8. Conversation History 的相邻边界

当前进程 Conversation History 的 Owner 是：

```text
AgentRunSession.messages
```

每个 Turn 创建副本：

```python
conversation_history = list(session.messages)
```

必要时将本 Turn 的预算控制 Message 作为 `PromptWindowRequest.transient_messages` 单独
传入。它不写回 Session，也不进入 digest 或 compaction cursor。

因此两个边界保持独立：

```text
Turn System Context
= current stable repository/policy/capability/working facts

Conversation History
= ordered user/assistant/tool interaction
```

# 9. 设计边界

- System Context 每 Turn 重建，不是跨 Turn mutable cache；
- WorkingMemory 是当前 Run 的状态视图，不是完整 Conversation；
- 长期记忆 reasoning snapshot 在 Run 开始时召回并固定，运行中写入不会悄然改变它；
- Management Candidates 每 Turn 做一次有界 deterministic scan，但不进入 reasoning；
- 两种查询都不使用 embedding、Vector DB 或额外模型调用；
- ToolRouter 决定本 Turn 可见 schema，Authorization 决定具体调用是否可执行；
- 字符预算是 Context section 边界，完整模型请求的 token 预算由 Prompt Window 管理。

## 源码入口（Source Anchors）

- `agent_forge/runtime/application/turn_preparation.py::TurnPreparation.prepare_turn()`：Context、History 与 Tool schema 汇合。
- `agent_forge/runtime/adapters/context_assembler.py::RepositoryTurnSystemContextAssembler.build()`：仓库型 Adapter。
- `agent_forge/context/application/context_builder.py::TurnSystemContextBuildReport`：System Context 读模型。
- `agent_forge/context/application/compaction.py::PromptWindowManager.prepare()`：Conversation Window 相邻 Owner。
- `agent_forge/runtime/application/run_preparation.py::RunPreparation._initialize_memory_context()`：Run-level Recall Snapshot 入口。
- `agent_forge/runtime/application/turn_preparation.py::TurnPreparation._management_candidates_for_turn()`：Turn-level 管理候选入口。
- `agent_forge/memory/application/service.py::LongTermMemoryService`：recall、candidates 与 ID-based consolidation。
- `agent_forge/tools/builtins/remember_memory.py::RememberMemoryTool`：模型可见 typed proposal。
- `agent_forge/runtime/application/tool_execution.py::ToolExecutionPipeline._execute_call()`：provenance 与 target validation。
