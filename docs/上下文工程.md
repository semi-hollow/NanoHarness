# 上下文工程

> 这份文档不是“Prompt 里有哪些字段”的清单，而是解释：
> **一个 Turn 的有限 Context Budget，如何在不同信息源之间分配。**

---

# 1. 业务分层先于代码变量

```text
                         LLM Context Budget
                                │
          ┌─────────────────────┼─────────────────────┐
          │                     │                     │
     Runtime State          Knowledge            Capability
          │                     │                     │
     Conversation           Repo Context          Skills
     Working State          External Evidence     Tool Schemas
     Task State             Long-term Memory      Permissions
```

关键结论：

> 不同 Context Source 不应该统一用一种 summary 策略。

---

# 2. 不同 Source 怎么治理

| Source | 典型增长方式 | 正确治理 |
|---|---|---|
| Conversation | Turn 越多越长 | protocol-aware compaction |
| Working State | 状态不断变化 | bounded structured state |
| Repo Context | 仓库很大 | selective retrieval |
| Long-term Memory | 跨 Run 累积 | relevance recall |
| Skill | 指令很多 | progressive disclosure |
| Tool Schema | Tool 越来越多 | routing / selection |
| Permission | Policy 变化少 | deterministic authoritative projection |

---

# 3. 当前 Turn 的真实构造链

```text
AgentRunSession
    │
    ├── messages
    ├── observations
    ├── WorkingMemory
    └── active Skills
    │
    │ + current workspace/repo
    │ + ToolRoute
    │ + Permission
    ▼
TurnPreparation
    │
    ├── Current Turn System Context
    ├── Conversation Window
    └── Tool Schemas
    ▼
PreparedTurn
    ▼
LLM.chat(llm_messages, tool_schemas)
```

`PreparedTurn` 是当前 Turn 的冻结输入快照，不是 durable state。

---

# 4. 当前 Turn 系统上下文 / Current Turn System Context

它最终是一条：

```text
role=system
```

的 Message。

逻辑上：

```text
Current Turn System Context
├── base runtime instructions
├── permissions
├── active Skill
├── long-term memory snapshot
├── current repo map / selected files
├── retrieved evidence
└── WorkingMemory projection
```

过去 Turn 的 system context 不 append 到 `session.messages`。

下一 Turn 根据当前事实重新生成。

---

# 5. 对话历史 / Conversation History

`session.messages` 是 chronological protocol history：

```text
user
assistant(tool_calls)
tool(result)
assistant(tool_calls)
tool(result)
user(steer)
...
```

ToolCall ID 只负责：

```text
assistant ToolCall
↕
tool Observation message
```

之间的协议关联。

---

# 6. 工作记忆 / WorkingMemory

```text
WorkingMemory
├── recent items
├── recent observations
├── summaries
├── run-local KV
└── long-term memory snapshot
```

它是：

> 当前 Run 的 bounded materialized view。

它不是：

```text
Conversation History
Checkpoint
Long-term Memory Store
整个 Session
```

Observation 执行后会被投影到多个消费者：

```text
Observation
├→ session.observations      typed runtime facts
├→ WorkingMemory             recent task-state view
├→ Message(role=tool)        provider protocol
├→ EvidenceLedger            final grounding
└→ Trace                     audit evidence
```

---

# 7. Tool Schema 为什么单独算 Context Budget

Tool schema 不在 `session.messages` 中，但同样占 Provider input tokens。

所以 Prompt Window Budget 必须按：

```text
Current Turn System Context
+
Conversation Window
+
Tool Schemas
```

整体估算。

优化 Tool Schema 的方式不是 summary，而是：

```text
ToolRegistry
↓
ToolRouter
↓
只暴露本 Turn 真正可能需要的 schema
```

# 8. 对话压缩 / Conversation Compaction

当前实现：

```text
完整 History
↓
超过 soft limit
↓
按 protocol transaction 分段
↓
旧 segments → ConversationHistoryDigest
recent segments → 保留 raw
↓
System + Digest + Recent → LLM
```

必须保持：

```text
assistant ToolCall
+
matching tool Observation
```

不可拆。

否则模型下一 Turn 会看到“调用过 Tool”但看不到真实结果。

详细 trade-off 见：

`上下文压缩与长任务设计.md`

---

# 9. Skill 和 Permission 为什么不是 WorkingMemory

三者职责不同：

```text
WorkingMemory
= 当前 Run 知道什么

Skill
= 当前 Run 应该怎么做

Permission
= Runtime 允许做什么
```

尤其 Permission 属于 Runtime authority，不能降级成模型可自行改写的 Memory。

---

# 10. 当前方案的主要成熟化方向

当前可审计版本已经有：

```text
bounded WorkingMemory
protocol-aware Conversation compaction
Tool schema routing
Skill progressive disclosure v1
long-term memory recall
```

进一步生产化：

```text
Conversation incremental rolling compaction
Repo map/index incremental caching
turn-level Skill reference disclosure
deadline-aware retrieval/model/tool budget
```

这些是 Context Engineering 的演进，不应该和当前 Multi-Agent V1 混成一次大改。
