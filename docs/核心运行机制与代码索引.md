# 核心运行机制与代码索引

本文汇总 NanoHarness 的核心运行规则和对应代码入口。每一行说明：什么时候触发、系统实际做什么、
失败或中断时怎样处理、由哪段代码负责。在 PyCharm 中点击“负责代码 / 运行证据”会打开本地源码文件；
旁边的 `L数字` 是精确行号，可按 `⌘L` 输入该数字到达定义。行号由测试校验。

已知能力名称、只需定位首个代码 Owner 时，使用[核心能力与代码入口](核心能力与代码入口.md)。
需要先建立整体认识时，从[系统概览与核心设计](系统概览与核心设计.md)开始。本文同时承担生命周期、异常处理和机制边界说明，
不再维护平行架构长文。需要核对 JSON、Diff 和恢复状态的存放位置、写入时机与权威边界时，
转到[运行产物与持久化契约](运行产物与持久化契约.md)。

## Model Input 与消息生命周期

| 边界 | 当前契约 | 关键异常与证据 |
| --- | --- | --- |
| 完整请求 | `Runtime Context + Conversation History + Tool Schemas`；前两者是 messages，Schemas 是并列输入 | 信息来源不等于 role；Tool Schemas 不伪装成 system message |
| 消息角色 | 每轮重建 Runtime Context `system`；初始 Task/运行前澄清为首条 `user`；Steer 为后续 `user`；Assistant ToolCall 与 `tool` Observation 成对 | `ask_human` 回答是 `tool`；Approval 只写 Store；remember 只写 Memory/Ledger |
| 历史压缩 | 先按 Assistant/Tool 事务分段，用 `SessionDigest(task, task_updates, tool_transactions, failed_tool_evidence, source_hash, estimated_tokens_before/after)` 替换旧段，保留最近原文 | Digest 在 wire 上是额外 `system`，语义上仍是 History 投影；原 session/trace 不删除 |
| 溢出恢复 | 完整请求接近软上限时主动压缩；Provider 明确报 overflow 时只有强制压缩确实降低 token 估算才重试一次 | `context_window` 记录覆盖数、压缩前后估算和 reason；无法安全变小就不盲重试 |

## ToolCall 的四层处理

| 层 | 只回答一个问题 | 代码执行顺序 | 输出 |
| --- | --- | --- | --- |
| ① 入口控制 | 这是不是本轮合法的 ToolCall？ | [`ToolRouter.route`](../agent_forge/tools/tool_router.py) · `L188` 决定可见工具 → [`ToolCallNormalizer.normalize`](../agent_forge/models/tool_call_normalizer.py) · `L29` 统一成 Runtime 使用的 ToolCall 格式 → [`ToolExecutionPipeline._execute_call`](../agent_forge/runtime/application/tool_execution.py) · `L182` 确认工具已注册且属于本轮允许集合 | 接收 ToolCall；不合法时向模型返回失败 Observation |
| ② 执行决策 | 这项操作现在应不应该执行？ | [`OperationTracker.resolve_existing_operation`](../agent_forge/runtime/application/operation_tracker.py) · `L124` 查操作状态 → [`HookManager.before_tool`](../agent_forge/runtime/hooks.py) · `L235` 汇总具体规则 → [`ToolAuthorizationGate.authorize`](../agent_forge/runtime/application/tool_authorization.py) · `L59` 结合 Approval 记录与 fingerprint，决定继续、拒绝或等待 | 进入执行、拒绝、等待人工、向模型返回上次结果，或停止自动恢复 |
| ③ 受限执行 | 获得许可后，执行是否始终限制在允许范围内？ | ① [`ToolRegistry.execute`](../agent_forge/tools/registry.py) · `L41` 校验参数并调用 Tool<br>② 命令、路径和进程仍受 [`check_command`](../agent_forge/safety/command_policy.py) · `L32`、[`WorkspaceSandbox`](../agent_forge/safety/sandbox.py) · `L4`、[`ExecutionEnvironment`](../agent_forge/runtime/execution_environment.py) · `L75` 约束 | Tool Observation；越界时返回拒绝原因 |
| ④ 结果与恢复 | 发生了什么，中断后从哪里继续？ | [`HookManager.after_tool`](../agent_forge/runtime/hooks.py) · `L285` 处理并脱敏 → [`OperationTracker.record_execution_result`](../agent_forge/runtime/application/operation_tracker.py) · `L340` 提交 executed/failed → [`RunLifecycle.update_checkpoint`](../agent_forge/runtime/application/run_lifecycle.py) · `L71` 保存恢复点 | 脱敏后的 Observation + 操作状态 + Trace + Checkpoint |

四层依次回答：**调用是否合法 → 当前是否允许执行 → 执行是否始终限制在允许范围内 → 结果是否已记录且可恢复**。Approval 只参与第二层，不能绕过第一层或第三层。

## ToolCall 端到端链路

下面以模型提出 `replace_text(path, old, new)` 为例。它不是七八个彼此独立的“检查函数”，而是一条由不同 Owner 依次负责的控制链：

```text
TurnPreparation 冻结本轮可见 Tool
  -> Model 返回一个或多个 ToolCall
  -> execute_calls 按单轮预算截取，并逐项顺序处理
  -> _execute_call 复核可见性、注册状态和连续重复调用
  -> OperationTracker 将原始 ToolCall 归一化为 OperationIntent
       action=write + operation key + 执行前 fingerprint
  -> 先查询 Operation Ledger，复用确定结果或阻断未知结果
  -> before_tool Hook 汇总环境与权限规则
  -> AuthorizationGate 返回 ALLOW / DENY / ASK
       ASK：写 Approval + Ledger(pending) + Checkpoint(WAITING_APPROVAL)，停止当前 Run
       DENY：写失败 Observation，不进入真实执行
       ALLOW：进入 ToolGateway 前最后一个 pause/cancel 安全点
  -> Ledger(executing) -> ToolRegistry 参数校验 -> ToolGateway 真实执行
  -> CommandPolicy / WorkspaceSandbox / ExecutionEnvironment 约束执行边界
  -> after_tool Hook 规范化并脱敏 Observation
  -> Ledger(executed/failed + 执行后 fingerprint)
  -> Working Memory + Evidence + Trace + Checkpoint
  -> 下一 Turn 的模型读取 Tool Observation
```

批准后不会直接执行旧 ToolCall。Continuation 重新进入 AgentLoop；只有模型再次提出相同操作、`operation key` 相同且目标 `fingerprint` 未漂移，历史批准才可复用。这样人工批准的是“这份目标状态上的这项操作”，不是永久放开某个工具。

### Tool 执行核心不变量

1. **模型只提出意图，Gate 只作决定，只有 ToolGateway 真实执行。** Hook、Approval、Trace 和 Checkpoint 都不会调用 Tool。
2. **获得批准不等于解除边界。** 参数 Schema、CommandPolicy、WorkspaceSandbox 和 ExecutionEnvironment 始终生效。
3. **可能改变持久状态的操作先写 `executing`，返回后再写 `executed/failed`。** 崩溃后停在 `executing` 表示结果未知，必须停止自动重放。
4. **只有 `executed` 且执行后 fingerprint 仍匹配，才能回填上次 Observation。** 目标漂移或结果未知都不能猜测成功。
5. **恢复依据来自 Ledger 和 Checkpoint，审计依据来自 Trace。** Trace 记录事实，但不是权限或恢复状态的权威来源。

### Tool 治理对象对照

| 对象 | 它回答的问题 | 生命周期与权威来源 |
| --- | --- | --- |
| ToolCall | 模型现在建议调用什么、参数是什么？ | 单次模型响应中的原始意图；不是执行事实 |
| OperationIntent | Runtime 将这项调用解释成什么动作？ | 每次执行前构造；统一 action、target、key 和 fingerprint |
| operation key | 恢复后提出的是否仍是同一工具、参数、workspace 和 action？ | 同一意图使用同一稳定 key |
| fingerprint | 这项操作针对的文件或命令目标是否仍是批准或执行时的状态？ | 执行前、批准时和执行后分别计算并比较 |
| Approval | 人是否授权了这个 operation key 在当时 fingerprint 上执行？ | 每项待审批操作一个记录，状态变化覆盖同一文件 |
| Operation Ledger | 这项持久状态变更进行到 planned、pending、approved、executing、executed 还是 failed？ | 每个 operation key 一个状态记录，并保留迁移 history |
| Observation | Tool 最终向模型反馈了什么结果？ | 真实执行、拒绝、跳过或历史结果回填后产生 |
| Checkpoint | 整个 Run 应从哪个可见状态继续？ | Run/Turn/Tool/HITL 边界保存任务级恢复快照 |
| Trace | 全链路实际发生过什么？ | 只追加事件，用于审计、诊断和 Workbench 投影 |

### 关键异常分支

| 触发条件 | 系统行为 | 为什么 |
| --- | --- | --- |
| Tool 未注册或本轮不可见 | 返回失败 Observation，不执行 | 模型输出不能扩大本轮能力面 |
| before_tool 返回 DENY | 记录拒绝和恢复建议，不执行 | 确定性规则高于模型意图 |
| before_tool 返回 ASK | 持久化审批、操作状态和等待 Checkpoint，停止当前 Run | 先保存事实，进程退出后仍能继续 |
| 批准后 fingerprint 漂移 | 旧批准标记 stale，要求重新申请 | 防止检查后到执行前目标被替换 |
| 旧 Ledger 为 executing | 以 `operation_outcome_unknown` 阻断 | 外部状态可能已变化，自动重试可能重复副作用 |
| 旧 Ledger 为 executed 且 fingerprint 匹配 | 不执行 Tool，回填历史 Observation | 复用确定事实，避免重复写入 |
| 第三次连续相同只读调用 | 跳过并要求改变工具或参数 | 保留 Run，但阻止无信息增益的循环 |
| 第三次连续相同状态变更调用 | 阻断 Run | 操作状态表又没有确定结果时不能冒险重试 |
| 任意三个 Tool Observation 连续失败 | 熔断 Run；一次成功即清零 | 限制无效恢复消耗，但不把测试断言失败误计为工具故障 |

### Pause / Cancel 的三个到达时机

| 信号何时到达 | 当前行为 | 设计原因 |
| --- | --- | --- |
| ① 模型或 Tool 尚未启动 | 处理信号，不启动下一项调用 | 此时没有正在执行的外部操作，可以直接停止 |
| ② 模型 Provider 的 HTTP API 请求已发出 | 等请求返回并记录 Usage/Trace；旧响应不再用于生成最终答案或触发 Tool，随后暂停或取消 | 中断客户端连接不能证明 Provider 未执行或未计费 |
| ③ ToolGateway 命令已在进行 | 等命令返回，保存脱敏后的 Observation、操作状态和 Checkpoint，然后停止 | 避免部分写入、残留子进程，以及操作长期停在结果未知的 `executing` |

## 按需启用的能力

## 职责不同、不能互相替代的概念

- 重复 ToolCall 判断模型是否原地打转；连续工具失败保护限制连续失败次数；操作状态表记录持久状态变更是否已执行。
- Hook 提供生命周期时机，具体处理器给出允许、拒绝或询问人工的判断，Gate 决定继续、拒绝或等待，Trace 记录事件，Checkpoint 保存恢复状态。
- operation key 判断是不是同一操作；fingerprint 判断目标是否变化；操作状态表记录执行进度。
- Batch 决定哪些 Task 可同时运行，Patch 表示 Worker 产生的候选改动，Coordinator 负责合并，Finalizer 只读验收。
