# 工具治理与执行

> 核心问题：
> **模型返回一个 ToolCall 后，怎样才能安全、可恢复地变成真实执行？**

---

# 1. 一张主链图

```text
MODEL SIDE

ToolRegistry
↓
ToolRouter
├── tool_schemas        → 给模型看
└── allowed_tool_names  → Runtime 自己留
        │
        ▼
      LLM
        │
        ▼
    ToolCall


RUNTIME SIDE

ToolCall
↓
route recheck
↓
OperationIntent
↓
existing Operation Ledger
↓
Authorization
├── ALLOW
├── DENY
└── ASK → Approval
↓
record executing
↓
ToolGateway / ToolRegistry
↓
Tool.execute
↓
Observation
↓
record executed / failed
↓
Session / WorkingMemory / Trace / Checkpoint
```

一句话：

```text
Model proposes
Runtime decides
Tool executes
```

---

# 2. Tool Schema 和 Permission 不是一回事

```text
Tool Schema
= 告诉模型“这个 Tool 怎么调用”

allowed_tool_names
= Runtime 本 Turn 的执行白名单

Authorization
= 针对具体 ToolCall / OperationIntent 判断能否执行
```

即使模型 hallucinate 一个没展示的 Tool：

```text
执行阶段仍会拒绝
```

所以 Tool visibility 不是安全边界本身。

---

# 3. ToolCall 为什么还要变成 OperationIntent

`ToolCall` 是模型协议对象：

```text
ToolCall
├ id
├ name
└ arguments
```

Runtime 真正治理的是：

```text
OperationIntent
├ action
├ command
├ side_effect
├ target
├ operation_key
└ pre_execution_fingerprint
```

关键：

```text
operation_key
= 逻辑操作身份

fingerprint
= 当前目标状态/版本
```

两者不能混。

---

# 4. Approval 和 Operation Ledger 的区别

```text
Approval
= 允许不允许执行

Operation Ledger
= 这个副作用已经执行到哪
```

典型副作用顺序：

```text
planned
↓
approved
↓
executing          ← 必须先 durable
↓
real side effect
↓
executed / failed
```

---

# 5. Crash 为什么不能直接 retry

假设：

```text
record executing
↓
真正 HTTP / file / command side effect
↓
进程 crash
```

恢复后：

```text
Ledger = executing
```

只能知道：

> 已经越过副作用边界，但不知道真实结果。

所以：

```text
executing
→ outcome unknown
→ fail closed
→ no blind replay
```

这不是“exactly once”，而是：

> 不允许因为恢复逻辑把一个可能已经发生的副作用再执行一遍。

---

# 6. executed 为什么也不一定直接复用

```text
existing = executed
```

还要比较目标状态：

```text
current fingerprint
vs
previous post fingerprint
```

如果匹配：

```text
复用已执行事实
```

如果 drift：

```text
stale
→ 重新读取
→ 重新规划
```

---

# 7. Tool 执行仍然有多层安全

```text
Tool Authorization
↓
ToolGateway / ToolRegistry
↓
Tool implementation
├── argument validation
├── Workspace path safety
├── CommandPolicy
└── ExecutionEnvironment
```

这叫 defense-in-depth。

不能因为前面 Authorization 通过，就把后面的路径/命令检查删掉。

---

# 8. Observation 是执行事实，不是模型自报

```text
Observation
├ tool_name
├ success
├ execution_succeeded
└ content
```

同一个 Observation 会投影到：

```text
session.observations
WorkingMemory
Message(role=tool)
EvidenceLedger
Trace
Checkpoint(last_observation)
```

这是不同消费者的 projection，不是多套 truth。

---

# 9. ask_human、Approval、Pause 要分开

```text
ask_human
= 模型缺业务信息
→ HumanInput
→ WAITING_HUMAN

Approval
= 模型知道要做什么，但 Runtime 需要授权
→ ApprovalRepository
→ WAITING_APPROVAL

Pause
= Operator 主动要求 Run 在安全边界停下
→ PAUSED
```

三条控制链不能混。

---

# 10. Recovery Failure Taxonomy 的作用

Tool 失败后不是 Runtime 自动“再跑一次”。

Runtime 先把 Observation 分类成：

```text
FailureKind
+
retryable
+
recovery_hint
```

写入 Trace。

下一 Turn 模型看到的是：

```text
真实 Observation
+
明确 recovery signal
```

真正是否换策略，由后续 Agent Turn 决定。
