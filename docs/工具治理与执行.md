# 工具治理与执行

<a id="overview"></a>

> NanoHarness 将模型提出的 ToolCall 转换为受路由、授权、幂等、沙箱与恢复约束的真实执行。本文先给出完整主链；后半部分仅用于具体状态机、字段和异常路径的按需下钻。

## 1. 总览 / Overview

```text
MODEL PREPARATION
ToolRegistry → ToolRouter ─┬→ schemas → Model
                           └→ allowed_names → execution recheck
Model raw response → ToolCall normalization → AgentResponse.tool_calls

RUNTIME EXECUTION
ordinary ToolCall → route recheck → OperationIntent → existing Ledger [side effect]
→ Authorization / Approval → Ledger: executing           [side effect]
→ ToolGateway / ToolRegistry → Tool.execute() → Observation
→ Ledger: executed / failed + Runtime projections         [side effect]
```

### 核心关系

```text
Model proposes | Runtime decides | ToolGateway executes
Approval = 能不能执行 | Operation Ledger = 已经执行到哪
operation_key = 逻辑操作身份 | fingerprint = 当前目标版本
executing after crash = outcome uncertain ≠ safe replay
```

# 详细设计 / Detailed Design

> 以下部分用于确认真实字段、状态机和特殊时序；主链已经完整包含在 Overview。

<a id="routing"></a>

## 2. 工具路由与可见性 / Tool Routing

[↑ 返回 Overview](#overview)

`ToolRouter` 的主要选择发生在模型调用之前。

同一次 route 产生两个投影：

```text
ToolRouter
├── schemas
│   → 发给模型
│   → 告诉模型本 Turn 有哪些 Tool、怎么调用
│
└── allowed_names
    → Runtime 自己保留
    → ToolCall 返回后再次强制复核
```

```text
schemas
= Model Capability View

allowed_names
= Runtime Enforcement View
```

模型输出不能被当成可信输入；即使某 Tool 没出现在 schema 中，模型仍可能 hallucinate 一个 ToolCall，所以执行阶段仍验证：

```text
Tool 已注册
+
Tool name ∈ allowed_names
```

<a id="schema"></a>

## 3. 工具契约 / Tool Schema 与 Provider Wire Contract

[↑ 返回 Overview](#overview)

NanoHarness 内部 canonical Tool Schema：

```text
ToolSchema
├── name
├── description
├── arguments
└── required
```

到 OpenAI-compatible Provider Adapter 才转换成类似：

```json
{
  "type": "function",
  "function": {
    "name": "read_file",
    "description": "...",
    "parameters": {
      "type": "object",
      "properties": {
        "path": {"type": "string"},
        "offset": {...},
        "limit": {...}
      },
      "required": ["path"]
    }
  }
}
```

对应关系：

```text
type=function
→ 可调用函数工具

parameters.type=object
→ Tool 参数整体是 JSON object

properties
→ object 允许的字段及类型

required
→ 必填字段
```

Runtime 内部保持 Provider-neutral；Adapter 才负责具体 wire schema。

<a id="normalization"></a>

## 4. 工具调用归一化 / ToolCall Normalization

[↑ 返回 Overview](#overview)

Normalization 发生在真实 Tool 执行之前，不处理 Observation。

```text
Provider Raw Response
↓
Provider Adapter / ToolCallNormalizer
↓
NanoHarness ToolCall domain object
↓
AgentResponse
```

它把 native tool calls、legacy function call、JSON encoded arguments 等差异收敛为：

```text
ToolCall
├── id
├── name
└── arguments: dict
```

真正 required/basic type validation 位于放行后的 ToolRegistry execution boundary。

<a id="operation-intent"></a>

## 5. 操作意图 / OperationIntent

[↑ 返回 Overview](#overview)

`ToolCall` 是模型语言；`OperationIntent` 是 Runtime 治理语言。

```text
OperationIntent
├── action
├── command
├── side_effect
├── target
│   ├── tool_name
│   ├── arguments
│   ├── action
│   └── workspace
├── operation_key
└── pre_execution_fingerprint
```

```text
action
→ read / write / validate / run_command / memory_write

command
→ run_command 时的具体命令

side_effect
→ 是否需要 durable operation governance

target
→ 这次操作针对什么

operation_key
→ logical operation identity

pre_execution_fingerprint
→ 执行前目标版本
```

当前 `run_command` 保守地视为 side effect。

<a id="ledger"></a>

## 6. 操作状态表与幂等 / Operation Ledger

[↑ 返回 Overview](#overview)

SHA-256 只提供 deterministic identity；真正幂等来自：

```text
Stable key
+
Durable state lookup
+
Runtime no-repeat rule
```

side-effect 生命周期：

```text
planned
→ pending / approved
→ executing
→ executed / failed
```

查询既有 Ledger 发生在新的授权/执行之前：

```text
existing = executing
→ 上一次已越过副作用边界，但结果未知
→ fail closed / BLOCKED
→ 不盲目 replay

existing = executed
+ 当前目标仍匹配已知 post-state
→ 不再执行 Tool
→ 复用已执行事实

existing = executed
+ 目标 drift
→ stale
→ 重新读取 / 重新规划
```

crash-safety 顺序：

```text
approved
↓
record executing
↓
ToolGateway.execute()
↓
record executed / failed
```

<a id="authorization"></a>

## 7. 授权与审批 / Authorization / Approval

[↑ 返回 Overview](#overview)

```text
Approval
= 能不能执行

Operation Ledger
= 已经执行到哪
```

AuthorizationGate 产生：

```text
ALLOW
DENY
ASK
```

只有 `ASK` 才进入人工 Approval。

```text
side_effect=True
≠ 一定需要人工审批
```

手工审批路径：

```text
OperationIntent
↓
planned
↓
ApprovalRepository.request()
↓
Ledger pending
↓
WAITING_APPROVAL checkpoint
↓
Run ends
```

操作者批准：

```text
Approval JSON
pending → approved
↓
resume from checkpoint
↓
NEW continuation Run
```

Approval 不是 `ask_human` Tool；它属于 Runtime control plane。

<a id="execution"></a>

## 8. 工具执行边界 / ToolGateway

[↑ 返回 Overview](#overview)

`ToolGateway` 是统一 Tool dispatch / execution boundary，不是 Approval Gateway。

```text
ToolGateway / ToolRegistry
↓
lookup Tool
↓
required/basic type validation
↓
Tool.execute(arguments)
↓
Observation
```

安全控制采用 defense-in-depth：

```text
Authorization / environment precheck
↓
ToolGateway
↓
Tool implementation
├ Workspace / path safety
├ CommandPolicy
└ ExecutionEnvironment
```

```text
Workspace / path safety
→ 文件目标是否逃出允许目录、是否命中敏感路径

CommandPolicy
→ 命令语义是否允许

ExecutionEnvironment
→ 真正在哪个环境执行，以及 cwd/network/container/resource 等系统边界
```

<a id="observation"></a>

## 9. 执行观察与投影 / Observation

[↑ 返回 Overview](#overview)

```text
Observation
├── tool_name
├── success
├── execution_succeeded
└── content
```

执行结果会投影到：

```text
session.observations
WorkingMemory
EvidenceLedger
Trace
Checkpoint
Message(role=tool)
```

这些对象面向不同消费者，不是简单重复存储。

`Message(role=tool)` 只在执行后仍允许继续时追加；若此时命中停止预算，其他运行态与持久化投影已经提交，
但不会再创建下一轮模型协议消息。

<a id="hitl"></a>

## 10. 持久化人工输入 / ask_human

[↑ 返回 Overview](#overview)

先区分：

```text
Pre-run Clarification
= Runtime 在第一次模型调用前发现任务缺关键输入

ask_human
= LLM 在 Run 中主动提出问题

Approval
= LLM 已知道动作，但 Runtime 要授权副作用
```

### Run 中 ask_human 完整时间线

```text
Turn N
LLM
↓
AgentResponse
└── ask_human(question, choices)
↓
_select_calls_for_turn()
↓
ask_human 成为 HITL barrier
只保留 first ask_human
↓
append:
assistant(tool_calls=[ask_human(...)])
↓
_handle_human_question()
↓
RunLifecycle.request_human_input()
↓
HumanInputRepository.request()
↓
canonical(thread_id, kind, question, choices)
↓
SHA-256 → deterministic request_id
↓
human_input/<request_id>.json
status = pending
↓
StopRequest(WAITING_HUMAN)
↓
AgentLoop / finalize_run()
↓
TaskCheckpoint
status = WAITING_HUMAN
metadata.human_input_request_id = xxx
↓
Harness.run() 返回
↓
当前 Run 真正结束
```

关键顺序：

```text
① Human Input JSON 先 durable
② 再产生 WAITING_HUMAN StopRequest
③ 再 finalize Run
④ 再落 WAITING_HUMAN checkpoint
⑤ Harness.run 返回
```

这不是阻塞等待，而是：

> **durable pause + new continuation run。**

`HumanInputRepository` 只拥有问题与回答的持久化，不运行进程内 wait loop。

### 回答与 Resume

```text
HumanInput JSON
pending → responded
↓
BuildContinuationPlan
↓
harness.resume(...)
↓
NEW Run
↓
NEW AgentRunSession
```

TUI 自动通过 `OperatorPrompt.key` 携带 request_id；CLI 只有多个 pending request 时才需要显式 `--request-id`。

### ask_human 与同 Response 其他 ToolCalls

```text
ask_human + A + B + C
↓
只保留 first ask_human
↓
A/B/C 不执行
A/B/C 不进入 assistant tool_calls Message
A/B/C 不进入 checkpoint 等待未来照单执行
↓
Trace 记录 deferred
↓
continuation 重新让模型基于真实回答规划
```

这里的 `deferred` 是把执行责任交给未来 replanning，不是持久化 Tool queue。

<a id="run-control"></a>

## 11. 运行控制与安全边界 / Run Control

[↑ 返回 Overview](#overview)

```text
Pause / Cancel
= terminal cooperative control

Steer
= non-terminal replanning
```

### 继续与重规划 / CONTINUE vs REPLAN

```text
CONTINUE
= 上一轮 AgentResponse 被接受
→ ToolCall / Observation / History 已提交
→ 下一 Turn

REPLAN
= Steer 在模型调用期间到达
→ Steer append 为 role=user
→ 刚返回 AgentResponse 判 stale 并丢弃
→ 不执行其中 ToolCall
→ 下一 Turn
```

### 时机表

| 控制信号到达时机 | Steer | Pause / Cancel |
|---|---|---|
| Model 调用前 | append user，本轮模型直接看到 | 下一安全边界停止 |
| Model 推理中 | Response 返回后丢弃旧 Response → REPLAN | 不强杀模型请求，返回后停止 |
| 单个 Tool A 执行中 | A 不强杀；完成后留队列，下一 model boundary 生效 | A 不强杀；A 完成后停止 |
| 多 Tool A/B/C/D，A 执行中 | 当前实现继续 B/C/D，batch 完成后消费 Steer | A 完成后，B/C/D 不再启动 |
| Tool batch 完成后 | 下一 model boundary 注入 | 下一 safe point 停止 |

当前 Steer 在 Tool boundary 使用 `include_steer=False`，只在 Model Boundary 消费。

### 运行控制器与可重入锁 / RunController / RLock

```text
ONE PYTHON PROCESS

UI Thread
   │ steer / pause / cancel
   ▼
┌────────────────────┐
│ RunController      │
│ _steers            │
│ _terminal          │
│ RLock              │
└────────────────────┘
   ▲
   │ drain / take
Agent Worker Thread
```

不同 Thread 之间仍然互斥；RLock 的额外能力仅是同一 Thread 可重复 acquire 同一把锁。

<a id="memory-authorization"></a>

## 12. 持久化记忆授权 / Durable Memory

[↑ 返回 Overview](#overview)

`remember_memory` 不把“模型想记住”直接等同于“用户已经授权”。

```text
remember_memory(
    content=...,
    source_quote=...
)
↓
Runtime 在当前 session.messages 中寻找：
role=user
且 source_quote 精确包含于用户原文
      │
   ┌──┴──┐
  YES    NO
   │     │
   │     └→ fail closed
   ▼
记录 provenance
├ message_index
├ message_sha256
└ source_quote
   ↓
OperationIntent
↓
Operation Ledger
↓
Memory write
```

授权依据是当前 Session 中可验证的 User Message provenance，而不是模型对自然语言授权语义的推断。

`scope` 默认是 `project`；只有用户原文明确表达全局或跨项目偏好时，模型契约才允许使用 `user`。
Runtime 不增加自然语言授权 classifier、promotion workflow 或第二次 Approval，因此不会宣称自己能绝对理解
这段授权语义。写入成功也不会热更新当前 Run 的长期记忆快照，新值从下一次 Run 起参与召回。
