# NanoHarness 系统概览与核心设计

以下内容围绕一个核心判断展开：**模型负责提出下一步意图，Runtime 负责把意图变成受约束、可恢复、
可验证的工程执行。**

## 系统定位

> NanoHarness 是一个面向真实代码仓库的 Coding Agent Runtime：它在隔离 workspace 中驱动模型检索、
> 编辑和验证代码，并统一管理 Context、Tool、权限、恢复状态、成本与运行证据。

## 适用场景

模型能生成代码，不代表它能稳定完成长周期 repository task。一次真实修复还要处理上下文预算、工具权限、
命令和路径隔离、人工审批、中断恢复、重复副作用以及结果验证。NanoHarness 把这些问题放进确定性 Runtime：
模型只产生 tool intent，Runtime 决定这一轮能看什么、动作能否执行、在哪里执行，并把 Observation、Checkpoint、
Trace、Usage 和候选 Diff 保存为可检查证据。在此基础上，系统还提供 Multi-Agent 编排、SWE-bench 批量评测
和只读 Workbench，用于判断任务是否真正完成，而不是只读取最终回答。

## 功能地图

| 能力域 | 已实现能力 | 解决的问题 |
| --- | --- | --- |
| 任务与 Context | 分层指令、仓库检索、上下文预算、压缩、Skill、Memory | 让模型在有限窗口中看到当前最相关且来源可追踪的信息 |
| 模型接入 | Provider 适配、ToolCall 归一化、有界重试、显式 fallback、Usage | 把不同模型输出收敛为统一协议，并记录真实调用成本和异常 |
| Tool 治理 | 动态可见性、参数校验、Hook、Approval、命令策略、路径沙箱 | 防止模型调用不可见工具、越界路径或未授权副作用 |
| 状态与恢复 | Pause、Cancel、Steer、HITL、Checkpoint、Continuation、Operation Ledger | 把长任务状态移出 Prompt，并避免恢复时重复执行持久操作 |
| 验证与证据 | 本地验证、Candidate Diff、Trace、Usage、Scorecard、Workbench | 区分“产生改动”“本地验证”和“独立评测解决”三个证据等级 |
| Multi-Agent | 依赖编排、独立 worktree、结构化交付物、合并与 Finalizer | 让可拆分任务并行，同时约束修改范围、冲突和最终验收 |
| Benchmark | SWE-bench、固定样本、official evaluator、失败分类 | 用完整 planned 分母衡量真实仓库修复，而不是挑选成功案例 |

## 一次 Run 的生命周期

```text
Run Request
  -> Prepare：workspace / instructions / skill / memory / checkpoint
  -> Turn：context budget / visible tools
  -> Model：final answer 或 tool intent
  -> Gate：route / normalize / policy / approval
  -> Execute：sandbox / command / tool
  -> Observe：result / trace / operation state / checkpoint
  -> Validate：tests / candidate diff
  -> Finalize：terminal state / usage / evidence
```

按顺序只需解释八件事：

1. `Harness.run` 接收任务、仓库和运行配置，并创建隔离 workspace。
2. Run Preparation 合并分层指令，加载本次需要的 Skill、Memory 与恢复摘要。
3. Turn Preparation 按完整请求预算组装 Context，并只暴露当前阶段允许的 Tool。
4. Model 返回最终回答或 ToolCall；Runtime 不把模型输出直接视为可执行命令。
5. ToolCall 依次经过格式归一化、可见性复核、规则判断和人工审批。
6. 获准调用仍在命令策略、路径沙箱和执行环境中运行，执行边界不会因 Approval 消失。
7. Observation、操作状态、Trace 和 Checkpoint 在每轮后更新，为诊断和恢复保留事实。
8. 终止时统一保存候选 Diff、本地验证、Usage、停止原因与最终状态。

`AgentLoop` 用最小分流模型结束每个 Turn，不再让 `None` 同时表示多种语义：

```text
TurnOutcome
├── CONTINUE：Tool 事务已回填，进入下一 Turn
├── REPLAN：Steer 使已返回的模型响应过时，重新规划
└── STOP + StopRequest(status, reason, stop_output, candidate_final_answer?)
```

每个进入 Runtime 统一停止链的 Run 都产生 `stop_output`；只有质量门接受的 `COMPLETED`
候选回答才成为 `final_answer`。恢复状态看 Checkpoint，调用方文本看 `stop_output`，两者不混用。

## 模型输入与 Context 架构

**ONE MODEL CALL = Runtime Context + Conversation History + Tool Schemas。** 这是信息来源层；
`system / user / assistant / tool` 是消息角色协议层。两层不是一对一：Tool Schemas 不是 Message，
SessionDigest 在语义上属于历史投影，但在 wire format 中以额外 `role=system` 发送。

```text
ONE MODEL CALL
├── Runtime Context → role=system（现在世界是什么样）
├── Conversation History（之前发生了什么）
│   ├── user / assistant / tool
│   └── Old History → deterministic SessionDigest
│                      └── wire format: additional role=system
└── Tool Schemas（模型现在能做什么）

Assistant ToolCall ↔ matching Tool Observation
```

```text
SessionDigest
├── task：initial task
├── task_updates：后续 steer / 任务约束变化
├── tool_transactions + failed_tool_evidence
└── covered_message_count + source_hash + 压缩前后 token 估算
```

| 人类输入 | 进入哪里 | 不进入哪里 |
| --- | --- | --- |
| 初始 Task / run-start clarification | 合并为首条 `role=user` | 不重复渲染到 Runtime Context |
| Steer | 下一模型边界追加 `role=user` | 不插入 Assistant/Tool 事务中间 |
| `ask_human` 回答 | 匹配 ToolCall 的 `role=tool` Observation | 不伪装成新 Task |
| Approval 决定 | Approval Store + Checkpoint/Trace | 不自动转成消息或执行旧 ToolCall |
| 显式 remember | Memory Store + Operation Ledger | 不热刷新当前 Run 的 Memory 快照 |

SessionDigest 只替换旧 History 在当前模型窗口中的可见形式；原始 session/trace 仍保留，Assistant ToolCall 与对应 Tool Observation 也必须成对留下。它不是第四种 Context，不是全局任务替代品，也不保存 chain-of-thought。

## 四个核心设计判断

### 1. 模型决策面与执行控制面分离

模型擅长理解任务和提出动作，但权限、预算、路径、命令和状态转换必须由确定性代码判断。因此 Tool 是否可见、
是否获准以及能否真实执行是三个不同阶段，不能只靠 Prompt 约束。

### 2. 长任务状态不能只存在于对话

Pause、HITL 和进程中断都会破坏纯对话状态。NanoHarness 把可恢复状态写入 Checkpoint；恢复时创建新的
Continuation，并保留来源 Run、待处理问题和人工决定。

### 3. 持久操作需要独立的防重复合同

Checkpoint 只说明“流程走到哪里”，不能证明写操作是否已经成功。Operation Ledger 使用 operation key、状态和
pre/post fingerprint 区分已成功、明确失败、结果未知和目标漂移；无法确认时停止自动重试。

### 4. 结果必须按证据等级表达

非空 Patch 只证明产生了候选改动；本地测试通过只证明记录的验证命令通过；只有 independent official evaluator
才能把对应 Case 记为 resolved。Trace、Reviewer 或 Finalizer 都不能替代这一结论。

## 架构演进与边界治理

NanoHarness 从 capability-first 模块化单体起步，随 HITL、恢复和 Multi-Agent 加入，再针对已出现的职责过重与依赖泄漏收敛边界：

| 阶段 | 暴露的问题 | 结构调整 | 保留的取舍 |
| --- | --- | --- | --- |
| 最小闭环 | 真实仓库任务尚未跑通 | 按 Context、Model、Tool、Safety、Trace 拆能力 | 允许早期流程与基础设施混合 |
| Runtime 分阶段 | AgentLoop 同时准备上下文、执行工具、恢复和落盘 | 抽出 RunPreparation、TurnPreparation、ToolExecution、RunLifecycle | AgentLoop 只保留阶段编排 |
| 依赖边界 | Application 直接认识 JSON、Git、进程和模型 SDK | 复杂能力内部使用 Domain、Application、Port、Adapter，由 Wiring 装配 | 简单模块保持扁平，不机械套层 |
| 显式契约 | 动态字典与模糊 Owner 需沿链反查 | 使用 dataclass/Enum、语义入口、分阶段注释与 AST 测试 | 只约束高风险主链 |

当前架构是 **capability-first modular monolith + selective hexagonal boundaries**：六边形边界只隔离会变的模型、存储、Git 和执行环境，完整 Owner 见[核心能力与代码入口](核心能力与代码入口.md)。

## Multi-Agent 协作

Multi-Agent 不是简单多开模型，而是 `Task DAG → 独立 worktree → 结构化交接 → 确定性合并 → 只读验收`。

- 强依赖阶段按 Implementer → Reviewer → Verifier 顺序推进。
- 修改范围互不冲突的子任务按依赖图并发，每个 Worker 使用独立 AgentLoop 和 worktree。
- Coordinator 汇总子任务状态和候选 Patch；冲突、越界或整体验证失败时停止合并。
- 失败恢复以子任务为单位；是否提高解决率仍需固定任务与模型的独立评测。

## 评测与当前边界

评测链路保持固定：

```text
issue + base commit
  -> isolated generation
  -> candidate patch
  -> local validation evidence
  -> official evaluator
  -> resolved / unresolved / empty / infra
```

当前公开结果是固定 SWE-bench Verified Mini-50 上的 Single-Agent Pass@1：official resolved `28/50`（56.0%），
另有 16 个 official unresolved 和 6 个 Agent terminal Empty Patch。50 个 Case 全部计入分母，最终没有仍待补全的 provider、Runtime、evaluator 或外部中断槽位。它说明真实 issue、仓库 checkout、工具循环、源码 Patch 和 official evaluator 已经贯通，
但不代表完整 500 题成绩，也不隔离 Harness 相对底座模型的单因素增益。完整分母、基础设施补全规则与声明边界见
[Quality Showcase](../benchmarks/showcase/canonical-showcase-v1.json)。

结果解释遵守以下边界：

- `planned` 是冻结分母，empty 和 unresolved 不能删除；
- Candidate、本地 PASS 和 Reviewer PASS 不能改写成 official resolved；
- 单次系统结果由模型、Runtime、工具、环境和 evaluator 共同产生；
- 不把固定 Mini-50 的结果外推为完整 500 题总体解决率。

## 后续优化路线

优化先看 failure distribution：验证反馈稳定时比较有界 revision loop，跨文件定位失败时比较 graph retrieval，
path/schema 中断集中时比较 typed feedback，任务可拆时比较固定 Multi-Agent DAG。每次固定 Case、Model、Budget 和 Environment，
预先定义 activation、official metric、non-regression guard 与 stop rule；未达门槛就回滚。

## 一分钟半快速介绍

1. NanoHarness 不是另一个代码生成器，而是把模型意图变成受治理工程执行的 Runtime。
2. 主链是 `Prepare → Turn → Model → Gate → Execute → Observe → Finalize`，模型只提议，Runtime 管 Context、Tool、权限、预算和恢复。
3. 核心取舍是 Checkpoint 与 Operation Ledger 分工：前者管流程位置，后者管持久副作用的确定结果与未知状态。
4. 质量用 Trace、Checkpoint、Diff、Usage 和 official evaluator 分层证明；当前公开口径是固定 Mini-50 的 `28/50` official resolved，不外推为完整榜单结果。

> NanoHarness 把 Context、Tool、权限、恢复、协作和 Evaluation 做成有明确状态、失败边界和运行证据的 Coding Agent Runtime。
