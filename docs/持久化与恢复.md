# 持久化与恢复

本文聚焦：

```text
不同 durable fact 分别存在哪里？
Checkpoint / ContextState / Ledger 为什么不能合并？
Crash / Resume 怎样重新组合这些事实？
```

> NanoHarness 按事实类型拆分 durable state：**Conversation 保存协议事实，ContextState 保存模型上下文状态，Checkpoint 保存 Run cursor，Approval/HumanInput 保存人工决定，Operation Ledger 保存副作用状态。**

# 1. 磁盘总图

```text
.agent_forge/
├── internal/state/
│   ├── threads/<thread_id>/
│   │   ├── thread.json
│   │   ├── conversation.jsonl
│   │   ├── context_state.json
│   │   └── terminal_intents/<turn_id>.json
│   │
│   ├── approvals/<operation_key>.json
│   ├── human_input/<request_id>.json
│   └── operation_ledger/<operation_key>.json
│
└── runs/<run>/
    ├── task_state/<run_id>.json
    ├── resolved_config.json
    ├── trace.jsonl
    ├── trace.json
    ├── usage.json
    ├── candidate_changes.diff
    └── execution_environment.json
```

速览：

| 文件 | 粒度 | 保存什么 |
|---|---|---|
| `thread.json` | Thread | Thread / Turn / Run navigation |
| `conversation.jsonl` | 一行一个 `ConversationItem` | raw Conversation |
| `context_state.json` | Thread | digest / cursor / Turn snapshots / revision |
| `task_state/<run_id>.json` | Run | Run checkpoint |
| `approvals/<operation_key>.json` | operation | human approval |
| `human_input/<request_id>.json` | question | human answer |
| `operation_ledger/<operation_key>.json` | side-effect operation | execution state |
| `trace.jsonl` | event | execution evidence |

# 2. Thread 控制面

## `thread.json`

保存：

```text
thread identity
workspace
Turn navigation
ThreadRun navigation
active / current ownership
journal tail metadata
```

它不保存完整 Conversation 正文。

## `conversation.jsonl`

一行一个 `ConversationItem`：

```text
user
assistant ToolCall batch
tool Observation
operator steer
human answer
```

核心 identity：

```text
sequence
= Thread-local append-log position

item_id
= stable logical / idempotent identity
```

所以：

```text
sequence
负责排序 / 增量读取 / compaction cursor

item_id
负责幂等 append / durable reference
```

# 3. `ThreadContextState`

`context_state.json`：

```text
ThreadContextState
├── revision
├── covered_sequence
├── conversation_history_digest
└── turn_snapshots[]
```

它是 derived Context state。

```text
conversation.jsonl
= raw authority

context_state.json
= bounded model-context projection state
```

# 4. `TaskCheckpoint`

一个 Run 一份：

```text
runs/<run>/task_state/<run_id>.json
```

核心：

```text
TaskCheckpoint
├── identity
├── workspace / execution mode
├── status / current_step
├── context_revision
└── pending_execution
```

`PendingExecutionPointer`：

```text
assistant_item_id
next_tool_call_index
pending_operation_key
pending_operation_fingerprint
```

Checkpoint 不复制：

```text
root_task
完整 Conversation
Digest
完整 ToolCall payload
```

它只保存恢复所需 cursor / pointer。

因此：

```text
一个 Turn
可以有多个 Run
→ 每个 Run 有自己的 checkpoint
```

# 5. Approval 与 Human Input

## Approval

```text
approvals/<operation_key>.json
```

回答：

```text
这个具体 operation
是否已经被人工允许？
```

## Human Input

```text
human_input/<request_id>.json
```

回答：

```text
这个具体人类问题
是否已经获得回答？
```

两者都是 durable human decision，但语义不同。

# 6. Operation Ledger

```text
operation_ledger/<operation_key>.json
```

粒度：

```text
一个副作用 operation
```

状态：

```text
planned / pending
→ approved
→ executing
→ executed | failed
```

同时保存：

```text
pre-fingerprint
post-fingerprint
result / history
```

所以：

```text
TaskCheckpoint
= Run 跑到哪里

OperationRecord
= 某个 side effect 跑到哪里
```

不能合成一个状态。

# 7. Run Artifacts / Trace

```text
resolved_config.json
= 本 Run 最终 resolved config

trace.jsonl
= append-only execution evidence

trace.json / usage.json
= presentation / metrics projection

candidate_changes.diff
= execution workspace 的候选修改
```

Trace 解释过程，但不成为 Resume authority。

# 8. Workspace / Worktree

```text
workspace
= 用户请求对应的原项目

execution_workspace
= 当前 Run 实际执行 Tool 的工作树
```

Local 模式可以相同。

Worktree：

```text
original repository
        ↓ git worktree
isolated execution working tree
```

Working files 独立，Git object database 共享。

等待 Resume 的 execution worktree 需要保留；terminal Run 才进入清理策略。

# 9. Resume 如何重新组合状态

恢复顺序：

```text
Thread / Turn identity
        ↓
ThreadContextState
        ↓
TaskCheckpoint
        ↓
pending ConversationItem / Tool Observations
        ↓
Approval / HumanInput
        ↓
Operation Ledger
        ↓
execution workspace
```

恢复的是这些 durable facts 的组合，而不是 Python stack。

# 10. Context Revision Crash Window

顺序：

```text
persist new ThreadContextState
→ update AgentRunSession pointer
→ persist TaskCheckpoint pointer
```

Crash：

```text
ContextState = 7
Checkpoint = 6
```

允许：

```text
authority 已 durable
→ continuation Run 对齐到 7
```

反向：

```text
Checkpoint = 7
ContextState = 6
```

不允许：

```text
checkpoint 指向不存在的 future context state
```

# 11. Tool Batch ID 关系

Assistant batch：

```text
ConversationItem.item_id
= assistant:run-A:3
```

其中一个 ToolCall：

```text
ToolCall.id
= call-write
```

它的 Tool Observation：

```text
ConversationItem.item_id
= tool:assistant:run-A:3:1:call-write
```

Checkpoint：

```text
assistant_item_id = assistant:run-A:3
next_tool_call_index = 1
```

这样 Runtime 可以：

```text
定位原 batch
→ 定位具体 index
→ 检查该 Tool Observation 是否已经存在
→ 决定继续 / replay / 只推进 cursor
```

# 12. 核心不变量

```text
1. Raw Conversation 与 derived Context 分离
2. Run cursor 与 side-effect state 分离
3. Trace 不驱动恢复
4. 一个 Run 一份 checkpoint
5. Resume 只恢复 durable evidence 可以证明的状态
6. authority state 先持久化，pointer 后更新
7. stable item identity 与 journal sequence 分工
```

# 13. 附录：等待 Approval 时如何排查

```text
1. thread.json
→ active Turn / current Run

2. task_state/<run>.json
→ status
→ pending assistant_item_id / index / operation_key

3. conversation.jsonl
→ original assistant batch
→ current Tool Observation exists?

4. approvals/<operation_key>.json
→ pending / approved / rejected

5. operation_ledger/<operation_key>.json
→ pending / executing / executed

6. execution workspace
→ actual target state

7. trace.jsonl
→ explain execution history
```
