# 架构导览

> NanoHarness 的统一架构入口：先建立身份、Ownership 与执行主链，再按能力文档下钻。

---

<a id="system"></a>

# 1. 系统定位

```text
Inbound applications
├── apps/                           CLI / Console / Showcase / Workbench / MCP
└── agent_forge/harness.py          Single-Agent embedded API
              │
              ▼
agent_forge/<capability>/
├── application                     用例编排与控制流
├── domain                          业务规则与状态语义
├── ports                           对外依赖边界
└── adapters                        文件、Git、Provider 等 IO 实现
```

`Harness.run()` 是 Single-Agent composition root；能力包不依赖展示应用。系统只保留一套
核心治理语义：

```text
Model proposes
Runtime decides
Execution produces facts
Evidence verifies results
```

# 2. 总体主链

```text
RunRequest
    ↓
Harness.run()
    ├── bind ConversationThread / Turn / new Run
    ├── ExecutionEnvironment
    ├── RuntimeDependencies
    └── AgentLoop.run()
            ↓
      RunPreparation.create_session()
            ↓
      RunPreparation.prepare_run()
            └── freeze/reuse TurnContextSnapshot
            ↓
      ToolExecutionPipeline.resume_pending_calls() when present
            ↓
      bounded Model Step loop
            ↓
      ModelStepPreparation.prepare_model_step()
            ↓
      PreparedModelStep
            ↓
      ModelPort.chat(...)
            ↓
      AgentResponse
       ├── final text → FinalAnswerBuilder
       └── ToolCalls  → durable batch → ToolExecutionPipeline → Observations
            ↓
      RunLifecycle.finalize_run()
            ↓
      accepted final + TaskCheckpoint v4 + Trace + Run artifacts
```

`Harness` 负责外部输入、Thread/Turn/Run 身份、Adapter 装配和产物收口；`AgentLoop`
只拥有 Runtime 控制流；各阶段业务规则由具名 Application Owner 执行。

# 3. Agent 运行数据模型

## 身份层级

```text
ConversationThread                    durable user conversation
└── Turn                              one top-level user request to terminal
    ├── Run 1                         execution attempt
    └── Run 2                         resume attempt of the same Turn
         └── Model Step 1..N          one llm.chat boundary per step
```

| 身份 | 何时变化 | 拥有什么 |
|---|---|---|
| `thread_id` | 新用户对话 | 全部 Turn、完整 durable Conversation 与导航状态 |
| `turn_id` | 新顶层用户请求 | `root_task`、稳定输入快照、一个或多个 Run |
| `run_id` | 每次实际执行或 Resume | checkpoint、trace、usage 和 artifact |

普通后续请求是 same Thread / new Turn / new Run；Resume 是 same Thread / same Turn /
new Run。一次用户 Thread 同时最多一个 active Turn。

## 权威数据与执行视图

```text
ConversationThread
├── thread.json                       Turn/Run navigation
├── conversation.jsonl                authoritative raw items
└── context_state.json
    ├── ConversationHistoryDigest     derived continuation projection
    └── TurnContextSnapshot           stable input contract per Turn

AgentRunSession                        one Run's bounded in-memory view
├── thread_id / turn_id
├── root_task / turn_focus
├── messages / observations
├── stable snapshot material
├── working_memory
└── lifecycle / controller

TaskCheckpoint v4                      one Run's latest execution snapshot
├── thread_id / turn_id / run_id
├── context_revision
├── execution workspace
└── pending assistant item + call cursor
```

`conversation.jsonl` 中每条 `ConversationItem` 带稳定 `sequence`、`item_id`、payload
hash、`origin` 和 `human_authority`。Provider `role=user` 只是模型输入编码，不能替代
内部授权语义。

详细关系见 [Agent 运行数据结构与模型输入](Agent运行数据结构与模型输入.md)。

<a id="context"></a>

# 4. LLM 输入的三块来源

```text
PreparedModelStep
├── turn_system_message
│     └── TurnSystemContextBuildReport.render()
├── llm_messages
│     └── stable system message + governed conversation projection
└── tool_schemas
      └── ToolRouter selected contracts
```

稳定 System Context、Conversation projection 和 Tool schemas 分别治理，最终在
`PreparedModelStep` 汇合。当前 mandatory governance prompt 不可被动态仓库上下文挤掉。

`TurnContextSnapshot` 在新 Turn 首次准备时冻结：

```text
Prompt profile
+ project/global instructions
+ selected Skills
+ Long-Term Memory Recall Snapshot
+ base Tool schemas
+ Runtime contract
        ↓
TurnContextSnapshot + contract_hash
```

同一 Turn 的全部 Resume Run 复用该快照；当前 Runtime contract 或 Tool registry 不兼容
时 fail closed。新 Turn 才重新发现这些稳定输入。仓库 map、Working Memory、权限摘要等
运行事实仍在每个 Model Step 动态组装。

# 5. 提示窗口（Prompt Window）

```text
ConversationThread raw items after covered_sequence
    + previous ConversationHistoryDigest
    + Turn stable/dynamic system context
    ↓
PromptWindowRequest.conversation_history
    ↓
PromptWindowManager.prepare()
    ├── within limit → previous digest + uncovered raw delta
    └── over limit   → merged digest + recent raw tail
    ↓
PromptWindowResult.llm_messages
    ↓
PreparedModelStep.llm_messages
```

Compaction 只改变模型输入投影，不删除或改写 Thread raw items。窗口切分不得拆开 assistant
ToolCall batch 与全部对应 Observation；`ask_human` 的原始日志保持 authority-first，模型
投影则恢复为 provider-valid 的 assistant → tool results → authoritative answer 顺序。

Long-Term Memory 的 task-aware Recall Snapshot 在新 Turn 冻结；按最新 human-authority
消息查询的 bounded Management Candidates 只服务当前 Model Step 的 `remember_memory`。
完整机制见 [上下文工程](上下文工程.md) 与
[上下文压缩与长任务设计](上下文压缩与长任务设计.md)。

<a id="governance"></a>

# 6. 运行治理（Runtime Governance）

```text
AgentResponse(content + ToolCalls)
    ↓
authoritative assistant item durable append
    ↓
TaskCheckpoint.pending_execution
    ↓
ToolExecutionPipeline
    ├── routing / guardrail
    ├── authorization / Approval
    ├── Operation Ledger
    └── ToolGateway.execute()
            ↓
      durable Tool Observation
            ↓
      advance call cursor
```

完整 assistant batch 必须先落盘，再逐项执行。Resume 读取相同 assistant item 与 cursor，
不会要求模型重新生成 ToolCall。副作用 operation identity/fingerprint 负责 replay 边界；
每个 ToolCall 只允许一条合法 Observation。完整链路见
[运行治理与工具执行](运行治理与工具执行.md)。

<a id="durability"></a>

# 7. 持久化控制面（Durable Control Plane）

```text
Authoritative state
├── Thread conversation.jsonl
├── Thread metadata / context state
├── Thread terminal intent
├── TaskCheckpoint v4
├── Approval / HumanInput
├── Operation Ledger
└── Long-term Memory

Execution evidence
└── trace.jsonl

Derived presentation
├── trace.json / usage.json / reports
└── Workbench projections
```

`trace.jsonl` 回答一次 Run 实际发生过什么，但不是 raw Conversation store。生产 Runtime
只加载 canonical current schema；历史 Lab / Mini-50 Evidence 的旧字段只由 Workbench
read-only presentation compatibility 解释，不进入恢复路径。

Normal follow-up 与 Resume 的差异：

```text
normal follow-up
same thread_id / new turn_id / new run_id
→ new TurnContextSnapshot

resume
same thread_id / same turn_id / new run_id
→ reuse snapshot and pending execution pointer
```

终态提交固定为 terminal intent → terminal checkpoint → Turn/current ThreadRun commit；若进程
在后两步之间崩溃，Thread loader 只在 intent 与 canonical v4 checkpoint 身份、状态一致时
幂等补完收口。

完整契约见 [运行产物与持久化契约](运行产物与持久化契约.md)。

# 8. 多 Agent 编排（Multi-Agent）

Repository execution 只有 Single / Ultra 两种公开策略。Single 直达同一
canonical `AgentLoop`；Ultra 强制 Planning，但允许 Runtime 根据合法计划选择
Single 或 Multi。Planning 与 execution 是 Application composition 的相邻阶段，
不是 `FanoutCoordinator.run()` 内部隐式调用 Planner：

```text
Repository Task
    ├── Single → Harness.run() → AgentLoop.run()
    └── Ultra  → AdaptivePlanner.decide()
                       └── PlanningDecision
                              ├── single → same Harness.run()
                              └── multi  → validated FanoutPlan
                                            ↓
                                  build_live_fanout()
                                            ↓
                                  FanoutCoordinator.run()
                                            ↓
                                  _run_plan() unified scheduler
                                      ├── HARD: integrated-state readiness
                                      └── LIVE: semantic early readiness
                                            ↓
                                  isolated Worker AgentLoops
                                            ↓
                                  candidate gates / integration
                                            ↓
                                  read-only Finalizer
```

Planner 只提议。Runtime 依次做 Schema、Domain 和 FanoutPlan/Graph validation；
失败时把明确错误编入最多一次 repair prompt，仍失败则回退 Single 或
对 remaining-plan replan fail closed。

Planner 与 Coordinator 不拥有 AgentLoop Conversation。每个 Worker 和 Finalizer 使用
私有 durable `ConversationThread`；用户主 Thread 只保留顶层请求与顶层结果，不灌入内部
Worker raw token/tool history。Coordinator 继续拥有确定性 integration，Finalizer 继续
使用只读 Tool surface。HARD 和 LIVE 是 dependency semantics，不是两套 scheduler；
纯 HARD DAG 可能自然形成一波波并发任务，但 Batch 只是运行结果。
完整设计见 [多 Agent 编排](多Agent编排.md)。

<a id="evaluation"></a>

# 9. 评测（Evaluation）

```text
Fixed Case Cohort
    ↓
RunSwebench.run_benchmark()
    ↓
LocalCaseExecutor.run() → build_agent_loop() → AgentLoop.run()
    ↓
Candidate Patch + canonical Trace
    ↓
Official Evaluator
    ↓
resolved / unresolved / empty patch / infrastructure failure
    ↓
Scorecard and failure projection
```

Candidate diff、local validation 和 official result 是不同事实。评测层读取证据并投影，
不把本地检查自动提升为 official pass，也不把历史 presentation compatibility 当作当前
Runtime contract。

## 源码入口（Source Anchors）

- `agent_forge/harness.py::Harness.run()`：Thread/Turn/Run 绑定与 Single-Agent composition root。
- `agent_forge/runtime/domain/thread.py::ConversationThread`：对话、Turn、Run 导航与 context snapshot 领域事实。
- `agent_forge/runtime/application/agent_loop.py::AgentLoop.run()`：Run 内 Model Step 主循环。
- `agent_forge/runtime/application/model_step_preparation.py::ModelStepPreparation.prepare_model_step()`：模型输入汇合点。
- `agent_forge/runtime/application/tool_execution.py::ToolExecutionPipeline`：完整 assistant batch 的治理与恢复。
- `agent_forge/runtime/application/run_lifecycle.py::RunLifecycle.finalize_run()`：accepted final、checkpoint 与 Turn 终态。
- `apps/repository_run.py::run_repository_task()`：Single / Ultra 公开路由。
- `agent_forge/multi_agent/application/fanout.py::FanoutCoordinator._run_plan()`：Multi-Agent 统一调度与集成入口。
- `agent_forge/bench/application/swebench.py::RunSwebench.run_benchmark()`：单 Case benchmark 入口。
