# 架构导览

> NanoHarness 是一个以治理、恢复和运行证据为核心的 Coding Agent Runtime。本文提供系统主链的快速技术导览；具体字段、状态机、源码与实验细节通过对应技术文档下钻。

<a id="system"></a>

## 1. 系统概览 / System Overview

```text
Repository Task
      ↓
Isolated Workspace
      ↓
AgentLoop
      │
      ├──── Context Engineering
      │       ↓
      │     Model
      │
      └──── Governed Tool Execution
              ↓
          Observation
              │
              ├→ Conversation / Working Memory
              ├→ Checkpoint / Ledger
              └→ Trace / Evidence
      ↓
Candidate Diff
      ↓
Validation / SWE-bench
```

三个核心原则：

```text
Model proposes
Runtime decides
Evidence verifies
```

NanoHarness 的重点不是“再封装一次模型调用”，而是解决长链路 Coding Agent 真正进入代码仓库之后的 Runtime 问题：

- 每一 Turn 给模型什么上下文；
- ToolCall 如何安全落地；
- 副作用如何授权、防重复和恢复；
- 人工输入、暂停、Steer 如何进入运行生命周期；
- Runtime 改动如何用真实 Benchmark 验证。

## 2. 上下文工程 / Context Engineering

```text
AgentRunSession
      ↓
TurnPreparation
      ↓
PreparedTurn
      ↓
Model
      ↓
AgentResponse
```

一次模型调用的核心输入来自三部分：

```text
Current Runtime Context
+
Conversation History View
+
Tool Schemas
```

其中最重要的四个概念是：

```text
Runtime Context
→ 当前世界，每 Turn 重建

Raw Conversation History
→ 已发生的 user / assistant / tool 协议事实

WorkingMemory
→ bounded run-local read model / scratchpad
→ 不等于 Conversation History

SessionDigest
→ 超预算后对旧 Raw History 做结构化压缩
```

压缩 / Compaction：

```text
Old Raw History
→ Protocol Segmentation
→ Semantic Projection
→ deterministic SessionDigest
```

并且每 Turn 都从 Raw Evidence 重新计算：

```text
Raw History → Digest
```

而不是：

```text
Digest → Digest → Digest
```

稳定前缀 / Stable Prefix：

```text
stable / relatively stable sections first
dynamic retrieval / memory / history later
```

Runtime 只负责 prefix-cache-friendly layout 和 Provider-reported cache usage observability，不保证 Provider cache hit。

<a id="governance"></a>

## 3. 受治理工具执行 / Governed Tool Execution

```text
MODEL PREPARATION

ToolRegistry
↓
ToolRouter
├── schemas ───────→ Model capability view
└── allowed_names ─→ Runtime enforcement view
        │
        ▼
      Model
        │
        ▼
    ToolCall


RUNTIME EXECUTION

ToolCall
↓
OperationIntent
↓
Existing Operation Ledger
↓
Authorization / Approval
↓
Ledger → executing
↓
ToolGateway / ToolRegistry
↓
Tool.execute()
↓
Observation
↓
Ledger → executed / failed
```

核心原则：

```text
Model proposes
Runtime decides
ToolGateway executes
```

两个关键区分：

```text
Approval
= 这个操作能不能执行

Operation Ledger
= 这个操作已经执行到哪
```

副作用防重复依赖：

```text
deterministic operation_key
+
durable state lookup
+
Runtime no-repeat rule
```

崩溃安全 / Crash Safety：

```text
approved
↓
executing
↓
real side effect
↓
executed / failed
```

如果 crash 发生在 `executing` 之后：

```text
outcome = uncertain
→ fail closed
→ no blind replay
```

这是一条防重复恢复合同，不宣称跨系统 exactly-once 或分布式事务。

## 4. 持久化与控制 / Durability & Control

```text
Running
   │
   ├── normal turn ─────────────→ continue
   │
   ├── ask_human ───────────────→ WAITING_HUMAN
   │                                  ↓
   │                               checkpoint
   │                                  ↓
   │                               Run ends
   │                                  ↓
   │                              human answer
   │                                  ↓
   │                           continuation Run
   │
   ├── approval ─────────────────→ WAITING_APPROVAL
   │
   ├── pause ────────────────────→ PAUSED
   │
   └── crash / side-effect state
          ↓
     Checkpoint + Ledger
          ↓
     recover known fact or fail closed
```

`ask_human` 不是阻塞线程等待输入，而是：

```text
LLM ask_human(question, choices)
↓
HumanInputRepository.request()
↓
deterministic request_id
↓
JSON status = pending
↓
WAITING_HUMAN checkpoint
↓
current Run ends
```

用户回答后：

```text
pending → responded
↓
BuildContinuationPlan
↓
Harness.resume(...)
↓
NEW Run / NEW AgentRunSession
```

Approval 与 `ask_human` 是两条不同控制链：

```text
ask_human
→ HumanInputRepository
→ WAITING_HUMAN

Approval
→ ApprovalRepository
→ WAITING_APPROVAL
```

运行控制 / Run Control：

```text
Pause
= 在安全边界协作停止当前 Run，可恢复

Cancel
= 在安全边界协作停止，任务终止

Steer
= non-terminal replanning
```

Steer 在模型调用期间到达时：

```text
model response returns
↓
response becomes stale
↓
discard AgentResponse
↓
append steer as role=user
↓
REPLAN
```

Steer 在 Tool batch 中到达时，当前实现不会硬中断已开始的 Tool transaction，而是在下一 Model Boundary 生效。

## 5. 评测 / Evaluation

NanoHarness 的 Runtime 改动同时看 correctness、efficiency 和 experiment governance。

### 开发门禁 / Development Gate

```text
Golden-20 R2

Resolved
14 / 20 → 14 / 20

Token
-33.6%

Tool Calls
-20.8%

1 gain
1 regression

→ Reject / Revert
```

核心判断：

```text
aggregate score unchanged
≠ non-regression
```

### 最终 Mini-50 / Final Mini-50

```text
Official resolved      28 / 50
Pass@1                 56%
Terminal-accounted     50 / 50
```

发布门：

```text
initial 23 / 50
↓
infrastructure publish gate failed
↓
result rejected
↓
only pre-registered provider / external interruption slots retried
↓
no correctness-terminal rerun
↓
50 / 50 cases receive attributable terminal states
↓
formal result: 28 / 50
```

Golden-20 是反复使用的开发集，不是 holdout；Mini-50 是固定样本，不代表完整 500 题排行榜，也不隔离 Harness 相对底座模型的单因素增益。
