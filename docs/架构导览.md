# 架构导览

> NanoHarness 是一个以 **长链路状态治理、受控执行、恢复和证据** 为核心的 Coding Agent Runtime。
> 本文只保留适合技术讲解的主链和边界。

---

# 1. 系统为什么不是一个简单 AgentLoop

最简单的 Agent：

```text
while not done:
    response = LLM(history, tools)
    execute(response.tool_calls)
```

真正进入代码仓库后，会立刻遇到：

```text
Context 会增长
Tool 会失败
副作用不能重复
任务会被打断
进程会崩
模型会重复探索
多个 Agent 会冲突
最终结果需要可验证
```

所以 NanoHarness 的定位是：

```text
Mature Coding Agent
=
Model
+ Runtime
+ Execution Environment
+ Durable State
+ Evaluation
```

<a id="governance"></a>

## 3.2 执行与治理平面 / Execution & Governance Plane

解决：

> 模型说“调用工具”，为什么不能直接执行？

```text
ToolCall
↓
route recheck
↓
OperationIntent
↓
existing Operation Ledger
↓
Authorization / Approval
↓
record executing
↓
ToolGateway
↓
Observation
↓
record executed / failed
```

核心原则：

```text
Model proposes
Runtime decides
Tool executes
```

详见 `工具治理与执行.md`。

---

<a id="durability"></a>

## 3.3 持久化控制平面 / Durable Control Plane

解决：

> Agent 跑半小时后 crash / 等人 / 暂停，怎么继续？

```text
Live Session
   │
   ├── TaskCheckpoint
   ├── HumanInput
   ├── Approval
   ├── Operation Ledger
   └── Trace
```

注意：

```text
Checkpoint = latest durable control snapshot
Trace      = append-only happened-before evidence
Ledger     = side-effect state
```

它们不是同一个东西。

详见 `运行产物与持久化契约.md`。

<a id="evaluation"></a>

## 3.4 评测平面 / Evaluation Plane

解决：

> Runtime 改了以后，怎么知道是真的变好？

```text
Fixed Case Cohort
↓
Agent Runtime
↓
Candidate Patch + Trace
↓
Official Evaluator
↓
Resolved / Unresolved / Empty Patch / Infra
↓
Scorecard / Failure Review
```

当前固定 Mini-50 的已冻结结果：

```text
Official resolved  28 / 50
Pass@1             56%
```

这个结果只属于固定 cohort + 固定模型/Runtime revision，不代表完整 500 题，也不能单独归因于某一个 Harness feature。

# 4. Context 不应该按变量堆叠理解

<a id="context"></a>

业务上按 LLM Context Budget 来源分三类：

```text
                         LLM Context Budget
                                │
          ┌─────────────────────┼─────────────────────┐
          │                     │                     │
     Runtime State          Knowledge            Capability
          │                     │                     │
     Conversation           Repo Context          Skills
     Working State          External Evidence     Tool Schemas
     Task State             Long-term Memory      Permissions
```

不同 Source 使用不同治理：

```text
Conversation    → compaction
Working State   → bounded structured state
Repo            → retrieval
Long-term Mem   → recall
Skill           → progressive disclosure
Tool Schema     → routing
Permission      → deterministic policy projection
```

# 5. Workspace、Worktree、Run Artifacts 必须分开

```text
ExecutionEnvironment
= 命令在哪、怎么执行

Workspace
= Agent 当前实际读写的代码树

Git Worktree
= Workspace 隔离的一种实现

Run Artifact Dir
= Trace / Checkpoint / Diff / Usage 等运行证据
```

Multi-Agent Worker 使用独立 worktree 的目的，是让多个 Worker 不在一个 mutable code tree 上互相踩写入状态。

# 6. 当前 Multi-Agent 能力边界

V0 stable 的 execution half：

```text
Typed FanoutPlan
↓
DAG / conflict-free scheduling
↓
Independent Worker AgentLoops
↓
Isolated Worktrees
↓
Candidate Diff
↓
Conflict Gates
↓
Stable Integration
↓
Read-only Finalizer
```

V0 stable 的 `FanoutPlan` 仍由外部提供。

`feature/multi-agent-v1` 当前已经补齐：

```text
Natural Task
↓
Planner
↓
Single / Fanout Gate
↓
Structured Handoff
↓
Bounded Recovery / Replan
↓
Criteria-aware Finalizer
```

V1 仍复用 V0 的 Scheduler、独立 Worktree、Conflict Gates 和稳定集成；Planner 只提议，Runtime 继续做确定性校验。V2 定量评测和自动语义冲突解决仍是 FUTURE / NOT IMPLEMENTED。

# 7. 长任务是 Runtime 问题，不只是 Context 问题

Run 生命周期变长以后，以下问题从“偶发”变成“必然”：

```text
Context Growth
Crash / Resume
Side-effect Replay
No-progress Loop
Plan Drift
Deadline Propagation
```

NanoHarness 当前已重点解决：

```text
Checkpoint / Resume
Operation Ledger
HITL
Repeat / Failure / Budget
Tool Governance
Trace / Eval
```

Conversation incremental compaction、in-flight deadline propagation 等仍是明确可演进项。

# 9. 60 秒摘要

> NanoHarness 不是把 LLM 和几个 Tool 接起来，而是把 Coding Agent 当成一个长生命周期 Runtime。一个 Run 的 live state 放在 AgentRunSession 中，每个 Turn 再投影成 PreparedTurn 给模型；ToolCall 返回以后必须经过路由复核、Operation Ledger、授权和执行边界，真实结果才成为 Observation。Checkpoint、HumanInput、Approval 和 Ledger 各自保存不同的 durable truth，Crash 后创建 continuation Run，而不是恢复 Python 栈。Multi-Agent 复用同一 Worker Runtime，只在上层增加 DAG、worktree isolation、冲突门和稳定集成。最后所有 Runtime 改动都通过固定 Benchmark 和 Trace Evidence 验证，而不是只看模型最终说了什么。
