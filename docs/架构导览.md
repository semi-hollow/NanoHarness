# 架构导览

> NanoHarness 是一个由确定性 Runtime 治理模型提案的 Coding Agent Harness。整套系统可以沿一条主线理解：用户请求进入 Turn，AgentLoop 迭代 Model Step，ToolCall 经过治理后形成事实，最终状态写入可恢复的控制面。

<a id="system"></a>

# 1. 系统定位

```text
Inbound applications
├── apps/                         CLI / Console / Workbench / MCP
└── agent_forge/harness.py        Single-Agent embedded API
              │
              ▼
agent_forge/<capability>/
├── application                  use-case orchestration
├── domain                       state and invariants
├── ports                        dependency boundaries
└── adapters                     filesystem / Git / Provider I/O
```

`Harness.run()` 是 Single-Agent composition root。模型与 Runtime 的职责边界固定为：

```text
Model proposes
Runtime decides
Execution produces facts
Evidence verifies results
```

# 2. 总体主链

```text
RunRequest
→ Harness.run()
→ bind ConversationThread / Turn / new Run
→ RunPreparation.prepare_run()
→ freeze or restore StableTurnContextSnapshot
→ AgentLoop.run()
    → ModelStepPreparation.prepare_model_step()
    → PreparedModelStep
    → ModelPort.chat(...)
    → AgentResponse
        ├── ToolCalls → durable batch → governed execution → Observations
        └── final text → typed stop candidate → output governance
→ RunLifecycle.finalize_run()
→ Thread state + TaskCheckpoint v4 + Trace + Run artifacts
```

`Harness` 绑定身份并装配依赖；`AgentLoop` 只拥有阶段顺序；输入、窗口、工具、副作用和终态分别由具名 Application Owner 决策。一次 Tool 后通常回到下一个 Model Step，直到完成、等待人工、暂停或失败。

# 3. Agent 运行数据模型

```text
ConversationThread                    durable user conversation
└── Turn                              one top-level user request
    ├── Run 1                         execution attempt
    └── Run 2                         resume attempt of the same Turn
         └── Model Step 1..N          one ModelPort.chat(...) boundary
```

| 身份 | 变化时机 | Canonical ownership |
|---|---|---|
| `thread_id` | 新对话 | 完整 Conversation、Turn/Run 导航、Thread Context State |
| `turn_id` | 新顶层请求 | `Turn.root_task` 与稳定输入快照 |
| `run_id` | 每次 fresh execution 或 resume | checkpoint、trace、usage、artifact |
| Model Step | 每次模型调用 | 一份冻结的 `PreparedModelStep` |

```text
Normal follow-up = same Thread + new Turn + new Run
Resume           = same Thread + same Turn + new Run
```

四类容易混淆的数据各有一个角色：

| 数据 | 角色 |
|---|---|
| `conversation.jsonl` | 无损、append-only 的 raw Conversation authority |
| `ThreadContextState` | digest、`covered_sequence` 与 Turn snapshots 的 derived state |
| `TaskCheckpoint v4` | 当前 Run 的恢复状态和未完成 Tool batch cursor |
| `trace.jsonl` | 实际执行过程的 append-only evidence |

完整 ownership 见 [Agent 运行数据结构与模型输入](Agent运行数据结构与模型输入.md)。

<a id="context"></a>

# 4. LLM 输入的三块来源

```text
PreparedModelStep
├── model_step_system_message
│   ├── StableTurnContextSnapshot.stable_system_prefix
│   └── current dynamic repository context
├── llm_messages
│   └── governed Conversation projection + transient control
└── tool_schemas
    └── ToolRouter selected contracts
```

稳定规则在 Turn 开始时冻结，动态仓库事实在每个 Model Step 重建，Conversation history 由 Prompt Window 治理，Tool schemas 独立路由。三者只在 `ModelStepPreparation.prepare_model_step()` 汇合。

# 5. 提示窗口（Prompt Window）

```text
previous ConversationHistoryDigest
+ journal items after covered_sequence
→ transaction-safe segments
→ smallest legal compact prefix that restores budget
→ merged digest + protocol-preserving recent tail
→ PromptWindowResult.llm_messages
```

Compaction 不改写 `conversation.jsonl`。assistant ToolCall batch 与对应 Tool Observations 是不可拆单元；超大正文可以确定性截断，因此只有 journal 是无损历史。Digest 从 `context_state.json` 恢复，只处理 cursor 后的新 delta。完整 retention 和 rolling search 见 [上下文压缩与长任务设计](上下文压缩与长任务设计.md)。

<a id="governance"></a>

# 6. 运行治理（Runtime Governance）

```text
AgentResponse(content + ToolCalls)
→ append complete assistant batch
→ TaskCheckpoint.pending_execution
→ route / guardrail / authorization
→ Operation Ledger for side effects
→ ToolGateway.execute()
→ append exactly one Tool Observation
→ advance cursor
```

模型只产生调用提案。Runtime 重新校验当前 route、具体授权和副作用身份；ConversationThread 保存协议事实；checkpoint 指向未完成执行。进程恢复直接继续原 batch，不要求模型重新生成。完整链路见 [运行治理与工具执行](运行治理与工具执行.md)。

<a id="durability"></a>

# 7. 持久化控制面（Durable Control Plane）

```text
Authoritative state
├── ConversationThread journal and metadata
├── ThreadContextState
├── TaskCheckpoint v4
├── Approval / HumanInput
├── Operation Ledger
└── Long-Term Memory

Execution evidence
└── trace.jsonl

Derived presentation
├── trace.json / usage.json / reports
└── Workbench views
```

恢复先读取 authoritative state，再用 Trace 解释过程。Turn 终态按 terminal intent、terminal checkpoint、Thread/Turn commit 收口；身份或状态不一致时 fail closed。Artifact 与恢复边界见 [运行产物与持久化契约](运行产物与持久化契约.md)。

# 8. 多 Agent 编排（Multi-Agent）

Repository execution 公开为 Single / Ultra。Single 直接使用 canonical `AgentLoop`；Ultra 先规划，再由 Runtime 选择合法的 Single 或 Multi 执行：

```text
Ultra
→ AdaptivePlanner.decide()
    ├── single → Harness.run()
    └── multi  → validated frozen FanoutPlan
                 → build_fanout()
                 → FanoutCoordinator.run()
                 → _execute_plan()
                     ├── HARD: integrated-state readiness
                     └── LIVE: semantic early readiness
                 → isolated Worker candidates
                 → Strict Integration Frontier
                 → read-only Finalizer
```

Planner 输出是 proposal，不是可直接执行命令。Worker 在隔离 worktree 中复用 AgentLoop，只产生 candidate；Coordinator 独占 integration authority。HARD 等待 upstream trusted integration，LIVE 只提前放开启动，最终仍校验 producer 已集成且 consumer 消费最新版本。完整控制闭环见 [多 Agent 编排](多Agent编排.md)。

<a id="evaluation"></a>

# 9. 评测（Evaluation）

```text
Fixed Case Cohort
→ RunSwebench.run_benchmark()
→ LocalCaseExecutor.run()
→ Candidate Patch + canonical Trace
→ Official Evaluator
→ resolved / unresolved / empty patch / infrastructure failure
→ Scorecard
```

Candidate diff、本地 validation 和 official result 是三个独立事实。评测层读取 evidence 并投影结果，不把本地检查提升为 official pass。

## 源码入口（Source Anchors）

- `agent_forge/harness.py::Harness.run()`：Single-Agent composition root。
- `agent_forge/runtime/application/agent_loop.py::AgentLoop.run()`：Run 内主循环。
- `agent_forge/runtime/application/run_preparation.py::RunPreparation.prepare_run()`：Turn 稳定输入边界。
- `agent_forge/runtime/application/model_step_preparation.py::ModelStepPreparation.prepare_model_step()`：模型输入汇合点。
- `agent_forge/runtime/application/tool_execution.py::ToolExecutionPipeline`：Tool batch 治理与恢复。
- `agent_forge/runtime/application/run_lifecycle.py::RunLifecycle.finalize_run()`：Run 与 Turn 终态收口。
- `apps/repository_run.py::run_repository_task()`：Single / Ultra 路由。
- `agent_forge/multi_agent/application/fanout.py::FanoutCoordinator.run()`：Multi-Agent execution owner。
