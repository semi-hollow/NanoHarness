# 核心能力与代码入口

[← 架构导览](./架构导览.md#system)

本文只回答一个问题：**已经知道能力名称时，第一段应该打开哪段核心代码**。表中的 Owner
是该能力的首个阅读入口，不是所有相关文件的罗列。GitHub 中可直接点击核心
Owner 进入源码；在 PyCharm 中也可连按两次 `Shift` 搜索完整 Owner，结果不唯一时先进入类，
再用 `⌘F` 搜索方法名。

模型输入数据流见[上下文工程](上下文工程.md)，工具执行骨架见[工具治理与执行](工具治理与执行.md)，
持久化状态和恢复权威见[运行产物与持久化契约](运行产物与持久化契约.md)。需要先建立整体认识时，
从[架构导览](架构导览.md)开始。本文是唯一全局源码 Owner 索引，不重复机制正文。

## 最小主链

一次 Single-Agent Run 的最短代码路径由下面八个 Owner 构成。遇到具体能力，再查后续索引。

| 顺序 | Owner | 只负责什么 |
| --- | --- | --- |
| ① | [`Harness.run`](../agent_forge/harness.py) | 接收公开请求，创建运行产物和执行环境，装配并启动 Runtime |
| ② | [`AgentLoop.run`](../agent_forge/runtime/application/agent_loop.py) | 编排 Run 准备、Turn、模型、Tool 和唯一终态 |
| ③ | [`RunPreparation.prepare_run`](../agent_forge/runtime/application/run_preparation.py) | 在首个 Turn 前处理澄清、Skill、Memory 和恢复摘要 |
| ④ | [`TurnPreparation.prepare_turn`](../agent_forge/runtime/application/turn_preparation.py) | 为本轮组装 Context、压缩预算并确定可见 Tool |
| ⑤ | [`ModelGateway.chat`](../agent_forge/models/gateway.py) | 统一主模型、同 Provider 有界重试、显式备用模型和 Usage |
| ⑥ | [`ToolExecutionPipeline._execute_call`](../agent_forge/runtime/application/tool_execution.py) | 串起 ToolCall 复核、操作状态、授权、执行和 Observation 提交 |
| ⑦ | [`FinalAnswerBuilder.build_stop_request`](../agent_forge/runtime/application/final_answer.py) | 把模型最终输出转换为类型化停止请求 |
| ⑧ | [`RunLifecycle.finalize_run`](../agent_forge/runtime/application/run_lifecycle.py) | 统一提交最终状态、停止原因、Trace 和 Checkpoint |

从 composition root 看，一个 Worker / Single-Agent Runtime 的装配顺序是：

```text
ExecutionEnvironment
→ RuntimeConfig
→ build_registry
→ build_runtime_dependencies
→ AgentLoop
→ RunPreparation.create_session
→ TurnPreparation.prepare_turn
→ ToolExecutionPipeline._execute_call
```

入口在 [Runtime wiring composition root](../agent_forge/runtime/wiring.py)。Fanout Worker 复用同一 Runtime
实现，但为每个 task 派生独立 workspace、state/approval/ledger roots、Tool allowlist 与新
`AgentLoop`；Worker 不共享 `AgentRunSession` 或 WorkingMemory。

## 核心数据结构入口

| 需要解释的状态 | 首个类 | 读完应该说清什么 |
| --- | --- | --- |
| AgentLoop 内的可变会话状态 | [`AgentRunSession`](../agent_forge/runtime/application/session.py) | Task、History、Observation、Working Memory、Evidence 和预算如何会合，但策略不属于它 |
| 一次模型调用的冻结输入 | [`PreparedTurn`](../agent_forge/runtime/application/turn_preparation.py) | Runtime Context/History、Tool Schemas、可见工具、预算与 Digest 来自同一快照 |
| 模型端口返回的规范化结果 | [`AgentResponse`](../agent_forge/runtime/domain/conversation.py) | 文本、Reasoning、ToolCall、错误、Usage 和 Provider 身份保持分层 |
| 当前 Run 的有界上下文读模型 | [`WorkingMemory`](../agent_forge/runtime/application/working_memory.py) | 最近事实、Observation 摘要、Run-local KV 与长期记忆快照不混成持久状态 |
| 最终答案可引用的工具事实 | [`EvidenceLedger`](../agent_forge/observability/domain/evidence.py) | 只筛选值得引用的 Observation，不参与 Tool 执行正确性判断 |
| ToolCall 的治理身份 | [`OperationIntent`](../agent_forge/runtime/application/operation_tracker.py) | action、command、side effect、target、operation key 与 fingerprint 如何统一解释 |
| 工具返回 Runtime 的统一事实 | [`Observation`](../agent_forge/runtime/domain/conversation.py) | 业务成功与执行基础设施成功为何需要区分 |
| 一轮后主循环能做什么 | [`TurnOutcome`](../agent_forge/runtime/application/agent_loop.py) | 只允许 `CONTINUE`、`REPLAN`、`STOP`，停止时必须携带 `StopRequest` |
| 旧 History 如何进入小窗口 | [`SessionDigest`](../agent_forge/context/domain/memory.py) | 保留初始 Task、task updates、工具事务、失败证据、源指纹与预算，不替代原 Trace |
| 所有退出分支如何汇合 | [`StopRequest`](../agent_forge/runtime/application/run_lifecycle.py) | `status + reason + stop_output` 是必需停止契约，候选 final answer 可空 |
| 哪些状态可用于 continuation | [`TaskCheckpoint`](../agent_forge/runtime/domain/task.py) | 保存可见流程状态和 `session_digest`，不保存 Python 栈、HTTP 连接或模型隐藏状态 |

## 按需能力代码索引

这些能力不在每个 Run 中出现，只需记住各自的顶层 Owner。

| 能力 | 顶层 Owner | 下钻条件 |
| --- | --- | --- |
| Skill 选择与激活 | `SkillRegistry.discover_for_task`、`SkillRegistry.activate` | 需要解释激活词、兜底、版本锁定或渐进披露时 |
| 长期记忆 | `LongTermMemoryService.recall`、`RememberMemoryTool.execute` | 需要解释字符预算快照、user provenance、memory_write Ledger 或跨 Run 可见性时 |
| 顺序 Multi-Agent | `MultiAgentCoordinator.run` | 需要解释 Implementer、Reviewer、Verifier 交接时 |
| Fanout 并发与合并 | `LiveFanoutCoordinator.run` | 并发进入 `LiveFanoutCoordinator._run_batch`，合并进入 `LiveFanoutCoordinator._merge_batch` |
| Fanout 恢复与最终验收 | `LiveFanoutCoordinator._checkpoint` | 恢复进入 `LiveFanoutCoordinator._restore_previous`，整体检查进入 `LocalAgentWorkerAdapter.run_finalizer` |
| SWE-bench 单次运行 | `RunSwebench.run_benchmark` | 需要解释 Case、Workspace、Patch 和官方评测产物时 |
| 重复实验 | `RunBenchmarkCampaign.run_campaign` | 需要解释固定输入、实验变体和增量恢复时 |
| 失败分类与 Scorecard | `classify_case_result`、`aggregate_cases` | 需要解释确定性分类、分母和证据等级时 |
| MCP stdio Tool | `MCPStdioClient.discover_tools`、`MCPStdioClient.call_tool` | 需要解释发现远端 Tool 和 JSON-RPC 调用时 |
| 实时操作台 | `OperatorConsoleApp` | 需要检查人工控制界面如何调用正式 Runtime 时 |
| 只读 Workbench | `WorkbenchServices` | 需要检查 Trace、Checkpoint 和评测证据如何展示时 |

## 代码审阅优先级

| 优先级 | 目录 | 阅读原则 |
| --- | --- | --- |
| 核心 | `agent_forge/runtime/application/`、`runtime/domain/`、`context/application/`、`tools/`、`safety/` | 能力的业务编排、状态和治理规则优先从这里进入 |
| 按需 | `multi_agent/application/`、`bench/application/`、`evaluation/`、`skills/` | 只有涉及对应能力时才打开 |
| 边界实现 | `*/adapters/`、`runtime/execution_environment.py` | 需要确认 JSON 持久化、协议或外部执行细节时再下钻 |
| 展示层 | `operator_console/`、`workbench/presentation/` | 用于界面和证据投影，不作为 Runtime 规则的首个入口 |
| 支撑代码 | `agent_forge/cli/`、`scripts/`、`.github/`、安装配置 | 负责参数接入、环境搭建和自动化，不用于理解核心机制 |
| 验证代码 | `tests/`、`examples/debug_lab/` | 在找到 Owner 后，用于核对行为和运行证据，不反向充当机制 Owner |

最小检索规则：**GitHub 中直接点击首个 Owner；PyCharm 中连按两次 `Shift` 搜索它。需要解释行为和异常分支时，
按问题进入[上下文工程](上下文工程.md)、[工具治理与执行](工具治理与执行.md)或
[运行产物与持久化契约](运行产物与持久化契约.md)。**
