# 核心能力与代码入口

本文只回答一个问题：**已经知道能力名称时，第一段应该打开哪段核心代码**。表中的 Owner
是该能力的首个阅读入口，不是所有相关文件的罗列。在 PyCharm 中连按两次 `Shift`，
搜索表中的完整 Owner；结果不唯一时，先进入类，再用 `⌘F` 搜索方法名。

运行规则、失败分支和恢复行为见[核心运行机制与代码索引](核心运行机制与代码索引.md)；模块依赖和
类型契约见[项目架构与代码导航](项目架构与代码导航.md)。本文不重复解释机制正文。

## 最小主链

一次 Single-Agent Run 的最短代码路径由下面八个 Owner 构成。遇到具体能力，再查后续索引。

| 顺序 | Owner | 只负责什么 |
| --- | --- | --- |
| ① | `Harness.run` | 接收公开请求，创建运行产物和执行环境，装配并启动 Runtime |
| ② | `AgentLoop.run` | 编排 Run 准备、Turn、模型、Tool 和唯一终态 |
| ③ | `RunPreparation.prepare_run` | 在首个 Turn 前处理澄清、Skill、Memory 和恢复摘要 |
| ④ | `TurnPreparation.prepare_turn` | 为本轮组装 Context、压缩预算并确定可见 Tool |
| ⑤ | `ModelGateway.chat` | 统一主模型、同 Provider 有界重试、显式备用模型和 Usage |
| ⑥ | `ToolExecutionPipeline._execute_call` | 串起 ToolCall 复核、操作状态、授权、执行和 Observation 提交 |
| ⑦ | `FinalAnswerBuilder.build_stop_request` | 把模型最终输出转换为类型化停止请求 |
| ⑧ | `RunLifecycle.finalize_run` | 统一提交最终状态、停止原因、Trace 和 Checkpoint |

## 核心能力代码索引

| 想查看的能力 | 首个 Owner | 继续下钻 | 代码中应看到的结果 |
| --- | --- | --- | --- |
| 分层指令 | `resolve_instructions` | `RunPreparation.prepare_run` | 按优先级合并指令并记录来源证据 |
| 仓库 Context | `RepositoryContextAssembler.build` | `ContextWindowManager.prepare` | 检索仓库内容，再按完整请求预算压缩 |
| Tool 可见范围 | `ToolRouter.route` | `ToolExecutionPipeline._execute_call` | 先生成本轮可见集合，执行前再次复核 |
| ToolCall 格式修复 | `ToolCallNormalizer.normalize` | `ModelGateway._call_with_retry` | 只修复可确定解析的格式，不猜业务参数 |
| Step、成本、超时和重复调用上限 | `StepController.should_stop` | `StepController.observe_tool_intent_for_repeat_limit` | 由确定性硬上限停止 Run，不依赖模型自行停止 |
| 生命周期处理器 | `HookManager.before_tool` | `HookManager.after_tool` | 执行前汇总规则，执行后依次处理 Observation |
| 权限与人工审批 | `ToolAuthorizationGate.authorize` | `JsonApprovalRepository.request` | 返回继续、拒绝或等待，并持久化待审批事实 |
| 操作防重与崩溃恢复 | `OperationTracker.resolve_existing_operation` | `OperationTracker.record_execution_result` | 复用确定结果、拒绝不确定重试，并提交 executed/failed；当前没有 executing 人工核实结果的写回入口 |
| 参数、命令、路径和环境边界 | `ToolRegistry.execute` | `check_command`、`WorkspaceSandbox`、`ExecutionEnvironment.execute_command` | 获得许可后仍校验参数并限制真实执行范围 |
| 人工补充信息 | `RunLifecycle.request_human_input` | `BuildContinuationPlan.build` | 先保存问题和等待状态，再用回答创建新 Run |
| Pause、Cancel、Steer | `RunControlHandler.consume_pending_signals` | `AgentLoop.run` | 在协作式安全点处理信号，不强杀进行中的调用 |
| Checkpoint | `RunLifecycle.update_checkpoint` | `JsonTaskStateRepository.save` | 保存可恢复状态，不保存 Python 栈或模型隐藏状态 |
| Trace 与可读运行故事 | `JsonTraceRecorder.add` | `project_run_story` | 先追加事实事件，再投影为可读阶段，不提升证据等级 |

## 按需能力代码索引

这些能力不在每个 Run 中出现，只需记住各自的顶层 Owner。

| 能力 | 顶层 Owner | 下钻条件 |
| --- | --- | --- |
| Skill 选择与激活 | `SkillRegistry.discover_for_task`、`SkillRegistry.activate` | 需要解释激活词、兜底、版本锁定或渐进披露时 |
| 长期记忆 | `LongTermMemoryService.recall` | 需要解释作用域、覆盖规则和跨 Run 召回时 |
| 顺序 Multi-Agent | `MultiAgentCoordinator.run` | 需要解释 Implementer、Reviewer、Verifier 交接时 |
| Fanout 并发与合并 | `LiveFanoutCoordinator.run` | 并发进入 `LiveFanoutCoordinator._run_batch`，合并进入 `LiveFanoutCoordinator._merge_batch` |
| Fanout 恢复与最终验收 | `LiveFanoutCoordinator._checkpoint` | 恢复进入 `LiveFanoutCoordinator._restore_previous`，整体检查进入 `LocalAgentWorkerAdapter.run_finalizer` |
| SWE-bench 单次运行 | `RunSwebench.run_benchmark` | 需要解释 Case、Workspace、Patch 和官方评测产物时 |
| 重复实验 | `RunBenchmarkCampaign.run_campaign` | 需要解释固定输入、实验变体和增量恢复时 |
| 失败分类与 Scorecard | `classify_case_result`、`aggregate_cases` | 需要解释确定性分类、分母和证据等级时 |
| MCP stdio Tool | `MCPStdioClient.discover_tools`、`MCPStdioClient.call_tool` | 需要解释发现远端 Tool 和 JSON-RPC 调用时 |
| 实时操作台 | `OperatorConsoleApp` | 需要检查人工控制界面如何调用正式 Runtime 时 |
| 只读 Workbench | `WorkbenchServices` | 需要检查 Trace、Checkpoint 和评测证据如何展示时 |

## 代码审阅优先级

| 优先级 | 目录 | 阅读原则 |
| --- | --- | --- |
| 核心 | `agent_forge/runtime/application/`、`runtime/domain/`、`context/application/`、`tools/`、`safety/` | 能力的业务编排、状态和治理规则优先从这里进入 |
| 按需 | `multi_agent/application/`、`bench/application/`、`evaluation/`、`skills/` | 只有涉及对应能力时才打开 |
| 边界实现 | `*/adapters/`、`runtime/execution_environment.py` | 需要确认 JSON 持久化、协议或外部执行细节时再下钻 |
| 展示层 | `operator_console/`、`workbench/presentation/` | 用于界面和证据投影，不作为 Runtime 规则的首个入口 |
| 支撑代码 | `agent_forge/cli/`、`scripts/`、`.github/`、安装配置 | 负责参数接入、环境搭建和自动化，不用于理解核心机制 |
| 验证代码 | `tests/`、`examples/debug_lab/` | 在找到 Owner 后，用于核对行为和运行证据，不反向充当机制 Owner |

最小检索规则：**连按两次 `Shift` 搜索首个 Owner；只有需要解释行为和异常分支时，才进入
[核心运行机制与代码索引](核心运行机制与代码索引.md)。**
