# 运行产物与持久化契约

本文回答三个问题：一次 Runtime 运行会留下什么，每份文件在什么时候写入，中断恢复时哪份记录才是权威事实。

## 先区分三种对象

| 对象 | 用途 | 能否驱动恢复 |
| --- | --- | --- |
| 控制状态 | 保存 Checkpoint、Approval、Human Input 和 Operation Ledger | 能；它们是恢复和授权的权威来源 |
| 运行产物 | 保存 Trace、请求、配置、候选 Diff、Usage 和 Manifest | 只能按各自声明的边界使用 |
| 导航投影 | 将分散的权威文件按 Run 聚合，供人和 Workbench 快速定位 | 不能；删除后不影响原始事实 |

`Artifact` 是“运行留下的文件”的总称，不等于“恢复状态”。例如 Candidate Diff 是 Artifact，但它不能证明任务已解决；Trace 记录事实，但不代替 Approval 或 Ledger 做恢复决策。

## 演示时从哪里打开

每次 Run 结束时，`publish_runtime_evidence_view` 都会生成下面的可读视图：

```text
.agent_forge/runtime_evidence/
├── README.md
├── INDEX.md
├── latest -> runs/<run-name>__<task-slug>/
└── runs/<run-name>__<task-slug>/
    ├── README.md
    ├── index.json
    ├── 01_checkpoint/
    ├── 02_human_input/
    ├── 03_approval/
    ├── 04_operation_ledger/
    ├── 05_trace/
    └── 06_run_artifacts/
```

- `latest` 始终指向最近一次 Run；`runs/` 保留历史视图。
- 分组中的 JSON 和 Diff 是指向权威文件的软链接，**不是副本**，因此不会产生两份恢复事实。
- `index.json` 是发布当时的目录快照；链接指向的 JSON 才反映后续审批或回答后的最新状态。
- 本次没有触发人工提问或写审批时，对应目录为空是正常事实，不代表文件丢失。
- 导航发布是尽力而为的派生步骤；失败时会写 `latest/runtime_evidence_error.txt`，但不会改写 Agent 的真实结果。

Workbench 走另一条机器发现链：`.agent_forge/latest/run.txt -> 原始 Run 目录 -> FileEvidenceCatalog`。`runtime_evidence/latest` 用于人工浏览，`latest/run.txt` 用于 Workbench 发现；两者都不是状态仓库。

## 权威文件放在哪里

```text
.agent_forge/
├── runs/<run-name>/              # 一次 Run 独有的产物
│   ├── task_state/<run_id>.json
│   ├── trace.json
│   ├── run_request.json / resolved_config.json
│   ├── execution_environment.json
│   ├── candidate_changes.diff / final_answer.txt
│   ├── usage.json / usage_report.md
│   └── run_manifest.json
├── approvals/<operation_key>.json
├── human_input/<request_id>.json
├── operation_ledger/<operation_key>.json
├── memory/<namespace_hash>/<memory_id>.json
├── sessions/<session_id>.json
├── latest/run.txt
└── runtime_evidence/             # 上述文件的派生导航
```

Run 内的 Checkpoint 跟着该次运行走；Approval、Human Input 和 Ledger 放在项目级稳定目录，因为 continuation 会创建新 Run，但仍需读取上一次 Run 留下的人工决定和操作状态。

## 核心控制状态的写入契约

| 文件 | 基数与主键 | 什么时候写 | 更新方式 | 它回答什么 |
| --- | --- | --- | --- | --- |
| `task_state/<run_id>.json` | 每个 Run 一份 | Run 创建时首写；Turn、Tool、HITL 和终态边界更新 | 用完整快照覆盖同一文件，不是每个 Step 新建一份 | 这次 Run 处于什么状态，恢复时定位到哪个 Step |
| `human_input/<request_id>.json` | 每个稳定问题一份 | Agent 提问时写 `pending`；人回答或取消时更新 | 临时文件原子替换，同一 request 覆盖 | 程序在等哪个问题，人给了什么回答 |
| `approvals/<operation_key>.json` | 每个确定操作意图一份 | 权限门返回 `ASK` 时写 `pending`；批准、拒绝或目标漂移时更新 | 状态覆盖同一文件 | 人是否授权“当时目标状态上的这项操作” |
| `operation_ledger/<operation_key>.json` | 每个确定操作意图一份 | 状态变更操作规划、待批、获批、执行前、返回后更新 | 顶层保存最新状态，`history` 保留迁移序列 | 操作究竟未执行、已执行、明确失败，还是结果未知 |

下面的值域聚焦会发生状态迁移的 JSON。请求、配置、Diff 和 Manifest 等终态产物没有这类状态机，边界见后文。

### 状态值域

| 对象 | 状态值域 | 含义与合法路径 |
| --- | --- | --- |
| Checkpoint `status` | `created`、`running`、`waiting_approval`、`waiting_human`、`paused`、`cancelled`、`blocked`、`failed`、`completed` | `created -> running` 后进入一种停止状态；恢复会创建 continuation Run，不会把旧 Run 伪装成从未停止 |
| Human Input `status` | `pending`、`responded`、`cancelled` | `pending -> responded/cancelled`；终态不能再次回答 |
| Approval `status` | `pending`、`approved`、`rejected`、`stale` | `pending -> approved/rejected`；批准后目标漂移时 `approved -> stale` |
| Ledger `status` | `planned`、`pending`、`approved`、`executing`、`executed`、`failed` | 人审路径通常为 `planned -> pending -> approved -> executing -> executed/failed`；自动放行可从 `approved` 开始 |
| Trace 事件 | `success` 只能为 `true/false`；`event_type` 使用受控事件词汇 | Trace 没有独立 run status；`success` 只评价这一条事件，不等于整个 Run 成功 |

两个容易误判的边界：`auto_approved` 只是一条 Trace 投影，不会生成 Approval JSON；人工拒绝保存在 Approval，Ledger 没有 `rejected` 状态，未越过执行边界的记录仍停在 `pending`。

### 打开文件先看哪些字段

```text
Checkpoint  = {run_id, status, current_step, last_tool, stop_reason, context_digest, metadata}
Human Input = {request_id, status, kind, question, choices, answer, response_note, run_id, step}
Approval    = {operation_key, status, tool_name, arguments, operation_fingerprint, decision_note}
Ledger      = {operation_key, status, tool_name, arguments, history, pre_fingerprint, post_fingerprint, observation}
Trace       = {run_id, task, stop_reason, events: [{step, event_type, success, error, ...事件专属字段}], metrics}
```

| 字段 | 类型或值域 | 谁产生、如何理解 | 典型值 |
| --- | --- | --- | --- |
| `current_step` | 大于等于 0 的整数 | `0` 是 Turn Loop 前；`1..N` 是模型轮次。同一轮可多次覆盖 Checkpoint，不等于文件数量 | `6` |
| `stop_reason` | 开放但机器可读的字符串 | 由 `StopRequest` 的具体退出分支写入，不是模型自由摘要 | `final_answer`、`waiting_approval`、`waiting_human`、`pause`、`max_steps`、`pending_tool_call_at_stop` |
| `context_digest` | `{}` 或 `SessionDigest` 对象 | `{}` 表示本次尚未压缩；非空时是有界结构化摘要，不只是哈希，也不包含原始全文 | `source_hash`、`tool_transactions`、`open_failures`、压缩前后 Token 估算 |
| Checkpoint `metadata` | JSON 扩展对象 | 按分支保存恢复定位事实；消费者必须按 key 判断，不能假定每项都存在 | `execution_environment`、`human_thread_id`、`model_capabilities`、`human_input_request_id`、最近十条 `steer_messages` |
| Human Input `kind` | `clarification` 或 `tool_question` | 前者是运行前任务澄清；后者是模型调用 `ask_human` | `tool_question` |
| `choices` / `answer` | 字符串数组 / 字符串 | 空 `choices` 表示自由文本；非空时 `answer` 必须命中一个选项；`pending` 时 answer 为空 | `["继续", "停止"]` / `"继续"` |
| `response_note` | 可为空的自由文本 | 来自人工回答接口的 `note`，用于审计；它不是给模型的答案 | `"由值班工程师确认"` |
| `operation_key` | 24 位十六进制字符串 | 对 `tool_name + arguments 的确定性 JSON + workspace 绝对路径 + action` 做 SHA-256 截断；恢复后 ToolCall id 变了也可命中同一操作 | `0aecbc13ed6e6a0c0f17bfd7` |
| Approval `reason` | 策略生成的字符串 | 权限门创建请求时写入，解释“为什么需要审批”；它不是人的决定 | `"write needs approval"` |
| `decision_note` | 可为空的自由文本 | CLI/API 的人工批准或拒绝附注；Operator Console 默认留空；目标漂移时由 Runtime 写固定原因 | `"已核对 target.py 修改范围"`；或 `"target fingerprint changed after approval request"` |
| `operation_fingerprint` | `kind` 为 `path`、`command` 或 `operation` | `path` 保存解析路径、是否在 workspace、存在性、SHA-256 和大小；`command` 保存命令文本；其余保存参数哈希 | `{"kind":"path","path":"target.py","sha256":"..."}` |
| Ledger `history` | 状态字符串数组 | 按顺序保留状态迁移，相邻相同状态不重复追加；顶层 `status` 是最新值 | `["planned","pending","approved","executing","executed"]` |
| `pre_fingerprint` / `post_fingerprint` | 指纹对象或 `null` | 分别表示执行边界前后目标状态；两者用于识别目标漂移和已执行事实 | 修改同一文件前后的两个不同 SHA-256 |
| Ledger `observation` | 最多 600 字符的字符串 | 真实工具返回后的结果摘要；成功和明确失败都可写，不是模型判断 | `"replaced text once: target.py"` |
| Trace `event_type` | 受控字符串词汇 | 关键值包括 `task_state_checkpoint`、`human_input_requested`、`human_approval`、`operation_ledger`、`tool_call`、`tool_observation`、`run_control`、`run_completed` | `operation_ledger` |
| Trace `duration_ms` | 大于等于 0 的整数 | 当前实现表示距上一 Trace 事件的时间差，不应直接解释成这个业务阶段自身耗时 | `51` |
| Trace `metrics` | 由 events 计算的计数和耗时 | 是派生汇总，不是新的权威事实 | `tool_call_count`、`failed_tool_call_count`、`steps_count`、`trace_event_count` |

下面是同一次 `replace_text` 操作的三个文件视角。为便于阅读，样例省略了时间戳、绝对路径和来源身份字段。

`task_state/<run_id>.json` 回答“Run 停在哪里”：
```json
{
  "status": "waiting_approval",
  "current_step": 6,
  "last_tool": "replace_text",
  "stop_reason": "waiting_approval",
  "resume_hint": "Approve this tool action or rerun with a safer task."
}
```

`approvals/<operation_key>.json` 回答“人是否授权”：
```json
{
  "operation_key": "0aecbc13ed6e6a0c0f17bfd7",
  "status": "approved",
  "tool_name": "replace_text",
  "arguments": {"path": "target.py", "old": "return 1", "new": "return 2"},
  "reason": "write needs approval",
  "operation_fingerprint": {"kind": "path", "path": "target.py", "exists": true, "sha256": "before_sha256"},
  "decision_note": "已核对 target.py 修改范围，同意执行"
}
```

`decision_note` 只提供人工审计说明，不参与是否放行的计算；真正控制执行的是 `status`。Operator Console 未填写说明时它是空字符串；目标漂移时 Runtime 会把状态改为 `stale`，并自动写入漂移原因。

`operation_ledger/<operation_key>.json` 回答“机器实际执行到哪里”：
```json
{
  "operation_key": "0aecbc13ed6e6a0c0f17bfd7",
  "status": "executed",
  "history": ["planned", "pending", "approved", "executing", "executed"],
  "pre_fingerprint": {"kind": "path", "path": "target.py", "sha256": "before_sha256"},
  "post_fingerprint": {"kind": "path", "path": "target.py", "sha256": "after_sha256"},
  "observation": "replaced text once: target.py"
}
```

`TraceEvent.data` 是代码中的类型化 payload 入参，序列化后会平铺到事件 envelope；因此 JSON 中不会再套一层名为 `data` 的对象。例如：

```json
{
  "step": 6,
  "event_type": "operation_ledger",
  "success": true,
  "error": "",
  "operation_key": "0aecbc13ed6e6a0c0f17bfd7",
  "operation_status": "executed",
  "operation": {"status": "executed", "history": ["planned", "approved", "executing", "executed"]}
}
```

Checkpoint 不保存完整消息列表、每次 Tool 输出原文、Python 栈或模型 KV Cache。恢复的是有限业务状态，不是还原已退出的进程内存。`context_digest.source_hash` 只用于追溯被压缩原文，不能还原原文。

Approval 和 Ledger 使用同一个 `operation_key`，但职责不同：

```text
operation_key = hash(tool_name + deterministic_arguments + resolved_workspace + action)
fingerprint   = 执行目标当前状态，例如文件路径 + SHA-256
Approval      = 人允不允许
Ledger        = 机器实际执行到哪一步
```

同一 `operation_key` 在 continuation 中可能再次出现，所以 Approval 不是“创建后永远不变”：`pending -> approved/rejected`，而已批准后如果 fingerprint 漂移，还会变成 `stale`。

## 一次审批写操作如何落盘

```text
模型提出 replace_text
  -> 计算 operation key 和执行前 fingerprint
  -> Ledger = planned
  -> 权限门返回 ASK
  -> Approval = pending
  -> Ledger = pending
  -> Checkpoint = WAITING_APPROVAL
  -> 当前 Run 结束
  -> 人批准，覆盖 Approval = approved
  -> continuation 加载 Checkpoint
  -> 模型再次提出同一操作
  -> 重算 operation key 和 fingerprint
  -> key 相同且目标未漂移，复用批准
  -> Ledger = approved -> executing
  -> ToolGateway 真实执行
  -> Ledger = executed/failed，保存执行后 fingerprint
  -> 新 Run 的 Checkpoint 保持 RUNNING 或进入终态；旧 Run 仍保留等待事实
```

`executing` 在真实状态变更之前写入。如果进程此后崩溃，Runtime 只知道“可能已执行”，因而 fail closed，不会把它猜成“未执行”并自动重放。

## 终态 Run 产物

| 产物 | 写入时机 | 证据边界 |
| --- | --- | --- |
| `run_request.json` / `resolved_config.json` | AgentLoop 启动前 | 保存脱敏请求与实际配置，用于复现运行条件 |
| `final_answer.txt` | AgentLoop 返回后 | 模型终态文本，不是正确性证明 |
| `candidate_changes.diff` | AgentLoop 返回后，从隔离工作区读取 | 只证明产生了候选改动 |
| `trace.json` | Runtime 终态收口时 | 事件先追加到内存列表，终态时整体写成 JSON，不是中途崩溃恢复日志 |
| `usage.json` / `usage_report.md` | `trace.json` 发布后 | 由 Trace 派生的 Token、成本和调用汇总，不是独立事实源 |
| `execution_environment.json` | 执行环境清理前 | 记录 workspace、隔离和网络边界 |
| `run_manifest.json` | 最后写入；后续新增恢复链时可刷新 | 列出实际存在的产物、Owner 和声明边界 |
| `resume_link.json` / `resume_chain.md` | 只有 continuation 创建后 | 说明新旧 Run 的关联，不代替 Checkpoint |

Trace 采用“运行中内存追加，终态整体写文件”；Ledger 采用“每项操作一份 JSON，最新状态 + history”。前者适合完整审计，后者适合恢复时快速查询一项操作。

## 项目级记录

- `sessions/<session_id>.json`：每个可读会话一份，变更标题、置顶、归档或 Run 索引时原子覆盖。`archived/pinned` 为布尔值，`runs[].relationship` 为 `initial/continuation/follow_up`，Run 的 `status` 复用 Checkpoint 值域。它类似“任务目录表”，只引用 Run，不复制 Trace 或 Checkpoint。
- `memory/<namespace_hash>/<memory_id>.json`：每条显式长期记忆一份，更新时原子覆盖，`forget` 时删除。`scope` 为 `user/project`，`source` 固定为 `user_explicit`，`status` 当前只允许 `active`，`revision` 从 1 递增。它是跨 Run 上下文，不是某次 Run 的恢复文件。

## 恢复和排障时谁说了算

| 问题 | 权威来源 |
| --- | --- |
| 这次 Run 停在哪里？ | Checkpoint |
| 人是否批准这项操作？ | Approval |
| 状态变更操作是否已经执行？ | Operation Ledger + fingerprint |
| Agent 在等哪个问题的回答？ | Human Input |
| 运行中实际发生了什么？ | Trace |
| 这个 Run 生成了哪些文件？ | Run Manifest |
| Workbench 应打开哪个 Run？ | `.agent_forge/latest/run.txt` |
| 候选改动是否解决了基准 Case？ | 独立 Evaluator 的结果，不是上述 Runtime 文件 |
