# 运行产物与持久化契约

> 核心问题：
> **Agent 运行过程中产生了很多“状态”，到底谁是恢复真相，谁只是日志，谁只是展示？**

---

# 1. 先按职责分，不按目录分

```text
Durable Runtime State
├── TaskCheckpoint
├── HumanInput
├── Approval
├── Operation Ledger
└── Long-term Memory

Append-only Evidence
└── trace.jsonl

Derived Projection
├── trace.json
├── usage.json
├── reports
└── Workbench views

Candidate / Result Artifacts
├── candidate_changes.diff
├── stop_output.txt
└── final_answer.txt
```

---

# 2. `.agent_forge` 顶层

```text
.agent_forge/
├── runs/       当前原生 Run 证据
├── internal/   控制状态 / 索引 / cache
└── archive/    历史归档
```

不要把：

```text
run artifacts
workspace
worktree
```

混在一起。

---

# 3. TaskCheckpoint 只是一份 latest-state snapshot

目标语义：

```text
TaskCheckpoint

Identity
├ run_id
├ task
├ workspace
└ agent_name

Execution Snapshot
├ status
├ current_step
├ last_tool
├ last_observation
├ stop_reason
├ stop_output
├ final_answer
├ resume_hint
├ messages_count
└ observations_count

Historical Projection
└ conversation_history_digest

Extension
└ metadata
```

Checkpoint 不保存：

```text
Python stack
HTTP connection
完整 session.messages
模型 hidden state
```

---

# 4. ConversationHistoryDigest 在 Checkpoint 里是什么角色

它是：

> 旧 Conversation History 的有界历史投影。

不是：

```text
整个 AgentRunSession 的 dump
整个 Current Turn System Context
完整 Conversation
```

只有发生 Conversation compaction 时才更新。

没有新 compaction：

```text
checkpoint 保留上一次 digest
```

---

# 5. Resume 的真实语义

```text
Old TaskCheckpoint
↓
summarize_checkpoint
↓
resume_summary
↓
NEW AgentRunSession
↓
WorkingMemory.seed_session
```

所以：

```text
Resume
= new continuation run

Resume
≠ live session resurrection
```

---

# 6. Checkpoint、Trace、Ledger 为什么不能互相替代

## Checkpoint 状态快照

```text
回答：现在处于什么状态？
```

mutable latest state。

## Trace 事件证据

```text
回答：实际发生过什么？
```

append-only event history。

## Operation Ledger 副作用状态

```text
回答：这个副作用执行到哪？
```

side-effect-specific durable state。

例：

```text
Checkpoint.status = BLOCKED
Trace = operation_outcome_unknown event
Ledger.status = executing
```

三者共同解释一次 crash，不应该合并成一个 JSON。

---

# 7. HumanInput / Approval / Ledger 各自是谁的 authority

```text
HumanInput
→ 用户问题和回答

Approval
→ 操作是否被授权

Operation Ledger
→ 操作执行状态
```

等待和恢复前必须先 durable。

---

# 8. 一次正常 Run 的典型 artifact

```text
runs/<run-id>/
├── run_request.json
├── run_manifest.json
├── trace.jsonl
├── trace.json
├── usage.json
├── task_state/
├── candidate_changes.diff
├── stop_output.txt
├── final_answer.txt
└── execution_environment.json
```

Fanout / Benchmark 可以增加自己的子目录，但不要维护第二份人工复制的“展示真相”。

---

# 9. Evidence Schema Migration 原则

如果只是把错误语义名：

```text
session_digest
```

修正成：

```text
conversation_history_digest
```

这是 persisted contract change。

正确做法：

```text
new canonical schema
+
明确 migration manifest
+
old hash → new hash mapping
+
只迁移当前系统仍消费的 canonical evidence
+
archive 保持原始历史
```

不能：

```text
悄悄改 JSON
然后继续声称 hash / provenance 没变
```

---

# 10. Workbench 的边界

Workbench：

```text
读取 immutable / canonical evidence
↓
投影成可读 review
```

它不应该：

```text
修改 Run
补写缺失事实
为了展示重新跑实验
猜测没有观测到的状态
```

所以技术展示时，看到的是：

```text
Design Contract
vs
Observed Artifact
```

---

# 11. 现场追 Crash/Resume 看什么

最小顺序：

```text
① TaskCheckpoint
   当前 status / step / resume_hint

② Operation Ledger
   副作用是否 known / unknown

③ Trace
   事件顺序

④ HumanInput / Approval
   是否存在未消费的 durable decision

⑤ Workspace / candidate diff
   当前物理代码状态
```

这比从 `trace.json` 一路猜状态可靠。
