# 运行产物与持久化契约

[← 架构导览](./架构导览.md#durability)

NanoHarness 的本地数据只分三层。无需在 `.agent_forge` 顶层寻找十几个功能目录：

```text
.agent_forge/
├── runs/       # 当前原生运行结果；调试时从这里打开
├── internal/   # 平台状态、索引、缓存与机械生成文件
└── archive/    # 历史实验、旧 Run 和临时材料
```

`runs/` 是唯一的运行证据入口。系统不创建分类软链接或第二份人工展示树。

## 一次 Run 在哪里

普通 Single-Agent、Multi-Agent 和 Benchmark 都把事实直接写进自己的 Run 目录：

```text
.agent_forge/runs/<run-id>/
├── run_request.json             # 脱敏后的输入与 Runtime 配置
├── run_manifest.json            # 本次 Run 的 artifact 清单与哈希
├── trace.jsonl                  # Run 中逐条 flush 的 append-only 事实
├── trace.json                   # 从 trace.jsonl 生成的可读投影
├── usage.json                   # Token、成本与调用计数
├── usage_report.md              # usage 的可读投影
├── task_state/                  # 本次 Run 的 checkpoint
├── candidate_changes.diff       # 候选代码改动
├── stop_output.txt              # 每次 Run 停止时返回的文本
├── final_answer.txt             # 仅 accepted COMPLETED 时存在
└── execution_environment.json   # 隔离环境与代码快照身份
```

不同运行类型可以多出 `cases/`、`predictions.jsonl`、`scorecard.json`、`results.json`、
`fanout/` 或 `multi_agent/`，但仍在同一个原生 Run 内，不会复制到别处。

先按“谁能改、谁能重建”区分 artifact，不要把同一目录中的文件都当成同一种事实：

| 类别 | 代表文件 | 权威边界 |
| --- | --- | --- |
| 不可变输入快照 | `run_request.json`、`execution_environment.json` | 说明本次运行接收什么以及在哪个代码/环境身份上执行 |
| 可变恢复真相 | Checkpoint、Human Input、Approval、Operation Ledger、Memory | Runtime 恢复与授权的 authoritative state；必须原子替换 |
| 只追加运行事实 | `trace.jsonl` | 事件 journal 的 source of truth；不回写、不代替 Checkpoint |
| 可重建投影 | `trace.json`、`usage.json`、`usage_report.md`、报告 | 只从 journal 确定性生成，丢失时应重建而非反向改事实 |
| 停止与候选产物 | `stop_output.txt`、`final_answer.txt`、`candidate_changes.diff` | 结束时发布；final answer 仍受 completion gate 和证据等级约束 |
| 身份与清单 | `run_manifest.json` | 记录应存在的 artifact 及哈希，不承担业务状态转换 |

最近一次 Run 的轻量指针位于：

```text
.agent_forge/internal/index/run.txt
```

它只帮助 CLI 与 Workbench 找到原生目录，不是运行证据。直接查看最近一次运行可用：

```bash
.venv/bin/forge inspect latest
```

## 控制动作对应哪个 JSON

固定目录会在 Runtime 启动时预建，便于在交互调试中观察状态变化：

| 动作或状态 | 权威文件 | 观察重点 |
| --- | --- | --- |
| pause / stop / resume | `runs/<run-id>/task_state/<run-id>.json` | `status`、`stop_reason`、`resume_hint`、step 与 metadata |
| 模型向人提问 | `internal/state/human_input/<request-id>.json` | `pending → responded/cancelled`、answer、run_id |
| 写操作等待审批 | `internal/state/approvals/<operation-key>.json` | `pending → approved/rejected/stale`、目标与指纹 |
| 写操作执行与恢复 | `internal/state/operation_ledger/<operation-key>.json` | `planned → executing → executed/failed`、pre/post fingerprint |
| 长期记忆 | `~/.agent_forge/memory/<namespace>/<memory-id>.json` | 内容、来源、可见性与更新时间；跨 Run、跨 Project 的 machine-local 状态 |
| Operator 会话目录 | `internal/state/sessions/` | 会话与多个 continuation Run 的关联 |

Checkpoint 属于具体 Run，所以保留在 `runs/<run-id>/task_state/`；审批、人工输入和 Operation Ledger
属于项目控制面，放在 `internal/state/`。Long-Term Memory 跨 Project，只有一个 machine-local
`~/.agent_forge/memory/`；项目内不再保留第二个 Memory Store。
预置 Lab 1 为了让一次交互自包含，会显式把这三类控制根绑定到同一个原生 Run：

```text
.agent_forge/runs/showcases/<lab1-run>/
├── human_input/<request-id>.json
├── approvals/<operation-key>.json
├── operation_ledger/<operation-key>.json
└── phases/<phase-run>/task_state/<run-id>.json
```

这些仍是 Runtime 直接读写的权威文件，不是二次整理的展示数据。

### 现场观察时的状态值域

- Checkpoint `status`：`created`、`running`、`waiting_approval`、`waiting_human`、`paused`、`cancelled`、`blocked`、`failed`、`completed`。
- Human Input `status`：`pending`、`responded`、`cancelled`；终态不能再次回答。
- Approval `status`：`pending`、`approved`、`rejected`、`stale`；目标指纹变化会使旧授权失效。
- Ledger `status`：`planned`、`pending`、`approved`、`executing`、`executed`、`failed`；`history` 保留迁移顺序。

Approval 中的 `decision_note` 只提供人工审计说明，不参与放行计算；Operator Console 未填写说明时它是空字符串。
Trace 中的 `TraceEvent.data` 是类型化 payload，序列化后会平铺到事件 envelope，所以 JSON 中不会再套一层 `data`。

## Schema v2 与停止输出

`task_state/*.json`、`trace.jsonl` / `trace.json`、`run_manifest.json` 和单条 Memory JSON 是被 loader
直接读取的 canonical artifact，使用 `schema_version=2`。内部 `StopRequest`、Trace Event 或普通 dataclass
不机械携带版本。v2 的关键语义是：

- `stop_output` 在 completed、waiting、paused、blocked、failed 等每种 Run stop 都存在；
- `final_answer` 只表示 completion gate 接受的真实模型回答，否则是 `null` 且没有 `final_answer.txt`；
- checkpoint 的 `session_digest` 是旧 Conversation History 投影，不是整个 Runtime Context 的摘要。

生产 loader 只读取 v2，不保留旧字段 alias 或 fallback。仍被当前 CLI、Workbench、fixture 与实验索引消费的
数据做一次迁移；已经退出当前系统边界的 raw archive 保持不可变历史格式。准确范围、已更新输入和
未转换归档记录在 [Runtime schema v2 migration manifest](../migrations/runtime-schema-v2-manifest.json)。

## 崩溃与落盘边界

Checkpoint、Human Input、Approval、Operation Ledger 与 Long-Term Memory 共用单文件写入顺序：同目录临时文件
→ `flush` → `fsync(temp)` → `replace` → `fsync(parent)` → 清理临时文件。它保证单 JSON 文件要么是旧完整值，
要么是新完整值，不声称跨文件 ACID。

每个 Run 只有一个 `trace.jsonl` writer；每个 event 独占一行并立即 `flush`，因此属于 process-crash durable，
但不宣称每条 event 都经磁盘 `fsync`。读取时只可忽略并报告 crash 截断的最后一行，中间损坏必须失败。
终止时 `trace.json`、`usage.json` 与报告都从该 journal 投影，Checkpoint 仍是 authoritative mutable state。

## 当前验证与恢复边界

- 已用自动化测试覆盖 atomic replace、末行截断、中间损坏失败和投影；还没有专门的真实 `kill -9` 注入实验。
- Trace 不做逐 event `fsync`，当前也没有独立的 orphan `trace.jsonl` 恢复 CLI；项目只宣称上述 process-crash durability。
- 当异常发生在 `Harness.run` 的环境/依赖装配阶段、尚未进入 `AgentLoop` 和 `RunLifecycle` 时，当前可写 failed manifest，
  但不保证生成 `stop_output.txt`。“每次 Run stop 有 stop_output”的契约边界是已进入 Runtime 统一停止链的 Run，本轮不扩展为 bootstrap 异常修复。
- v2 重构的快速验证不包含新的真实 Provider 付费 smoke run；运行语义与外部 Provider 端到端稳定性是两个证据等级。

## `internal/` 里还有什么

```text
.agent_forge/internal/
├── state/               # 上表中的持久化控制状态
├── index/               # latest run / benchmark / campaign 指针
├── cache/
│   ├── bench/repos/     # SWE-bench repository cache
│   └── worktrees/       # 隔离 worktree
├── generated/
│   ├── case-inspections/# 只读 SWE-bench Case 展开结果
│   └── evaluation/      # 机械导出的评测数据
└── debug-lab/           # Lab workspace、工具与 Workbench 进程状态
```

这些文件支撑运行，但不是默认阅读入口。需要验证审批、恢复或工具边界时才下钻 `state/`；
缓存、索引和机械输出不应被当作质量结论。

## Benchmark 结果

新评测同样落在 `runs/`：

```text
.agent_forge/runs/benchmarks/<benchmark-name>/<run-id>/
.agent_forge/runs/experiments/<experiment>/<variant>/<run-id>/
.agent_forge/runs/campaigns/<campaign-id>/
```

其中 `results.json` 是运行状态与逐 Case 结果，`scorecard.json` 是指标投影，
`predictions.jsonl` 是提交给 SWE-bench evaluator 的 Patch，official evaluator 产物决定
`resolved / unresolved`。Candidate Diff 或本地测试通过不能替代 official result。

## 历史归档

`.agent_forge/archive/` 只保留旧实验、旧 Run 和临时产物，避免干扰当前调试：

```text
.agent_forge/archive/
├── experiments/
├── runs/
├── demos/
└── temporary/
```

归档不会被当前 Runtime 自动选择，也不是新实验的输出目标。需要复盘旧实验时，再通过
`benchmarks/experiments/*/*.execution.json` 中保存的路径和 SHA 定位原始文件。
归档 raw run 可以保留历史 schema；这不是生产兼容合同，Runtime loader 不进入 `archive/`。

## 必须保持的不变量

- 一次 Run 只写一份原生 artifact，不维护人工重排副本。
- `run_manifest.json` 记录 artifact 身份；Workbench 只读取，不改变事实。
- pause、approval、human input 与 operation 状态必须先持久化，之后才能 continuation。
- 相同 operation key 的恢复必须检查 run identity 与 fingerprint，不能盲目重放副作用。
- Benchmark 的 planned denominator、空 Patch、infra failure 和 official outcome 都必须保留。
- `archive/` 只承接历史，不参与当前结果发现。
