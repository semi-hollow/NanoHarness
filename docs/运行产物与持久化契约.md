# 运行产物与持久化契约

> 持久化层必须区分“恢复时可以相信的当前状态”“实际发生过的事件证据”和“由证据
> 生成的展示”。三者不能互相替代。

# 1. 三类持久化对象

```text
Authoritative Mutable State
├── TaskCheckpoint
├── HumanInput
├── Approval
├── Operation Ledger
└── Long-term Memory

Append-only Evidence
└── trace.jsonl

Derived Presentation
├── trace.json
├── usage.json
├── reports
└── Workbench views
```

Candidate artifacts（如 `candidate_changes.diff`）是本次执行的结果对象，也不是
mutable control state。

# 2. 写入者与读取者（Writer / Reader）

| Artifact | Canonical Writer | 主要 Reader | 决定什么 |
|---|---|---|---|
| `TaskCheckpoint` | `RunLifecycle` → `TaskStateRepository` | continuation、operator control | 当前 Run 状态与恢复提示 |
| HumanInput | `RunLifecycle.request_human_input()` | continuation | 问题是否已有回答 |
| Approval | `ToolAuthorizationGate` | Tool authorization | 具体 operation 是否获准 |
| Operation Ledger | `OperationTracker` | Tool replay/recovery | 副作用执行到哪一步 |
| Long-term Memory JSON v3 | `LongTermMemoryService` | 新 Run 的 recall/catalog | ID-based、带 user provenance 的跨 Run 显式记忆 |
| `trace.jsonl` | `JsonTraceRecorder` | projection / audit | happened-before 事件证据 |
| `trace.json` / `usage.json` | projection writers | reports / Workbench | 可读聚合，不控制 Runtime |

# 3. TaskCheckpoint 只是一份 latest-state snapshot

```text
TaskCheckpoint
├── Identity
│   ├── run_id / task / workspace / agent_name
├── Execution Snapshot
│   ├── status / current_step
│   ├── last_tool / last_observation
│   ├── stop_reason / stop_output / final_answer
│   ├── resume_hint
│   └── messages_count / observations_count
Historical Projection
└ conversation_history_digest
```

Checkpoint 不保存 Python stack、HTTP connection、完整 `AgentRunSession.messages` 或
模型 hidden state。`conversation_history_digest` 在实际 Conversation compaction 后更新，
未产生新 delta 时复用已有投影。current-session compaction cursor 不持久化。

# 4. 继续执行（Resume）

```text
Old TaskCheckpoint
├── summarize_checkpoint() → WorkingMemory continuation seed
└── conversation_history_digest
          ↓ ConversationHistoryDigest.from_dict()
   NEW AgentRunSession digest + cursor=0
```

```text
Resume
= new continuation run
```

它不是旧 Session resurrection。新的 Run 拥有新的 run identity、Session、Provider 调用
和事件序列，只继承显式持久化事实；下一次 compaction 将 restored digest 与新 Session
raw delta 合并。

# 5. 三个权威边界

## Checkpoint 状态

```text
回答：现在处于什么状态？
```

## Trace 事件证据

```text
回答：实际发生过什么？
```

Trace 保存 durable execution evidence，不是完整 raw Conversation store。当前进程 raw
Conversation 的 Owner 是 `AgentRunSession.messages`；进程退出后可恢复的是 checkpoint
中的有界 digest 与控制事实。

## Operation Ledger 副作用状态

```text
回答：这个副作用执行到哪？
```

例如 crash 时可能同时出现：

```text
Checkpoint.status = BLOCKED
Trace = operation_outcome_unknown
Ledger.status = executing
```

`executing` 表示外部状态可能已经改变但最终结果未知，不能依据 checkpoint 或缺失
Observation 自动重放。

# 6. Run 产物

```text
runs/<run-id>/
├── run_request.json
├── run_manifest.json
├── trace.jsonl
├── trace.json
├── usage.json
├── task_state/
├── candidate_changes.diff
├── stop_output.txt
├── final_answer.txt                accepted COMPLETED only
└── execution_environment.json
```

`stop_output.txt` 在 AgentLoop 产生 typed stop 后写入；`final_answer.txt` 只在
checkpoint 中存在 accepted `final_answer` 时生成。异常发生在 typed stop 之前时，
最终状态由已写入的 control state、trace 与 manifest 共同说明，不能伪造 final text。

# 7. 写入耐久性

Authoritative mutable state 使用强原子写入：

```text
same-directory temp
→ flush
→ fsync(temp)
→ replace
→ fsync(parent)
→ cleanup temp
```

`trace.jsonl` 每 Run 单 writer、每 event 一行并 flush。最后一条 crash-truncated line
可被 reader 忽略并报告，中间损坏必须失败；最终 `trace.json`、usage 和报告由它投影。

# 8. Schema 迁移

Canonical persisted contract 发生命名或结构变化时：

```text
new canonical schema
+ one-time deterministic migration
+ migration manifest
+ old hash → new hash mapping
+ only current reader closure
+ archive 保持原始历史
```

生产 loader 只读取新 canonical schema，不永久保留多套 alias；migration 也不能改写
模型输出、Tool Observation、执行顺序、usage、timestamp 或业务结论。

# 9. Workbench 边界

```text
canonical evidence
→ deterministic projection
→ Workbench
```

Workbench 只读已有证据，不修改 Run、不补写缺失事实、不为展示重新执行任务。它呈现：

```text
Design Contract
vs
Observed Artifact
```

# 10. 恢复检查顺序

```text
TaskCheckpoint
→ Operation Ledger
→ trace.jsonl
→ HumanInput / Approval
→ workspace / candidate diff
```

先确定 authoritative mutable state，再用 append-only evidence 解释过程，最后查看物理
workspace 结果。
