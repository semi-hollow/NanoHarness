# 运行治理与副作用

本文聚焦：

```text
为什么 Model ToolCall 不能直接执行？
副作用怎样做授权、幂等和 crash recovery？
中断后怎样继续原 assistant Tool batch？
```

> Run Governance 的核心是：**模型只拥有 ToolCall proposal；Runtime 在真实副作用发生前重新建立操作身份、恢复语义和授权，在副作用发生后把结果提交成 durable fact。**

# 1. 总体主链

```text
Model ToolCall
      ↓
Runtime Governance
      ↓
Authorized Side Effect
      ↓
Durable Observation
```

Runtime Governance 内部按固定顺序：

```text
Route / Guardrail
→ Special protocol / provenance
→ Build OperationIntent
→ Ledger replay / crash idempotency
→ Repeat guard
→ Authorization
→ Execute + durable result
```

只有最后阶段可以真正进入 `ToolGateway`。

# 2. Durable Tool Batch

模型一次 response 可以返回多个 ToolCall：

```text
Assistant Message
├── ToolCall 0
├── ToolCall 1
├── ToolCall 2
└── ToolCall 3
```

Runtime 在任何 Tool 真实执行之前，先把**完整 assistant batch**持久化。

同时 Checkpoint 只保存：

```text
assistant batch pointer
+ next ToolCall index
```

因此：

```text
模型提出了什么
≠
其中哪些已经执行
```

# 3. Route / Guardrail

当前调用先验证：

```text
Tool registered
AND
ToolCall.name ∈ allowed_tool_names
```

这里解决：

```text
当前 Model Step 有没有把这个 capability 暴露给模型？
```

而不是：

```text
这个具体副作用是否最终获准？
```

所以：

```text
visibility
≠
authorization
```

# 4. Special Protocol / Provenance

## `ask_human`

```text
ToolCall
→ durable HumanInputRequest
→ waiting_human
```

它是可恢复人工屏障，不按普通 Tool 执行。

## `remember_memory`

Memory mutation 先验证真实人类 provenance：

```text
source_quote
→ current Turn human-authority ConversationItem
```

模型不能通过自己的输出给自己制造长期记忆写权限。

# 5. Build `OperationIntent`

普通调用统一进入：

```text
ToolCall
name + arguments
        ↓
OperationTracker.build_operation_intent()
        ↓
OperationIntent
```

`OperationIntent` 提供：

```text
action
target
side_effect
ledger_tracked
operation_key
pre_execution_fingerprint
```

它只做统一解释，不负责：

```text
Approval
Ledger decision
Tool execution
```

三个相邻 Owner 共用同一份操作事实：

```text
OperationTracker
→ replay / idempotency

ToolAuthorizationGate
→ permission / Approval

_run_tool
→ real execution
```

# 6. Operation Identity 与 Fingerprint

```text
operation_key
= 这是哪个 operation

fingerprint
= 当前 target 是什么状态
```

例如 `write_file(auth.py)`：

```text
pre-fingerprint
= 写前 auth.py 状态

post-fingerprint
= 写后 auth.py 状态
```

Fingerprint 服务两条治理链：

```text
Approval freshness
approved pre-fingerprint
vs current pre-fingerprint

Ledger replay
previous post-fingerprint
vs current pre-fingerprint
```

所以它既防批准后的 TOCTOU 漂移，也参与 crash/replay 判断。

# 7. Ledger Replay / Crash Idempotency

对需要跨 crash 治理的副作用：

```text
write
memory_write
run_command
```

Operation Ledger 维护：

```text
planned / pending
→ approved
→ executing
→ executed | failed
```

恢复策略：

| Durable state | Runtime 行为 |
|---|---|
| 无旧记录 | 继续正常治理 |
| `executed` 且 target fresh | 复用旧执行事实，不再次 ToolGateway |
| `executing` 但无 final result | outcome unknown，fail closed |
| 旧执行事实与当前 target 不一致 | stale，拒绝自动复用 |

Ledger 的价值不是日志，而是：

> **判断副作用是否可以安全重放。**

`run_command` 的 operation identity 绑定 canonical ToolCall invocation，因此同一个 crash-resumed invocation 不重跑，而新 Model Step 新提出的相同 command 仍可以执行。

# 8. Repeat Guard

Repeat Guard 解决：

```text
模型是否连续重复没有进展的调用？
```

它与 Ledger 不同：

```text
Ledger
= durable side-effect replay

Repeat Guard
= model no-progress loop
```

无副作用调用可以更轻量地跳过；可能改变持久状态的重复调用更保守。

# 9. Authorization

`ToolAuthorizationGate.authorize()` 汇合：

```text
Hook / policy
+ OperationIntent
+ Approval state
+ current fingerprint
```

输出：

```text
ALLOW
DENY
ASK
```

ASK：

```text
create / read durable ApprovalRequest
→ waiting_approval
```

重要边界：

> **Authorization 只给治理结论，不执行 Tool。**

只有 `proceed=true` 才进入真实执行。

# 10. Execute + Durable Result

真实副作用链：

```text
final control check
→ OperationRecord = executing
→ ToolGateway.execute()
→ after-tool processing
→ post-fingerprint
→ OperationRecord = executed / failed
→ durable Tool Observation
→ caller advances pending cursor
```

两个关键顺序：

```text
executing
必须在真实 side effect 前 durable

Tool Observation
必须在 cursor advance 前 durable
```

这样 crash 后才能区分：

```text
可能已执行但结果未知
vs
结果已落盘但 cursor 尚未推进
```

# 11. Human Authority

三种人类交互作用不同：

```text
Approval
= 是否允许一个具体 operation

Human Input
= 回答模型明确提出的问题

Steer / clarification
= 更新当前 Turn 的人类约束
```

真实用户内容进入 Conversation 时使用：

```text
human_authority=true
```

Provider 的 `role=user` 只是协议角色，不能替代 Runtime authority。

# 12. 核心不变量

```text
1. Tool visibility != authorization
2. Model ToolCall != real side effect
3. OperationIntent 是统一操作事实，不是执行器
4. executing outcome unknown 时不能自动重放
5. Approval 与 target fingerprint 绑定
6. Observation durable 后才推进 Tool batch cursor
7. 一个 ToolCall 最终必须闭合成唯一合法 Observation
```

# 13. 附录：4 ToolCall + Approval + Resume

```text
Assistant batch
0 read_file
1 write_file
2 python_validation
3 git_diff
```

Run A：

```text
Tool 0
→ execute
→ Observation durable
→ cursor 0 → 1

Tool 1
→ OperationIntent
→ Ledger pending
→ Approval pending
→ Run waiting_approval
→ cursor stays 1
```

用户批准后，Same-Turn Run B：

```text
restore pending assistant item
→ restore original ToolCalls
→ start from index 1

write_file
→ rebuild OperationIntent
→ Ledger / Approval / fingerprint re-check
→ executing
→ real write
→ executed
→ Observation durable
→ cursor 1 → 2

then validation
then git_diff
→ clear pending_execution
```

两个 Crash Window：

```text
Observation 已写，cursor 未推进
→ Resume 发现 Observation 已存在
→ 不执行 Tool，只推进 cursor

Ledger 已写 executing，结果未知
→ 不能判断副作用是否已发生
→ fail closed
```
