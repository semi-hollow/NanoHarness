# 功能冻结后的 Runtime 质量实验

> 这是 Runtime 质量优化的唯一入口：实验设计、真实结果、证据边界和设计复盘都在这里。

## 1. 要回答的问题

Debug Lab 证明 HITL、Checkpoint、Sandbox、Ledger 和多 Agent 等功能确实存在；本实验回答
另一个问题：**功能冻结后，Runtime 能否根据失败证据提高收敛质量和效率？**

这里不与开源 Agent 刷榜，也不把新增 Feature 算作优化。采纳顺序固定为：

1. 保住已知正确结果，安全边界不得退化；
2. 减少无 Patch 退出和失败工具调用；
3. 再比较 Token、成本和模型调用次数；
4. 新 Patch 未经官方评测时，不得记为 solved。

## 2. 实验协议

| 项目 | 固定值 |
| --- | --- |
| 数据 | SWE-bench Verified `test`，revision `c104f840cc67f8b6eec6f759ebc8b2693d585d4a` |
| 样本 | Golden-10 v1，覆盖 6 个仓库 |
| 模型 | `deepseek-v4-flash`，temperature 0，Thinking enabled，reasoning high |
| Runtime | 同一 AgentLoop、Tool、Skill、Memory、安全策略和 worktree 环境 |
| 资源 | `max_steps=32`，每轮最多 4 个 ToolCall，单题估算成本上限 `$0.05` |
| 重复 | 每个版本每题 1 次；用于开发期决策，不声称统计显著性 |
| 候选变量 | Context 压缩触发阈值 |

Golden-10 是开发样本，不是排行榜样本：

| 路径 | Case | 选择原因 |
| --- | --- | --- |
| 正向锚点 | `django__django-11451` | 已有 official resolved，可检测正确性回归 |
| 跨仓库正向路径 | `matplotlib__matplotlib-13989` | 检查相同候选改动能否稳定复现 |
| 失败工具恢复 | `scikit-learn__scikit-learn-14629` | 历史触发连续失败熔断 |
| 长链收敛 | `django__django-12209`、`sphinx-doc__sphinx-10323` | 历史在检索或验证阶段停止 |
| 大仓库 Context | `sympy__sympy-20590` | 可检测压缩造成的语义退化 |
| 错误或未裁决 Patch | `django__django-10097`、`psf__requests-2317` | 区分有 Patch 和真正解决 |
| 预算敏感 | `matplotlib__matplotlib-22871`、`django__django-13028` | 检查同预算下能否形成候选改动 |

每个候选版本先跑 Sentinel-4：`django-11451`、`django-13028`、`matplotlib-22871`、
`sympy-20590`。出现正确性或语义回归就拒绝，不补跑剩余六题。最多两轮候选优化，防止
为了数字继续堆逻辑。

测量链路修复单独记录，不冒充 Runtime 收益：

- 隔离被测仓库与 NanoHarness 自身的 pytest 配置；
- 修正 Failure Taxonomy 优先级，使预算耗尽和熔断不再被泛化成工具不可用；
- 用 Case、不可变数据版本和 Patch SHA 对齐裁决，新的 Patch 不继承旧结论。

## 3. 真实结果

| 版本 | 范围 | Context 阈值 | 已确认解决 | 候选 Patch | 无 Patch | 失败 ToolCall | Token / 成本 | 决策 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| R0 | Golden-10 | 65,536 | 1/10 | 5/10 | 5 | 29/248 | 3,041,338 / `$0.4098` | 基线 |
| R1 | Sentinel-4 | 32,768 | 1/4 | 3/4 | 1 | 8/98 | 1,066,854 / `$0.1435` | 拒绝 |
| R2 | Golden-10 | 49,152 | 1/10 | 8/10 | 2 | 19/227 | 2,641,315 / `$0.3514` | 采纳 |

表中 Token 和成本是各自范围的总量；R1 只能与 R0 的同一 Sentinel-4 子集配对，
不能用它的绝对总量与 Golden-10 横向比较。R0 与 R2 才是同一 Golden-10 上的直接对比。

R0 的失败 Pareto：6 个运行达到成本预算，其中 4 个没有 Patch；共 29 次失败工具调用；
`scikit-learn` 因连续三次失败工具触发熔断。

R1 看似漂亮：Sentinel-4 的 Token 比同组 R0 下降约 15%，失败工具调用下降 20%。但逐题
审查发现 `sympy-20590` 从修改源代码退化为只新增临时调试测试。聚合效率改善掩盖了语义
回归，因此 R1 被拒绝。这个负结果是实验中最重要的决策证据。

R2 把阈值调回 48K，并保留测量隔离。相对 R0：

- 已知 solved 锚点的 Patch SHA 完全一致，正确性锚点未退化；
- 候选改动覆盖 `5/10 → 8/10`，增加 30 个百分点；
- 无 Patch 退出 `5 → 2`，减少 60%；
- 失败工具调用 `29 → 19`，减少 34.5%；
- 总 Token 下降 13.2%，Provider Usage 估算成本下降 14.2%；
- 成本停止 `6 → 4`，但 `django-12209` 和 `sphinx-10323` 仍未形成 Patch。

因此采纳 R2 的结论是：**同一功能集合和资源边界下，Runtime 的收敛、工具稳定性与成本
得到改善。** 这不是“官方解决率从 50% 提升到 80%”。R2 只有 1 个已确认 solved，2 个
明确未解决，另外 7 个新 Patch 尚未完成官方裁决。
这个 48K 阈值被采纳为本实验的 DeepSeek 运行配置，没有被写成所有模型的全局默认值；
Context 预算应随模型窗口、任务长度和成本约束独立配置。

机器可读结果在
[`golden-10-v1.json`](../../benchmarks/runtime-quality/golden-10-v1.json)，本机保留原始 Trace
时可在 Workbench 下钻到逐题过程；GitHub 只提交小型、可审计摘要。

## 4. 设计复盘讲述

### 90 秒主线

> 功能集合冻结后，我没有继续堆 Feature，而是固定模型、十个覆盖六个仓库的 Case、工具
> 集合和资源预算，建立 R0。R0 只有 5/10 形成候选 Patch，主要瓶颈是预算停止和失败工具
> 调用。第一轮我尝试把 Context 阈值压到 32K，Token 的确下降了约 15%，但逐题哨兵发现
> SymPy 从源代码修复退化成只写调试测试，所以我拒绝了这个版本。第二轮改为 48K，既保住
> 已知 official-resolved 的完全相同 Patch，又把候选改动覆盖从 5/10 提到 8/10，无 Patch
> 退出减少 60%，失败工具调用减少 34.5%，Token 下降 13.2%。我采纳的是 Runtime 收敛和
> 成本改进；七个新 Patch 尚未官方裁决，因此没有把 8/10 包装成解决率。这个过程让我形成
> 了正确性优先、逐题哨兵、失败 Pareto、候选回滚和证据分级的调优方法。

### 追问口径

**为什么不直接报 SWE-bench 解决率？**

Golden-10 是用于快速诊断的开发集，且 7 个新 Patch 未完成官方裁决。报告总体解决率会把
候选产物和正确性混为一谈；每题仅运行一次，也不支持统计显著性声明。

**为什么 R1 指标更省还要拒绝？**

因为第一指标是语义正确性。SymPy 的临时测试 Patch 证明聚合 Token 和失败率会掩盖逐题
回归；Sentinel 的价值就是在扩跑前阻断这种版本。

**R2 最大的剩余问题是什么？**

长链 Case 仍受预算和验证失败影响；下一步应先完成 7 个新 Patch 的官方裁决，再决定是优化
Context 选择、验证恢复还是资源分配，而不是看到数字后继续增加工具。

**这项实验能证明什么？**

它证明我会把 Runtime 当成可测系统：固定条件、建立基线、按失败分布提出最小假设、设置
回归门槛、拒绝负优化，并明确区分候选 Patch、已确认解决和总体能力。它不证明 NanoHarness
达到生产级或排行榜水平。
