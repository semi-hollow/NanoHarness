# 回归测试与评测范围

本文只回答两件事：NanoHarness 当前有什么可复核的质量结果，以及不同证据分别能支持什么结论。
历史模型选型、低预算 Campaign 和被拒绝 Treatment 不在这里展开；需要审计时从
[评测历史归档](../../benchmarks/archive/README.md)按问题查阅。

## 当前结果

当前公开工程口径是：**单 Agent 在固定 SWE-bench Verified 开发样本上的 Pass@1 official
resolved 约为 40%（4/10）**。

| 字段 | 当前值 |
| --- | --- |
| 数据集 | SWE-bench Verified `test` |
| 样本 | 固定、已见的 10 个开发 Case |
| Agent 形态 | single Agent |
| 主指标 | official resolved / planned |
| planned | 10 |
| official resolved | 4 |
| official unresolved | 3 |
| empty / skipped | 3 |
| official infrastructure error | 0 |
| 当前公开表述 | 4/10，约 40% |

该观测证明 NanoHarness 已经能完成从真实 issue、仓库 checkout、模型工具循环、源码 Patch 到 official
evaluator 的端到端链路，并在部分任务上给出被官方测试接受的修复。它不等于完整 500 题 Verified
解决率，不隔离 Harness 相对底座模型的独立增益，也不允许改写成尚未运行的 `40/100`。

机器可读摘要见 [Quality Showcase](../../benchmarks/showcase/canonical-showcase-v1.json)。底层冻结结果保留在
Git 历史的 `3a96f14:benchmarks/runtime-quality/golden-10-v1.json`，其中包含 planned、官方 bucket、
运行配置和 evidence 路径。

## 下一轮确认实验

下一轮只做一件事：在新的、按仓库分层且预先冻结的 100-Case 样本上，用一个质量优先模型/profile
执行一次 Pass@1 确认性测量。启动前固定：

- dataset revision、100 个 Case 的成员与顺序；
- provider、model、Tool/Skill、Context、timeout 与安全配置；
- official image/evaluator 身份；
- `resolved / 100` 主分母、empty/infra 终态和零 correctness rerun；
- candidate、prediction 与 official input 的字节一致性。

该实验是扩大样本后的确认，不用于事后挑模型、换题或调参。结果出来后可以把公开句式更新为
“固定 100 题样本上 `X/100`”；在此之前保持当前 `4/10 ≈ 40%` 的样本边界。

## 四层证据不能混用

| 层级 | 回答的问题 | 不能证明 |
| --- | --- | --- |
| Runtime 契约测试 | 审批、恢复、压缩、防重复、熔断是否满足不变量 | 模型解决率 |
| Infrastructure Smoke-5 | dataset、checkout、Tool、Patch、evaluator、Evidence 链路是否健康 | 质量百分比 |
| 固定开发样本 4/10 | 当前系统是否具备真实仓库端到端解题能力 | 完整 Verified 总体率 |
| 未来 100-Case | 扩大样本后的固定测量值 | Harness 的单独因果增益 |

Candidate Patch、本地测试通过、Reviewer/Finalizer PASS 和进程 exit code 都不能替代 official resolved。
每个 planned Case 必须进入 resolved、unresolved、empty、provider infra 或 evaluator infra 之一，不能通过
丢弃失败题缩小分母。

## 为什么使用 SWE-bench Verified

它保留真实 issue、repository、base commit 和可执行 official tests，与 NanoHarness 的 repository-task
边界直接对应。它不覆盖 approval stale、Memory 生命周期或多 Agent merge conflict；这些机制由确定性
单元/集成测试证明。

其他基准只有在产品边界扩展后再接：通用 terminal 任务需要更宽的执行环境，业务 Agent 需要真实 API、
policy 和 user simulator。Benchmark 数量不是目标；可执行 oracle、完整分母和不会误导的结论才是目标。

## Runtime 契约回归

| 场景 | 保护的不变量 | 主要证据 |
| --- | --- | --- |
| approval + resume | 请求先持久化，未批准不执行；恢复不伪装成 Python 栈续跑 | `tests/test_human_approval.py`、`tests/test_task_resume.py` |
| operation ledger | 防重复执行；目标漂移或结果未知时 fail closed | `tests/test_operation_ledger.py` |
| context transaction | 压缩不能拆散 ToolCall 与对应 Observation | `tests/test_context_window.py` |
| command / path policy | 未授权命令和越界路径不能进入真实执行 | `tests/test_command_policy.py` |
| provider failure accounting | 失败请求、重试和 overflow 也进入 Usage/Evidence | `tests/test_llm_client_transport.py` |
| multi-agent merge | scope、worktree、冲突和只读 Finalizer 必须同时成立 | `tests/test_live_fanout.py` |

## 面试口径

主动说：

> 当前固定开发样本的 Pass@1 official resolved 是 4/10，约 40%。我把它当作个人项目已经跑通真实
> repository repair 闭环的工程基线；下一步用预冻结 100 题确认，不把小样本外推成完整榜单成绩。

被问“为什么只有 10 题”时：

> 这是目前完成且证据完整的一轮。样本小，所以我只把它叫开发样本观测；扩大到 100 题的协议已经明确，
> 但不会在结果出来前伪造 `40/100`。

被问“40%是谁的能力”时：

> 是固定模型、Runtime、工具、环境和 evaluator 组成的系统结果。我不把它全部归功于 Harness；要证明
> 某个 Runtime 机制的 uplift，需要同模型、同题、单变量的 matched experiment。
