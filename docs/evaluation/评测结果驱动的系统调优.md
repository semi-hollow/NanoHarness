# 从 Benchmark Case 到 Runtime 改进

本文只保留已完成 50×2 实验的设计、结果和决策。评测分母与回归范围见
[回归测试与评测范围](回归测试与评测范围.md)，分类优先级见
[失败分类规则与诊断流程](失败分类规则与诊断流程.md)。

## 1. 这次实验回答什么

固定 SWE-bench Verified 50 题、`deepseek-v4-flash`、AgentLoop、预算、安全边界和执行环境，比较：

- `minimal-control`：完整工具集，不注入 Skills。
- `governed-runtime`：task-aware Tool Routing + 自动 Skills。

两项因素同时变化，所以实验只回答“整套 preset 的实际取舍”，不能回答 Routing 或 Skills 单独造成了
多少变化。

## 2. 为什么是 50 × 2

- 50 题来自预先冻结的 100 题集合 A 分片，选择只依赖 `instance_id` 的 SHA-256 排序。
- 没看题目、gold patch 或历史结果后再挑题，避免挑容易成功的 Case。
- 每题运行两个 preset，形成同任务配对；执行顺序交替，降低 provider 时间漂移偏向一侧。
- 另一半 B 分片没有运行。以后扩到 100 题，或做单因素消融，只跑 B，不重复付费跑 A。

本次原始执行绑定源码 revision `34cbe9113bccd62438065cc7ce99af3c653aad4e`。运行结束后的
审计只修正聚合分母、重试成本和页面表达，不改写单 Case 的原始 scorecard；旧 scorecard 中由
taxonomy v1.0 生成的分类也保留原样，v1.1 的优先级修正从后续运行生效。

## 3. 真实结果怎么读

| 指标 | Minimal | Governed | 说明 |
| --- | ---: | ---: | --- |
| Official resolved / selected | 20/50（40.0%） | 14/50（28.0%） | 主结果，分母是预注册 Case |
| Candidate patch | 32/50 | 27/50 | 是否到达编辑阶段，不代表正确 |
| Accepted / evaluated patch | 20/32（62.5%） | 14/27（51.9%） | 只衡量进入 official verdict 的 patch |
| Failed tool calls | 36/993（3.63%） | 14/973（1.44%） | Governed 相对下降约 60.3% |
| Token | 8,308,931 | 8,078,883 | Governed 下降约 2.8% |
| 实际执行成本 | $1.242115 | $1.124990 | 含三次被丢弃的基础设施失败尝试 |

一个 governed 槽位在 provider error 重试后仍失败。排除这一基础设施 pair，49 组可裁决结果为：
Minimal 6 胜、Governed 1 胜、42 平。

**决策**：拒绝整体采纳 governed preset。它减少了无效工具调用，却降低 patch reachability 和当前
样本 correctness。下一轮应在 B 分片把 Routing 与 Skills 分开做单因素实验。

## 4. 一条 Case 怎样变成证据

```text
冻结 Case + Runtime 配置 + source revision
  -> AgentLoop 运行
  -> Trace / Usage / Candidate Diff
  -> Local validation
  -> Official per-case report
  -> Failure Taxonomy
  -> Scorecard
  -> Campaign 聚合与人工决策
```

在证据职责上，Trace 是过程流水，Official report 是最终回执，Taxonomy 是失败归因，Campaign
summary 是批次汇总，人工 `adopt / iterate / reject` 是最终采纳决策。不能用中间流水替代最终回执。

## 5. 代表性 Case 抽样

每轮实验从以下类别各抽取 1 至 2 条，无需逐条检查全部 100 个 Run：

1. **Official resolved**：确认正确路径经过哪些文件、工具和验证。
2. **Official rejected**：对照 candidate diff 与 official test，定位是检索、推理、编辑还是验证问题。
3. **No patch / pending tool**：看预算结束前为什么没有收敛，是否在重复读、错误路由或缺少决策门。
4. **Infrastructure failure**：确认与 Agent failure 分离，原配置只重试一次，不借重跑挑好结果。

每条记录五项信息：触发现象、第一条分叉证据、根因层、可改变量、最小复现实验。

## 6. 数据飞轮不是自动加 UT

```text
聚合发现差异
  -> 按 failure class 分层
  -> 抽样回看 Trace 和 Diff
  -> 提出一个可证伪假设
  -> 固定其他变量做 matched experiment
  -> 通过 official oracle 验证
  -> 人工 adopt / iterate / reject
  -> 把稳定机制写入 Runtime 契约回归
```

UT 保护已经确定的 Runtime 不变量；Benchmark 判断这些机制是否真的改善真实任务。失败样本不会自动变成
训练数据，也不会自动改 Prompt。未经人工复核的 Taxonomy 只是候选归因。

## 7. 实验结论摘要

结论可概括为五点：

1. 实验预先冻结 Verified 的 100 题确定性 cohort，本轮仅运行互斥的 50 题 A 分片。
2. 每题用相同模型、预算和 AgentLoop 配对比较两个 Runtime preset，并以 official evaluator 为 oracle。
3. 100 个槽位中 Minimal 解出 20/50，Governed 解出 14/50；后者把失败工具调用率从 3.63% 降到 1.44%。
4. 治理减少了无效动作，但当前组合同时损害 patch reachability，因此实验不支持“整体提升”结论。
5. 下一步不重复跑 A，而是在冻结的 B 分片分别消融 Tool Routing 与 Skills，判断是哪一个因素造成收益和损失。

## 8. 结论边界核对

- 为什么 `20/32` 不能写成 62.5% 的总体解决率？
  因为 32 只包含产生并进入评测的 patch，漏掉了 18 个 no-patch；主分母必须是预注册的 50。
- 为什么基础设施错误不能直接算模型失败？
  因为 provider 或 evaluator 没有完成能力裁决；最多原样重试一次，仍失败则披露并从 pair 裁决排除。
- 为什么不能直接说 Skills 有害？
  因为 governed 同时改变 Routing 和 Skills；当前只能拒绝这套组合，不能归因到单一因素。
- 为什么下一轮要用 B 分片？
  因为 A 已经参与观察和决策；继续在 A 上调参会产生测试集过拟合，也会重复花费。
- 这是不是 SWE-bench 官方分数？
  不是。它是固定 50 题、单次运行、指定模型与本地 Runtime 配置下的工程样本结果。
