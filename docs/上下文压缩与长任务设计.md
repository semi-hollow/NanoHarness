# 上下文压缩与长任务设计

> 当前实现保持不变。  
> 本文用于解释：为什么当前方案合理、为什么它不是最终生产形态、不同任务长度应该采用什么策略。

---

# 1. 当前 NanoHarness 怎么压 Conversation

```text
完整 session.messages
        ↓
完整 Request Token Estimate
        ↓
超过 soft limit
        ↓
按 ToolCall / Observation 事务切 segment
        ↓
old segments
        ↓
ConversationHistoryDigest
        │
        ├→ 本轮 LLM
        └→ TaskCheckpoint

recent raw segments
        ↓
本轮 LLM
```

优点：

```text
协议事务不拆
原始 Session/Trace 不删除
Digest 有 source hash
结果确定性可重算
实验容易审计
```

---

# 2. 当前方案真正的局限

每个 Turn 仍然：

```text
完整 session.messages
↓
重新扫描
↓
重新搜索 cut boundary
↓
重新构造 Digest
```

所以长链路越跑越久：

```text
live raw history size ↑
compaction scan cost ↑
state duplication ↑
```

当前选择的 trade-off 是：

> 优先可审计、可复现，而不是极致长任务效率。

---

# 3. 生产目标：Incremental Rolling Compaction

不推荐：

```text
summary(summary(summary(...)))
```

推荐：

```text
Canonical Raw Event Store
        │
        ▼
CompactedConversationState
├── covered_until_seq
├── task / constraints
├── decisions
├── important tool facts
├── validation state
├── unresolved issues
└── artifact refs

+
Recent Raw Tail
```

下一次只处理增量：

```text
Old Compacted State
+
New Raw Delta
        ↓
typed merge/update
        ↓
New Compacted State
+
Recent Raw Tail
```

核心是：

```text
增量状态归并
≠ 反复自由文本摘要
```

# 4. 不同任务长度怎么选

## 4.1 短任务

典型：

```text
< 10~20 Turns
History 远低于窗口
运行几分钟
```

方案：

```text
完整 Conversation
+
bounded WorkingMemory
```

不要为了“架构先进”提前压缩。

---

## 4.2 中长任务

典型：

```text
History 接近窗口
工具调用多
仍属于同一主要任务阶段
```

方案：

```text
incremental digest
+
recent raw tail
+
bounded WorkingMemory
+
selective Repo Context
```

---

## 4.3 超长 / 多阶段任务

典型：

```text
几十分钟到小时
Turn 数不可预测
有多阶段
可能等人
可能 crash
外部副作用多
```

需要：

```text
explicit plan/task state
+
durable compacted conversation state
+
artifact/reference based context
+
phase-local recent tail
+
checkpoint/resume
```

---

# 5. 长任务真正的 6 类系统问题

长任务不是“Context 太长”的同义词。

## 5.1 上下文增长 / Context Growth

```text
bounded context
incremental compaction
retrieval
progressive disclosure
```

## 5.2 崩溃与恢复 / Crash & Resume

```text
durable checkpoint
continuation-safe state
```

## 5.3 副作用重放 / Side-effect Replay

```text
Operation Ledger
idempotency
executing/executed distinction
fail closed
```

## 5.4 无进展循环 / No-progress Loop

```text
repeat detection
failure fuse
budget
bounded retry
progress watchdog
```

## 5.5 计划漂移 / Plan Drift

```text
completed / remaining / blocked
acceptance criteria
bounded replan
```

## 5.6 截止时间传播 / Deadline Propagation

```text
global run deadline
↓
model timeout
tool timeout
subprocess timeout
subagent timeout
```

如果 deadline 不向内部传播，Runtime 只能等阻塞调用返回后才知道“早就超时了”。

---

# 6. NanoHarness 当前做到哪

已经较强：

```text
Checkpoint / Resume
Operation Ledger
HITL
Repeat Detection
Failure Recovery
Budget
Tool Governance
Trace / Eval
```

当前明确可演进：

```text
incremental Conversation compaction
cached/incremental Repo context
in-flight deadline propagation
more explicit long-task plan state
```

Multi-Agent V1 已在自己的 feature branch 补齐：

```text
explicit plan
acceptance criteria
bounded replan
```

这些 V1 能力不等于增量压缩、in-flight deadline 等 Long-task 改动已经实现。

---

# 7. 工程边界说明

> 当前版本为了保证实验可审计性，完整 Raw Conversation 一直保留；只有在单次模型请求接近窗口时，Runtime 才按 ToolCall/Observation 事务边界把旧 History 投影成结构化 ConversationHistoryDigest，同时保留 recent raw tail。这样不会出现 ToolCall 和 Observation 被拆开的协议错误，也可以从 raw trace 重建压缩结果。实际跑长链路以后我发现，这种每轮从完整 History 重算 digest 的方式不适合作为最终生产形态；生产版本会切换成 durable compacted state + covered cursor + recent raw tail，每轮只 merge 新增 delta。这里我没有为了“看起来完整”立即重写实验版本，而是把 trade-off 和演进方向明确分开。
