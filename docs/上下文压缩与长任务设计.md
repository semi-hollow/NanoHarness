# 上下文压缩与长任务设计

> 核心结论：`conversation.jsonl` 保存无损事件历史；`ConversationHistoryDigest` 只保存继续执行所需的确定性投影；模型同时看到 digest 与最近 journal tail。Compaction 不删除或改写原始对话。

## 1. 为什么需要 Compaction

长任务会持续追加用户约束、Assistant 分析、ToolCall 和 Tool Observation。全部原文每轮重发有三个问题：

- Provider context window 有限；
- 按消息数截断可能拆开 ToolCall 与 Observation；
- 按位置删除可能让用户约束永久退出模型可见上下文。

因此 NanoHarness 把 durability 与 model visibility 分开：

```text
raw Conversation authority
+ deterministic continuation projection
+ recent journal tail
= one bounded Model Step input
```

这里最重要的边界是：

```text
Event History != Durable Continuation State
```

一次旧 `read_file` 的完整返回是可重建事件；“不能修改 public API”是 human authority；某个测试目标当前仍然失败是 current state。三者不能使用同一种 retention 规则。

## 2. 三个核心持久化对象

### 原始对话权威：`conversation.jsonl`

`ConversationThreadRepository` 以 append-only journal 保存每个 canonical Conversation item，并维护 sequence/hash chain。Compaction 只读取它，不删除、不覆盖、不重排磁盘内容。

`ask_human` 是一个特殊投影：journal 为了授权 provenance 先持久化 human answer，模型输入再把完整事务排列为 `Assistant ToolCall → all Tool Observations → human answer`。重排只发生在内存视图，raw sequence 不变。

### 上下文状态：`context_state.json`

它持久化：

```text
revision
covered_sequence
conversation_history_digest
turn_snapshots[]
```

- `covered_sequence` 是 journal compaction cursor：后续正常 Model Step 只加载该 sequence 之后的 raw delta。
- `revision` 是整个 `ThreadContextState` 的 CAS version；保存时必须提交读取到的 `expected_revision`。
- `conversation_history_digest` 是 derived projection，当前使用 clean-break digest schema V2。
- `turn_snapshots[]` 保存同一 Turn 的稳定输入快照；它不是 Conversation digest。

`covered_sequence` 与 `digest.covered_message_count` 不能混用：前者是 canonical journal 位置，后者只是 derived projection 的累计审计计数。

### 运行恢复指针：`TaskCheckpoint`

Checkpoint 不复制 digest，只保存 `context_revision`，表示当前 Run 绑定的 Context State version。另一个写入已经推进 revision 时，本次 Model Step preparation fail closed，不做 last-write-wins。

## 3. 一次 Model Step 如何得到最终历史

入口是 `ModelStepPreparation.prepare_model_step()`：

```text
load ThreadContextState
→ verify session.context_revision == state.revision
→ restore previous digest from context_state.json
→ load conversation.jsonl after covered_sequence
→ group transaction-safe segments
→ search compact-prefix candidates
→ build delta digest and merge previous digest
→ CAS persist context_state.json
→ return final llm_messages
```

### 真实 rolling 例子

假设：

```text
covered_sequence = 850
previous digest 已覆盖 journal 1..850
当前 uncovered journal = 851..1000
```

Repository 只加载 `850` 之后的有界 page，并按事务分为：

```text
S1, S2, S3, S4, S5 ...
```

每个普通消息是一个 segment；一个 Assistant ToolCall batch、它的全部 Tool Observations，以及可能存在的 `ask_human` answer 是一个不可拆 segment。

若完整请求超过 soft limit，`PromptWindowManager` 从最小 legal prefix 开始：

```text
candidate 1 = previous_digest + digest(S1)       + recent(S2..)
candidate 2 = previous_digest + digest(S1..S2)  + recent(S3..)
candidate 3 = previous_digest + digest(S1..S3)  + recent(S4..)
```

实现不是为每个 candidate 重新提取 `S1..Sn`。它每轮只对下一个 segment 调一次 `_build_digest()`，把 delta rolling merge 后再估算完整 prompt。

完整估算包含 System Context、digest、recent messages、transient Runtime control、Tool schemas 和 reserved output。普通压缩目标是 soft input limit；Provider overflow 的 forced compaction 目标是 soft limit 的 65%。第一个达到目标且确实缩小请求的 candidate，就是最小可行 compact prefix。

`recent(Sn..)` 表示尚未进入 digest 的 journal items。模型投影会对单条 `content/reasoning_content` 做 deterministic excerpt：普通压缩最多 2000 chars，forced compaction 最多 800 chars；journal 原文不变，ToolCall/Observation 事务仍整体保留。

如果所有 candidate 都未达到目标，Runtime 只接受“所有候选中估算最小且确实比原请求小”的 best-effort 结果，并用 `*_best_effort_reduction` reason 明确它没有冒充 target satisfied。若没有任何安全缩小，则 cursor 不前移。

候选成功后：

```text
covered_sequence: 850 → compact prefix 对应的最大 raw sequence
conversation_history_digest: previous + delta
revision: r → r + 1 after CAS
```

下一 Model Step 不再加载或重新总结 `1..new covered_sequence`。

### 超过一页的长任务

每页默认最多加载 200 个 item，并用 bounded lookahead 补齐页尾 Tool transaction。若 Thread 仍有后续 page，Runtime 强制 rolling merge、CAS 推进 cursor、再加载下一页；中间 page 从不发送给模型。追到最新 tail 后才构造一次最终 Model request。

## 4. Digest 保什么，淘汰什么

当前 V2 数据结构：

```text
ConversationHistoryDigest
├── initial_task
├── authority_updates[]
├── resource_hints[]
├── state_evidence[]
├── recent_tool_transactions[]
├── workspace_mutation_observed
├── covered_message_count
├── source_hash
└── estimated_tokens_before / after
```

`source_hash` 是 `previous digest hash + raw delta hash` 的链式证据，不冒充完整 journal hash。

### `initial_task` 与 `authority_updates`

只有 `role=user && human_authority=true` 才能进入 authority。Runtime coordination 即使使用 `role=user`，也不能获得 human authority。

- `initial_task` 单独保存，不重复加入 updates；
- 后续 authority 每条 normalize whitespace，并用 `truncate_middle` 限到 480 chars；
- update 数量不做 first/last position eviction；
- authority 总字符超过 `max(512 chars, hard input chars × 25%)` 时抛出 `authority_context_overflow`，不猜哪条约束更重要。

这是 deterministic POC 的明确边界：单条输入允许可审计 excerpt，但不同 authoritative inputs 不按位置静默删除。

### 最近工具事务：`recent_tool_transactions`

它只保存最近 8 个已 compacted Tool transactions：

```text
tool_name
capability
mode
arguments_summary
success
observation_excerpt
```

Retention 是直接的 latest-8。它的职责只是回答“最近做了什么、结果怎样”，不是长期 semantic memory；因此不存在“最早 1/3 + 最近 2/3”。

8 条也不是“足够记住任务”的假设。任务意图由 authority 保存，当前验证状态由 state evidence 保存，代码事实由 workspace 保存；8 只是一段 execution breadcrumb window。

### `state_evidence` 与 `unresolved_failures`

只有 Tool Router metadata 中 `capability=validate` 或 `mode=command` 的事务产生 durable current-state evidence。key 为：

```text
capability : tool_name : sha256(canonical arguments)[:16]
```

arguments 先做 JSON 结构与 key order normalization，但保留字符串值内部的精确空白，避免把两个不同命令错误合并；`arguments_summary` 再单独做有界可读 excerpt。同 key 采用 latest-value-wins，不同 key 独立存在。

状态是：

```text
passed | failed | blocked | unknown | stale
```

`validation_blocked:` 是 Validation Tool 的显式协议标记，因此不会因为 `Observation.success=true` 被错误渲染成 PASS。

成功的 `capability=edit` 或 `mode=write` 会把此前 validation/command states 标为 `stale`。修改源码后，修改前的 PASS 和 FAIL 都仍是历史证据，但都不能继续冒充当前 workspace 的验证结果；同 key 后续重跑会再用新的 PASS/FAIL 覆盖。`workspace_mutation_observed` 是让 delta merge 能跨页、跨 Run 传播这一失效边界的 deterministic flag。

`unresolved_failures` 不是第二份持久化列表，而是 `state_evidence` 中所有非 `passed` 项的 derived view。这样 `FAIL → PASS` 只更新一个 authority：新 PASS 替换同 key FAIL，derived unresolved view 自然清空。

不同 state key 不按 latest-N 静默淘汰。超过 32 个 distinct keys，或 state projection 超过 `max(512 chars, hard input chars × 25%)`，抛出 `state_evidence_overflow`。

### 资源线索：`resource_hints`

Resource hint 是可选导航线索，不是事实缓存。实现只从固定 Tool argument keys `path / validation_target / keyword` 提取标识，每条最多 160 chars，去重后保留最新 24 个。它不扫描 Observation，也不做重要性 ranking。

旧 hint 可以淘汰，因为 Agent 随时可以在当前 workspace 重新 `list/read/grep`。

### Coding Agent 例子

原始事件：

```text
user: 修复 auth refresh bug
read auth.py
grep refresh
user: 不能修改 public API
replace auth.py
pytest tests/test_auth.py -> FAIL
read tests/test_auth.py
replace auth.py
pytest tests/test_auth.py -> PASS
git diff
```

压缩后的 continuation projection 接近：

```text
initial_task:
- 修复 auth refresh bug

authority_updates:
- 不能修改 public API

state_evidence:
- [passed] validate:python_validation:<args-hash>
  {"check_type":"pytest","validation_target":"tests/test_auth.py"}

unresolved_failures:
- none

resource_hints:
- auth.py
- tests/test_auth.py
- refresh

recent_tool_transactions:
- 最近 8 个事务，包括最后一次 pytest PASS 与 git diff
```

最早的 `read_file` Observation 可以退出 digest，因为源码可能已经变化，当前 workspace 才是 code state authority。write Observation 也不是代码 authority；需要确认实际改动时重新读取 workspace 或 `git diff`。第一次 pytest FAIL 被同 key PASS supersede，因为 continuation 关心当前已知状态，而不是失败年表。

### 明确允许退出模型可见上下文的内容

- 超过 recent-8 的 generic Tool events；
- read/search/discover 返回的旧大段 Observation；
- write/edit 的旧执行回执；
- 被同 key 新状态 supersede 的 validation/command 状态；
- 超过 latest-24 的 resource hints；
- Assistant 的旧自由文本分析，除非仍在 recent tail。

这些内容仍完整存在于 `conversation.jsonl`，只是 normal continuation 不再自动重发。

## 5. 为什么当前不用 LLM、Embedding 或 BM25

当前目标是 deterministic、recoverable、auditable 的 Agent Runtime POC。该方案：

- 不新增 Provider call、retry、timeout、cancellation 与 usage attribution 链路；
- 同一 raw delta 和 metadata 产生同一结构化事实投影（`created_at` 审计时间除外）；
- resume 可直接恢复并继续增量 merge；
- retention 与 overflow 都能用源码和测试直接验证。

它不承诺回答：

> 200 个 ToolCall 以前某次 `read_file` 返回的任意一句源码，是否仍具有跨长时间的语义价值？

在没有 semantic summarization/retrieval 时，用越来越多自定义规则回答这个问题会变成 heuristic soup。当前承诺是：

1. raw Conversation 永不因 compaction 丢失；
2. human authority 不按位置静默丢失；
3. keyed current/unresolved state 不按位置静默丢失；
4. generic reconstructable event history 允许淘汰；
5. current workspace 是 code state authority；
6. recent execution breadcrumbs 有界保留；
7. durable deterministic facts超出预留时 fail closed。

未来如果产品要求任意 long-horizon semantic recall，可以在相同 raw/digest boundary 后升级到 governed semantic summarization 或 retrieval，再对结构化结果做 Runtime validation；当前不实现。

## 6. Resume 与长任务恢复

Resume 恢复的是显式 durable state，不是 Python stack、Provider KV cache 或隐藏模型状态：

```text
same Thread + same Turn + new Run
→ restore StableTurnContextSnapshot
→ load ThreadContextState and verify context_revision
→ restore digest directly from context_state.json
→ load only raw journal items after covered_sequence
→ continue rolling compaction when needed
```

因此：

- covered raw prefix 不重新读取、不重新 build digest；
- Checkpoint 只携带 `context_revision` pointer；
- CAS conflict 在模型调用前失败；
- raw journal 仍可独立审计；
- normal follow-up 创建新 Turn，但继续复用同一 Thread 的 rolling digest。

## 核心源码入口

- `agent_forge/context/application/compaction.py::PromptWindowManager.prepare()`：segment、candidate search、capacity 与 merge。
- `agent_forge/context/application/compaction.py::_build_digest()` / `_merge_digest()`：delta extraction 与 incremental state transition。
- `agent_forge/context/domain/conversation_digest.py`：V2 digest、Tool transaction/state schema 与 render。
- `agent_forge/runtime/application/model_step_preparation.py::ModelStepPreparation.prepare_model_step()`：分页追赶、CAS persist 与最终 `llm_messages`。
- `agent_forge/runtime/domain/thread.py::ThreadContextState`：cursor/revision/digest/snapshot 的持久化边界。
- `agent_forge/runtime/adapters/thread_json.py::JsonConversationThreadRepository`：append-only journal 与 atomic Context State persistence。
